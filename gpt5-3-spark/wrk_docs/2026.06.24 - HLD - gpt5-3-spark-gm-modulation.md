# 2026.06.24 - HLD - GM Modulation Enrichment for gpt5-3-spark

Status: SIGNED-OFF
Owner: Arthur + Codex
Task: Enrich GM MIDI expressive controls in `gpt5-3-spark` tracks and verify richer controller usage.

## 1) Scope
- In scope
  - `gpt5-3-spark/engine.py`
  - GM-compatible track-generation behavior and verification output in `gpt5-3-spark`.
  - Naming format for generated track files/tracks should remain aligned with existing `gpt5-5` style.
- Out of scope
  - `opus4-8`, `gpt5-5`, and non-`gpt5-3-spark` code paths.
  - Migration, feature flags, backward-compatibility shims.

## 2) Approach
- Keep musical structure unchanged (same tracks, durations, songs, and names).
- Extend `MidiTrack` with GM-safe modulation events:
  - `pitch_bend(channel, value, beat, center=8192)`
  - `channel_pressure(channel, value, beat)`
  - helper for RPN pitch-bend-range setup using CC99/CC98/CC6/CC38/CC101/CC100 pattern.
- Extend `setup_expression()` to add non-default, time-varying controls per track:
  - Keep existing CC7 (volume), CC10 (pan), CC64 (damper), CC91 (reverb), CC11 (expression).
  - Add CC1 (modulation wheel), CC71 (resonance), CC74 (brightness), and a small global pitch-ramp in selected tracks.
  - Use bar-position interpolation derived from existing `intensity` so expression changes feel tied to song form.
- Apply modulation events per track type:
  - `Piano`, `Strings`, `Violin family`, and `Celesta` get regular CC1/CC71/CC74 and periodic pitch bends.
  - `Conductor` remains meta-only (tempo, keysig, markers).
  - `Low percussion` keeps only control updates that fit percussion semantics (volume/pan/expression/sustain), avoiding aggressive pitch-bend on drum channel.
- Add parser-level verification for richer output:
  - Track parse now tracks CC controller counts, pitch-bend counts, and channel-pressure counts.
  - `verify_album()` adds checks that melodic tracks include:
    - at least one non-default modulation CC (CC1),
    - at least one brightness/control tweak (CC74),
    - at least one pitch-bend and optional one channel-pressure event in tracks that support it.
- Keep output order deterministic and reproducible by existing deterministic RNG.

## 3) File impact
- `gpt5-3-spark/engine.py`
  - Add new MIDI event methods for modulation messages.
  - Extend `setup_expression()`, add small expression profile helper.
  - Extend `parse_midi()` return data with control-event metrics.
  - Extend `verify_album()` thresholds/requirements accordingly.

## 4) Acceptance criteria
- [ ] Track filename and in-file track naming follows current project format and matches the existing `gpt5-5` conventions.
- [ ] `python .\build.py` regenerates all 12 MIDI files and `album_manifest.json` without runtime errors.
- [ ] `python .\build.py --verify` succeeds.
- [ ] For each generated MIDI, `parse_midi()` reports:
  - tempo map present (existing requirement preserved),
  - >=1 track with CC1 present,
  - >=1 pitch-bend message somewhere in melody-heavy tracks,
  - per-track control metadata present for verification confidence.
- [ ] Musical density checks remain conservative (duration, format, PPQ, note-on volume).

## 5) Decision log
- Decision: stay entirely in `gpt5-3-spark/engine.py`.
  - Why: avoids cross-project churn and keeps behavior changes scoped.
- Decision: apply modulation depth conservatively and avoid percussive abuse of bends.
  - Why: keep GM behavior stable across DAWs and drum channels.
- Decision: no non-GM controller payloads (no SysEx, no nonstandard NRPN-only-only sequences).
  - Why: user requested GM compatibility and broad playback support.

## 6) Adversarial design review (independent)

Reviewer A (feature-risk lens)
- Risk A1: Added CCs could inflate tempo/CPU validation by generating many redundant CCs, possibly bloating files.
- Refutation attempt A1: Keep events bar-aligned with low-frequency updates and reuse existing bar loop in `setup_expression`; event count increase should remain bounded and parse still allows large tracks. Marked as low risk.

Reviewer B (correctness lens)
- Risk B1: Pitch-bend without explicit pitch-bend-range setup can make values behave inconsistently across devices.
- Refutation attempt B1: Add explicit RPN range setup to 2-semitone default before bend automation; fallback clamp keeps values safe. Accepted only if implementation includes explicit setup.

Reviewer C (playback/format lens)
- Risk C1: Parser currently ignores channel pressure/pitch bend and could silently pass while new requirements fail.
- Refutation attempt C1: Extend parser output to track pitch-bend and channel-pressure counts and wire those checks into `verify_album()`. Accepted.

Surviving findings to carry forward
1. Explicit pitch-bend-range initialization should be included (to avoid device variance).
2. Verification must actually observe richer controls (not assume writes succeeded).
