# hollowsynth realtime / mddosem integration HLD

Status: DRAFT - awaiting Arthur sign-off

## Intent

Make `hollowsynth` usable as a live General MIDI-ish synth inside `mddosem` by adding a stateful raw-MIDI/block-render library API while preserving the existing offline MIDI-to-WAV CLI.

## Scope

- Add a reusable `hollowsynth` library surface beside the current CLI.
- Accept live MIDI bytes, including running status, and translate supported channel messages plus reset commands into crate-private live commands.
- Render stereo `f32` audio into caller-owned buffers in arbitrary frame counts.
- Keep the public realtime API independent of `mddosem` traits and private offline parser types so `hollowsynth` remains standalone.
- Preserve current offline rendering behavior and tests.
- Document the downstream `mddosem` adapter shape, but do not implement `mddosem` changes in this repo.

## Non-goals

- No DAW plugin, C ABI, VST, or audio-device ownership in `hollowsynth`.
- No dependency from `hollowsynth` to `mddosem-types`.
- No full GM completion beyond the separate v0.9 branch and req-ledger instrument work.
- No MIDI clock tempo-following in V1. Live echo delay uses an explicit/fixed option.
- No sample-accurate MPU timestamping. The V1 renderer accepts untimestamped byte streams and applies complete messages at the next internal 64-sample boundary.
- No hard realtime guarantee for note creation. V1 should avoid steady-state allocation during render blocks with no new events, but may allocate when voices are spawned.
- No claim that `mddosem`'s current threaded synth path is already low-latency enough. That must be measured or adjusted during the later `mddosem` integration.
- No migration, rollback, feature flags, or environment-variable switches.

## Existing Shape

- `fable5/hollowsynth/src/main.rs` is a binary-only CLI: parse SMF, build `engine::Options`, call `engine::render`, normalize, write WAV.
- `fable5/hollowsynth/src/midi.rs` is an SMF parser. It emits `EvKind`, but it is not a live MIDI byte parser.
- `fable5/hollowsynth/src/engine.rs` owns all synth state inside `render_buses`: channel strips, active voices, sends, reverb, chorus, echo, drum room, glue, scratch buffers, and stats. It walks a complete `Song`.
- `fable5/hollowsynth/src/voices.rs` voices already render into caller-provided slices, so the voice layer is usable for realtime once engine state is persistent.
- `fable5/hollowsynth/src/sampler.rs` embeds sample bytes with `include_bytes!` and lazily parses them via `OnceLock`. Runtime deployment stays self-contained, but a live API should offer prewarming to avoid a first-note parse hitch.
- `mddosem`'s synth interface is raw-MIDI-byte input plus additive stereo block output: `MidiWriter::write_byte(u8)` and `MidiSynth::generate_samples(count, sample_rate, output)`. `generate_samples` adds into `output`, it does not clear it.
- `mddosem_types::MidiSynth` requires `Send + 'static`. A threaded adapter will only compile if the owned `RealtimeSynth` is `Send`; today `voices::Voice` has no `Send` supertrait.
- `mddosem::ThreadedSynth` currently owns an 80 ms stereo audio ring and can generate up to 1024 frames after draining MIDI. That protects emulator timing, but it does not guarantee low MIDI-to-audio latency.

## Approach

### 1. Split binary and library

Add `fable5/hollowsynth/src/lib.rs` and move module ownership there:

```rust
pub mod live;
pub mod offline;

mod drums;
mod dsp;
mod engine;
mod midi;
mod reverb;
mod sampler;
mod voices;
mod wav;
```

Keep `main.rs` as the CLI wrapper. It should call the library's existing offline entry points rather than privately owning all modules.

The library exports two surfaces:

- Existing offline surface in `offline`, intentionally small: parse/render/write helpers needed by the CLI and tests.
- New realtime surface in `live.rs`. It must not expose `midi::EvKind` or any other private offline implementation type.

### 2. Factor engine state out of offline rendering

Create a persistent engine core inside `engine.rs`, for example:

```rust
pub(crate) struct EngineCore {
    sr: u32,
    opt: CoreOptions,
    strips: [Strip; 16],
    active: Vec<Active>,
    buses: BusState,
    scratch: Scratch,
    output_ring: SmallStereoRing,
    stats: Stats,
}
```

The exact type names can follow the current file's style. The important boundary is:

- `EngineCore::new(options)` initializes channel strips, bus effects, scratch buffers, and stats once.
- `EngineCore::handle_event(EvKind)` applies one MIDI-like event to persistent channel state.
- `EngineCore::handle_command(LiveCommand)` applies channel events and reset commands for the realtime path.
- `EngineCore::render_add(frames, output)` renders `frames` stereo frames and adds them to `output`.
- Offline `render_buses(song, opt, bus_mode)` becomes a scheduler around `EngineCore`: convert song events to sample positions, feed due events, render blocks, then keep the existing offline normalization path.

Preserve the current `BLOCK = 64` internal processing quantum for live mode. `RealtimeSynth::render_add` serves arbitrary caller frame counts from a small internal stereo output ring:

- Complete live messages received before `render_add` apply at the next internal 64-sample boundary after any already-buffered output.
- Incomplete messages do not fire until enough bytes arrive.
- Splitting `render_add(64)` into `render_add(32)` + `render_add(32)` with no intervening MIDI writes should produce the same output within a tight floating-point tolerance.
- The ring should only buffer the remainder of the current internal quantum, not pre-render a long queue. Added synth-side latency is therefore under 64 frames, about 1.45 ms at 44.1 kHz, before any host or `mddosem` buffering.
- Controller smoothing, wah, aftertouch, expression, CC1, and portamento can keep the current once-per-64 math because the live path always advances them on that same internal quantum.

This chooses byte-identity and simpler engine extraction over a larger variable-block rewrite. A variable-block design would need every smoothing coefficient and the stored portamento glide coefficient re-derived from the actual frame count; that is out of scope for V1.

`RealtimeSynth` must be `Send`. The likely implementation is to add `Send` to the `Voice` trait (`pub trait Voice: Send`) after verifying all concrete voice structs are `Send`, then add a compile-time assertion for `RealtimeSynth: Send`.

### 3. Add a live MIDI byte parser

Add a crate-private parser in `live.rs` or `midi_live.rs`, with no external dependency:

```rust
pub(crate) struct MidiByteParser { ... }

pub(crate) enum LiveCommand {
    Channel(EvKind),
    Reset(ResetKind),
}

pub(crate) enum ResetKind {
    GmSystemOn,
    SystemReset,
}

impl MidiByteParser {
    pub(crate) fn push(&mut self, byte: u8, out: &mut Vec<LiveCommand>);
    pub(crate) fn reset(&mut self);
}
```

Supported V1 behavior:

- Channel voice messages:
  - Note Off: `0x8n key vel`.
  - Note On: `0x9n key vel`; velocity 0 becomes Note Off.
  - Poly Aftertouch: `0xAn key pressure`; consume both data bytes and ignore the event.
  - Control Change: `0xBn cc value`.
  - Program Change: `0xCn program`.
  - Channel Pressure: `0xDn pressure`.
  - Pitch Bend: `0xEn lsb msb`, converted to the same semitone range used by the SMF parser.
- Channel-message data lengths are driven by the high nibble, including ignored messages: 0x8/0x9/0xA/0xB/0xE consume two data bytes, 0xC/0xD consume one.
- Running status works across channel messages.
- MIDI real-time bytes `0xF8..=0xFE` do not clear running status. `0xFF` is live MIDI System Reset and emits `LiveCommand::Reset(SystemReset)`.
- SysEx is skipped safely with fixed bounded state. The parser only needs to keep enough bytes to recognize GM System On (`F0 7E <device> 09 01 F7`, device id tolerant); longer or unrecognized SysEx is skipped until `F7` without unbounded allocation.
- Real-time bytes inside SysEx are handled as real-time and do not become SysEx payload bytes. `0xFF` inside SysEx still performs System Reset and exits the partial SysEx state.
- System Common messages are consumed by documented length: F1 consumes one data byte, F2 consumes two, F3 consumes one, F6 consumes none, F4/F5 are ignored. System Common and SysEx clear running status; real-time bytes do not.
- Bare data bytes without running status are ignored.
- `F7` outside SysEx is ignored and leaves the parser recovered.
- Unsupported channel messages are ignored without panics. Poly aftertouch remains ignored, matching the SMF parser's current behavior.

The parser is deliberately byte-oriented so `mddosem` can forward bytes exactly as its MPU/WinMM paths already do.

### 4. Realtime API

Add the public API in `live.rs`:

```rust
pub struct RealtimeOptions {
    pub sample_rate: u32,
    pub wet: f32,
    pub delay_s: f32,
    pub samples: bool,
    pub master_gain: f32,
}

pub enum RealtimeError {
    OutputTooSmall { needed: usize, got: usize },
}

pub struct RealtimeSynth { ... }

impl RealtimeSynth {
    pub fn new(options: RealtimeOptions) -> Self;
    pub fn reset(&mut self);
    pub fn prewarm_samples(&self);
    pub fn write_byte(&mut self, byte: u8);
    pub fn render_add(&mut self, frames: usize, output: &mut [f32]) -> Result<(), RealtimeError>;
    pub fn active_voice_count(&self) -> usize;
}
```

Defaults:

- `sample_rate`: caller supplied.
- `wet`: match the CLI default unless mddosem integration chooses a different user default.
- `delay_s`: fixed 0.375 s by default, equivalent to a dotted-eighth feel at 120 BPM. Live mode does not derive delay from MIDI clock.
- `samples`: true by default, because the sample bytes are embedded.
- `master_gain`: use a conservative default calibrated during implementation against both sparse single-note and dense GM fixtures. Realtime cannot use offline peak normalization, so the output stage must apply fixed gain and a simple soft limiter/saturating guard to keep output finite and within a usable emulator-mix range.

`render_add` checks `output.len() >= frames * 2` before rendering. If the buffer is too small, it returns `RealtimeError::OutputTooSmall` and leaves `output` untouched. The `mddosem` adapter can uphold the precondition with a `debug_assert!` and ignore/log the impossible error because `MidiSynth::generate_samples` returns `()`.

The sample rate is fixed for a `RealtimeSynth` instance. A host that changes sample rate must construct a new instance and accept a hard reset. The later `mddosem` threaded integration cannot rely on the per-call `sample_rate` parameter for this, because `ThreadedSynth` captures the rate at thread spawn.

### 5. Reset and controller semantics

Realtime reset must be more explicit than the offline path because games may send reset SysEx and device switches. Implement a reset matrix:

| Trigger | Voices | Controllers / channel state | Programs | Parser state | Bus / effect tails |
| --- | --- | --- | --- | --- | --- |
| `RealtimeSynth::reset()` | Stop all voices immediately | GM defaults on all channels | Program 0 on melodic channels, drum channel unchanged | Clear running status, partial messages, SysEx state | Clear reverb, chorus, echo, drum room, sympathetic, glue, strip delay/filter state |
| GM System On SysEx | Same as hard reset | Same as hard reset | Same as hard reset | Clear parser state after recognizing command | Same as hard reset |
| Raw MIDI System Reset `0xFF` | Same as hard reset | Same as hard reset | Same as hard reset | Same as hard reset | Same as hard reset |
| CC 120 All Sound Off | Choke active voices on that channel | Leave controllers as-is | Leave program as-is | No parser reset | Leave global tails to decay |
| CC 123 All Notes Off | Release active held voices on that channel; pedal-held voices follow current pedal semantics | Leave controllers as-is | Leave program as-is | No parser reset | Leave global tails to decay |
| CC 121 Reset All Controllers | Release voices held only by pedal state if the pedal resets off | Reset bend, RPN, data entry, sustain, sostenuto, portamento, soft, aftertouch, CC1, expression, and filter/wah targets to GM/channel defaults; re-derive program-owned drive and send defaults from the current program | Leave program as-is | No parser reset | Leave global tails to decay |

The CC120/CC123 rows match what `mddosem::MidiFanout::switch_to` already sends to old synths during device switches.

### 6. mddosem fit

The downstream adapter should live in `mddosem`, not in `hollowsynth`. A direct-mode adapter has this shape:

```rust
struct HollowsynthMidi {
    synth: hollowsynth::live::RealtimeSynth,
    sample_rate: u32,
}

impl MidiWriter for HollowsynthMidi {
    fn write_byte(&mut self, data: u8) {
        self.synth.write_byte(data);
    }
}

impl MidiSynth for HollowsynthMidi {
    fn generate_samples(&mut self, count: usize, sample_rate: u32, output: &mut [f32]) {
        if sample_rate != self.sample_rate {
            self.sample_rate = sample_rate;
            self.synth = hollowsynth::live::RealtimeSynth::new(options_for(sample_rate));
        }
        debug_assert!(output.len() >= count * 2);
        let _ = self.synth.render_add(count, output);
    }

    fn name(&self) -> &'static str { "hollowsynth" }
    fn active_voice_count(&self) -> usize { self.synth.active_voice_count() }
    fn as_any(&self) -> &dyn std::any::Any { self }
    fn as_any_mut(&mut self) -> &mut dyn std::any::Any { self }
}
```

Recommended `mddosem` integration:

- Add `SynthId::Hollowsynth`, CLI/settings string `hollowsynth`, and label/name `hollowsynth`.
- Do not assume the current `ThreadedSynth` is low-latency enough. It can queue up to the existing audio ring depth ahead of newly-arrived MIDI.
- First prove a direct adapter and a threaded adapter against the same audio smoke tests. Default selection should be measurement-gated:
  - Use `Direct` if hollowsynth CPU stays comfortably inside the emulator's 1 ms mix budget.
  - Use `Threaded` only after `mddosem` has a low-latency policy for this synth, such as a much smaller ring, smaller generation chunks, or stale-audio discard on activation/MIDI bursts.
- Require an integration latency measurement from MIDI Note On byte arrival to first non-zero audio. Target: under 25 ms in the default path.
- Add no ROM or asset requirement. `hollowsynth` embeds its samples.
- If threaded diagnostics matter, extend `ThreadedSynth` to publish active voice count or document that threaded synths report zero today.
- Recreate the synth/thread if `mddosem` changes sample rate after startup.
- Keep MT-32 as the default unless Arthur deliberately changes emulator defaults later.

### 7. Tests and acceptance criteria

Acceptance criteria for the `hollowsynth` repo implementation:

- Existing CLI behavior remains intact: current tests pass, and the engine refactor is guarded by old-vs-new render comparisons captured before implementation.
- The old-vs-new comparison covers `samples=false` and `samples=true`, the synthetic reference song, same-tick Program/CC/Note ordering, and at least one representative real MIDI path used by `render_opus.py`. Expected result is byte-identical output unless the implementation records and justifies a deliberate sonic change before sign-off.
- Adding CC120/CC121/CC123 handling must not change existing offline renders that never author those controllers. If any checked MIDI does use those controllers, compare that path explicitly.
- `RealtimeSynth` accepts raw MIDI bytes and renders additive stereo `f32` audio in caller-provided buffers.
- `RealtimeSynth` is `Send`; a compile-time assertion covers this.
- `render_add` returns `RealtimeError::OutputTooSmall` without modifying output when the buffer is too short.
- Rendering the same completed byte stream with the same event/render boundaries in one chunk and in several uneven chunks produces near-identical output.
- Chunk-invariance tests include controller-heavy streams: CC1, CC11, CC64, CC66, CC68, CC70, CC71, CC74, pitch bend, aftertouch, and portamento.
- Live Note On timing is tested for the output-ring contract: messages take effect at the next 64-sample internal boundary, with less than 64 frames of synth-side buffering.
- Running status works for Note On/Off, CC, and Program Change.
- Poly Aftertouch consumes both data bytes and does not desynchronise the stream.
- MIDI real-time bytes interleaved in a channel message do not corrupt running status.
- System Common messages consume their documented data bytes and clear running status.
- Long or unterminated SysEx uses bounded parser state and recovers at `F7` or reset.
- GM System On SysEx resets channel state and stops active notes.
- Raw MIDI System Reset `0xFF` is tested separately from ignored real-time bytes.
- CC 120, CC 121, and CC 123 are tested separately against the reset matrix.
- Hard reset clears parser running status/partial state and bus/effect tails.
- `render_add` adds to non-zero output instead of clearing it.
- `active_voice_count` reports active voices after Note On and drops after release/tail.
- `prewarm_samples` forces embedded samples to parse before the first render call.
- Sample-rate mismatch behavior is explicit and tested in the adapter or realtime API.
- Realtime output gain is calibrated against both sparse and dense fixtures. Sparse output must remain audible in the emulator mix, and dense output must avoid hard clipping or excessive limiter distortion.
- `cargo fmt --check`, `cargo clippy --all-targets`, and `cargo test` pass for `fable5/hollowsynth`.

Acceptance criteria for later `mddosem` integration:

- `hollowsynth` can be selected with `--midi-default hollowsynth`.
- No asset-gate failure occurs when selecting `hollowsynth`.
- MPU/WinMM bytes forwarded through `MidiFanout` produce audible stereo output through the selected direct or low-latency threaded path.
- Device switching sends All Notes Off/All Sound Off to the old synth and does not leave stuck notes.
- Default-path MIDI-to-audio latency is measured under load and stays below 25 ms, or the default path is changed.
- If `ThreadedSynth` is used, either active voice count is published through the threaded wrapper or diagnostics explicitly do not rely on it.

## Decision Log

- Keep `hollowsynth` standalone. The library exposes a generic live API; `mddosem` owns the trait adapter.
- Use a raw MIDI byte parser inside `hollowsynth`, but keep it crate-private. That keeps the integration thin and preserves running-status behavior without leaking offline parser types.
- Reuse the existing engine by extracting persistent state instead of building a parallel realtime engine.
- Keep the 64-sample internal quantum as the live rendering quantum and serve arbitrary host callback sizes through a small output ring. This preserves existing smoothing math and gives a clear, bounded latency cost.
- Use fixed live echo delay instead of MIDI clock tempo-following in V1.
- Use fixed realtime gain plus a soft limiter/saturating guard instead of offline peak normalization. Do not add AGC in V1 unless sparse/dense fixture calibration proves fixed gain unusable; AGC pumping would be a separate design decision.
- Do not choose direct vs threaded `mddosem` integration on taste. Make it a measured CPU/latency decision; current threaded infrastructure needs work before it can be assumed low-latency.
- Land implementation after the v0.9 instrument branch is integrated, or rebase carefully before editing `engine.rs`, because that branch also touches engine/instrument behavior.

## Residual Risks

- The `engine.rs` refactor is the main blast radius. It can accidentally change offline output even if the public feature is realtime-only.
- The v0.9 branch and instrument req work may conflict with the engine extraction. Implementation should start from current trunk after that work lands, or rebase this design's branch before code.
- Live gain calibration is empirical. A too-hot default clips; a too-quiet default makes the synth unusable in mixed emulator audio.
- GM reset SysEx handling is small but important. Ignoring it would cause stale channel state across many game tracks.
- Lazy sample parsing can cause a first-note hitch unless `prewarm_samples` is called by the adapter.
- The V1 timing model is render-boundary timed, not sample-accurate. This is acceptable for current `mddosem` plumbing but should be revisited if precise MIDI timestamps are added later.
- Adding `Send` to voices should be straightforward if voices only own numeric DSP state, but the implementation must compile-prove it.
- Low-latency threaded integration may require `mddosem` changes outside this repo.

## Adversarial Review Findings

Three reviewers critiqued the draft and then ran a refutation pass against each other's findings. No material finding was refuted with verified evidence. The survived findings were folded into this revision:

- Public API boundary: keep `MidiByteParser`, `LiveCommand`, and `EvKind` crate-private; expose only `RealtimeSynth` and simple public options/errors.
- Reset routing: represent GM System On and raw System Reset as typed live commands instead of trying to encode them as `EvKind`.
- Buffer contract: `render_add` returns a concrete `RealtimeError` for undersized output.
- Parser reset: hard reset also clears running status, partial messages, and SysEx state.
- Send bound: `RealtimeSynth` must satisfy `Send` before it can be moved into `mddosem::ThreadedSynth`.
- Threaded latency: current `mddosem::ThreadedSynth` is not automatically a low-latency path; default integration must be measured or the thread policy changed.
- Chunking: controller-heavy render splits need explicit invariance tests, not just a simple note stream.
- Parser edge cases: System Common, malformed data, long SysEx, F7 recovery, real-time-inside-SysEx, and raw `0xFF` policy are now in scope.
- Offline regression: the engine refactor needs old-vs-new render comparison broader than the current tolerant golden fixture.
- Reset matrix: CC120, CC121, CC123, GM System On, public reset, raw System Reset, and effect-tail behavior are explicitly defined.
- Diagnostics: threaded `active_voice_count` does not surface through current `mddosem`; integration must either publish it or avoid relying on it.

## External Review Findings

Claude Opus ran one read-only fresh-eyes review after the adversarial findings were folded. It reported no Critical findings. Triage:

- Accepted High H1: chunk-invariance needed a mechanism. The design now chooses an internal fixed-64 quantum plus a small output ring, and relaxes event timing to the next internal quantum instead of "before sample 0".
- Accepted Medium M1: CC121 must re-derive program-owned drive and send defaults from the current program instead of zeroing them while leaving the program unchanged. The offline gate now also covers the new CC120/121/123 handling.
- Accepted Medium M2: the live parser now specifies channel-message data lengths by high nibble, including ignored Poly Aftertouch, so discarded channel messages cannot desynchronise running status.
- Partly accepted Medium M3: the realtime output stage still avoids AGC in V1 for simplicity, but gain calibration now includes sparse and dense fixtures plus a limiter-distortion acceptance check. If fixed gain cannot satisfy that, AGC becomes a separate design discussion rather than an implicit implementation detail.
