# MM-REQ-KILN-00017 — Bagpipe and Shanai Reed Voices

Status: SIGNED-OFF

## Intent

Render GM 109 bagpipe and GM 111 shanai as reed-family instruments instead of the steel-guitar catch-all.

## Scope

- Add GM 109 and GM 111 to the existing ferrosintesis reed family.
- Give shanai a narrow, bright double-reed preset.
- Give bagpipe a reed chanter plus one continuous channel drone.
- Keep the fix inside the existing voice, engine-routing, docs, version, and req-ledger surfaces.
- Out of scope: new sample layers, migration/back-compat ceremony, non-GM retuning systems, and changes to excluded `MM-REQ-KILN-00008`.

## Current Findings

- `crates/ferrosintesis/src/voices.rs` already has a parametric `Reed` voice for GM 64-71.
- `make()` routes only 64-71 to `reed()` today; 109 and 111 fall through to `STEEL`.
- `engine.rs` controller routing treats 64-71 as vibrato-family reeds and has no 109/111 reed effect profile.
- MIDI scan result: 58 committed `albums/` and `demos/` MIDI files were scanned. No album MIDI uses program 109 or 111. The synth feature showcase demo uses both.
- `origin/main` moved during design review and now commits `listening/OpenAI Codex/Synth Feature Showcase/05 - Atlas of Unbuilt Machines.opus`. Because that demo uses 109/111, the demo listening asset is in scope for validation and likely refresh.

## Approach

- Keep `ReedPreset` as the chanter/double-reed preset table. Existing presets keep their audio path unchanged.
- Add a separate `BagpipeDrone` voice in `voices.rs`, built from two phase-continuous `ReedPulse` oscillators at tonic and fifth with conservative gain and lowpass shaping.
- Manage the bagpipe drone in `EngineCore`: for program 109, maintain at most one synthetic drone voice per channel. Low bagpipe notes act as drone controls; higher notes spawn normal reed chanters over the existing channel drone. The drone releases when no authored low drone note or GM109 chanter remains active.
- Add `BAGPIPE` and `SHANAI` presets:
  - Bagpipe: bright nasal chanter, stable vibrato, persistent root/fifth drone.
  - Shanai: narrow high-energy double-reed pulse, strong nasal formants, light breath/chiff.
- Route `109 | 111` through `reed()` for chanter/double-reed notes and add them to `vibrato_family()`/`fx_profile()` as reed-family controller targets.
- Update the reed/engine fixtures and add the required regression test `bagpipe_shanai_route_to_reed_engine_with_drone_or_double_reed`.
- Update `crates/ferrosintesis/README.md`, bump crate versions from `0.10.6` to `0.10.7`, and mark the requirement implemented.

## Decision Log

- Reuse the existing reed engine. A separate bagpipe/shanai family would duplicate pitch, breath, formant, and lifecycle code.
- Use one engine-managed bagpipe drone per GM109 channel instead of a preset-level drone inside every chanter voice. This prevents overlapping authored drone and melody notes from multiplying drones.
- Low GM109 notes control the channel drone; higher GM109 notes are chanters. Fixed Highland-pipe tuning is out of scope for GM rendering.
- Because trunk now commits synth showcase listening audio, refresh that demo output if the new GM109/111 render changes it.

## Adversarial Review

Reviewer A, synthesis/lifecycle:

- Finding: a drone tied to `base_f` on every retune would fail the "persistent drone" expectation during CC68 legato because the drone would move with the chanter.
- Refutation attempt by Reviewer B: current GM notes may be independent rather than legato, so per-note drone movement may be acceptable. Refuted: the existing reed voice explicitly supports `legato_to()`, and bagpipe should keep the drone stable in that path.
- Survives: yes, but the external review refined the fix. The implementation should not put a drone inside every `Reed`; it should manage one drone per GM109 channel.

Reviewer B, testability/regression:

- Finding: tests must observe the drone in a late steady window, not just routing to `"reed"`, or the implementation could pass while making bagpipe a plain shanai-like reed.
- Refutation attempt by Reviewer C: preset presence could be enough if code review confirms it. Refuted: the requirement's `Satisfied-by` test name explicitly says "with drone or double reed"; the oracle should measure both.
- Survives: yes. The focused test should assert a low drone band for GM 109 and nasal double-reed formants for GM 111.

Reviewer C, scope/backward-compat:

- Finding: a fixed Highland-pipe tonic would be more authentic than transposing the drone with each note.
- Refutation attempt by Reviewer A: GM rendering should transpose predictably with MIDI note data, and fixed tuning would be hard to test without a key-signature model. Refuted.
- Survives: no. Keep a transposed initial drone tonic per spawned note, with legato persistence as above.

Reviewer C, validation:

- Finding: the byte-identity claim should distinguish albums from demos because the feature-showcase MIDI uses programs 109 and 111.
- Refutation attempt by Reviewer B: demos are not album listening assets, so the claim can stay broad. Refuted: the scan found committed demo usage, and the HLD needs to state the exact blast radius.
- Survives: yes. Validate no album MIDI uses 109/111 and keep `albums`, `listening`, and `demos` diffs empty unless deliberately refreshing demo outputs.

## External Review

Claude Opus plan review: `C:\Users\marti\.claude\plans\review-this-design-for-dazzling-muffin.md`.

Accepted findings:

- Per-note transposed drones would not be persistent for ordinary GM input and would multiply under polyphony. Design changed to one engine-managed drone per GM109 channel.
- The synth feature showcase demo uses 109/111 and now has committed listening audio on trunk. Validation now includes re-rendering/verifying that demo and refreshing output if changed.
- The tests need more than routing: add one-drone-per-channel, drone level, DC/finite, and shanai alias/timbre checks.
- Add a baseline-vs-new album render `cmp` rather than relying only on the static MIDI scan.

Rejected or scoped findings:

- Make the drone opt-in only at the composition layer: rejected. The accepted requirement explicitly asks for GM109 bagpipe to render with a persistent drone, so the synth must supply one for plain GM input.
- Fixed Highland-pipe tonic: rejected as out of scope for a GM renderer without key-signature tuning semantics.
