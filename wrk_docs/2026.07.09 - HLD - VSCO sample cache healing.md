# VSCO Sample Cache Healing

Status: Accepted

Fable 5 consult, 2026-07-09. Scope: `crates/ferrosintesis/samples/prepare.py`
after a timed-out VSCO download poisoned the local cache with a partial WAV.

## Diagnosis

The failure is partial-cache poisoning, not a RIFF parser bug. `urlretrieve`
writes directly to the final cache path, so a killed or short transfer can leave
a file whose RIFF header is complete but whose data chunk is truncated. The
script then treats `exists(path)` as validity and reuses the broken file.

`read_wav` also needs a strict payload-length check. Without one, 16-bit
truncation crashes opaquely during `struct.unpack`, while 24-bit truncation can
silently read short slices as tiny/zero values.

## Decision

- Download to `<path>.part`.
- Move into place with `os.replace()` only after `urlretrieve()` returns.
- Validate `len(raw) == frames * channels * sample_width` in `read_wav`.
- If a cached file fails validation, delete just that file, refetch once, and
  retry. A second failure is fatal.
- Do not derive frame count from the truncated payload length.

## Oracle

Add a stdlib-only `test_prepare.py` that:

- monkeypatches `urlretrieve` to write a partial `.part` and raise, proving no
  final cache file is created;
- proves a successful retry lands the final file and leaves no `.part`;
- writes valid 16-bit and 24-bit mono/stereo WAVs, truncates each, and asserts
  `read_wav` raises `ValueError`;
- confirms intact 16-bit and 24-bit mono/stereo files still read.
