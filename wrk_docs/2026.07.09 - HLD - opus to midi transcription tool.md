## 1. Problem & context

Transcribe **arbitrary external audio** (Arthur's own music: OPUS/WAV/MP3 mixes, or
partial stems he already has — bass / drums / vocals / "everything else") into
**multi-track MIDI**: separate the sources, identify instruments where possible, and
reconstruct note events.

A 6-dimension research sweep (12 agents, adversarially verified against primary
sources) is the ground truth:

- **Solved:** monophonic pitch (melody/bass) and solo-piano transcription (CREPE
  ~99.7% raw-pitch on clean audio; ByteDance piano onset-F1 ~0.967). *These numbers
  show **why per-stem transcription is tractable** — they are context, not the tool's
  expected accuracy: v1 ships Basic Pitch (mono note-F well below CREPE), and its
  guitar/piano inputs are 2–3 dB separations, not clean solo audio.*
- **Unsolved:** multi-instrument transcription with instrument-ID. 2025 AMT-Challenge
  SOTA ~**0.60 F1**; precision **collapses 0.91→0.46** from 1 to 3 simultaneous
  instruments.
- **Binding constraint:** per-instrument separation of the harmonic "other" bucket caps
  at **~2–3 dB SDR** (guitar/piano) — often unusable; artifacts corrupt downstream
  transcription.
- **Viable path:** SEPARATE, then TRANSCRIBE PER STEM. All tools free/permissive.
- **Not viable:** a from-scratch or zero-dep-Rust transcriber.

**Implication:** we do not build a transcriber; we build a thin **orchestrator** around
existing tools, mapping onto an existing repo pattern (§4).

## 2. Goals & non-goals

### Goals
1. One command turns an audio **mix** *or* a set of **pre-made stems** into MIDI.
2. Output **per-stem `.mid`** files plus **one combined multi-track GM** file.
3. Route each stem to a fitting transcriber; **attempt the instrument split** of the
   harmonic content, with an honest **single-track "sketch"** fallback.
4. Keep repo identity: committed tool is **stdlib-only Python**; ML tooling is an
   **external, isolated prerequisite**, never vendored.
5. **Testable** primarily via a **no-ML** assemble oracle (§7).

### Non-goals (these collapse the complexity)
- **Faithful** per-instrument reconstruction of dense mixes (best-effort only).
- **Notation / MusicXML.** MIDI note events only.
- **Tempo/beat detection & quantization.** Emit time-accurate, *un-quantized* MIDI at a
  fixed nominal tempo; quantize in the DAW.
- **Audio chunking / long-file windowing.** v1 processes whole files; a max duration is
  declared and over-length inputs get a clear "split it" error (§4.4). No overlap-stitch
  logic.
- **Real-time / streaming**, **GUI**, **any in-repo ML or Rust transcriber**.
- **Guaranteeing real-world accuracy** — bounded by the upstream models.

## 3. Success / acceptance criteria

A1. Given a decodable input, the tool writes per-stem `.mid` files **and** one combined
    multi-track GM `.mid`; exits non-zero naming any missing external tool **and its
    install command**.

**A2 (the ONLY hard build gate) — no-ML assemble oracle.** Fed hand-built synthetic
    per-stem note inputs, the assembler produces a combined MIDI recovering **100%** of
    input notes with **exact** pitch, channel, program, track-name and tick placement.
    Deterministic; runs with **zero external tools**. This is the sole pass/fail gate.

A3. **Input auto-detection:** a *file* is a mix (separated first); a *directory* of
    conventionally-named stems is transcribed directly. No flag. *(Lone isolated stem →
    place it in a stems directory; §9 Q-D.)*

A4. Committed orchestrator imports **only** stdlib (enforced by an import-scan test).
    External tools invoked via `subprocess`, resolved by path (§4.3), never imported.

**A2-diag / A5 (diagnostics, NOT build gates).** The clean-stem round-trip and the
    full-mix smoke are opt-in checks run via an explicit `--diagnose` command; they
    depend on machine/tool-versions and never gate the build. The §7 tripwire flags a
    *broken oracle*, it does not gate.

## 4. Approach

### 4.1 Shape — mirror `render_opus.py` (orchestration only)

`transcribe.py` (repo root) is the inverse of `render_opus.py` in shape:

```
audio in ─▶ [normalize] ─▶ [separate] ─▶ [transcribe per stem] ─▶ [assemble] ─▶ MIDI out
            ffmpeg         Demucs 6-stem  Basic Pitch → CSV        stdlib merge
                           (skip if       drum ADT → onsets/MIDI
                            stems given)
```

`render_opus.py` is the precedent for **orchestration only**; the MIDI assembly half is
new code (§4.3).

### 4.2 Pipeline stages

**Stage 0 — Normalize (ffmpeg).** Decode any input (incl. `.opus`) → WAV 44.1 kHz
stereo, so downstream tools get a format they accept.

**Stage 1 — Separate (Demucs `htdemucs_6s`).** *Mix* input → 6 stems (vocals/drums/bass/
guitar/piano/other) at the fixed Demucs layout `separated/htdemucs_6s/<track>/<stem>.wav`.
*Stems* input → skip; match provided files by **alias→canonical role** (e.g.
`vox|vocal|lead → vocals`); **error on a duplicate or ambiguous role**. Trade-offs of
always-6-stem in D4.

**Stage 2 — Transcribe per stem (route by role):**
- **vocals, bass, guitar, piano, other** (pitched) → **Basic Pitch**, consuming its
  **note-event CSV** (`start_s, end_s, pitch, velocity, pitch_bend`; absolute seconds,
  read with stdlib `csv`). CSV avoids parsing Basic Pitch's MIDI and stripping its
  pitch-bends. The 6-stem `other` residual → a **single unlabelled sketch track**.
- **drums** → a **drum-ADT** → onsets/MIDI mapped to a GM ch-10 core kit. Tool choice is
  genuinely unsettled (§9 Q-A): *ADTOF-pytorch* is torch-native (shares Demucs's env)
  but ships as an unreleased clone with no clear licence and only **5 fixed GM drum
  classes** (fixed velocity/duration); *omnizart drum* is MIT/packaged but drags in the
  fragile `madmom`+legacy-TF stack. Decide via an install spike at implementation.
- **Empty stems:** a stem that transcribes to **zero notes** (silent/unpitched) is
  recorded as an omitted/empty track — detected from the note count, needing **no DSP**
  (keeps the orchestrator stdlib-pure).

**Stage 3 — Assemble (stdlib).** See §4.3.

### 4.3 Prerequisites, config, and the assemble stage

**Prerequisites are isolated.** Demucs, Basic Pitch and the drum ADT have incompatible
dependency graphs (torch vs TF/tflite/onnx vs madmom) — they cannot share one
interpreter. Each lives in **its own venv**. The orchestrator resolves each tool's
executable from a single **gitignored `transcribe.local.json`** (per-tool path, plus
device and any per-tool extra args / cache dir), falling back to PATH; a committed
`transcribe.local.json.example` documents it. This is **one config file, not env vars or
per-invocation flags** — consistent with the brief, and it absorbs the real-world knobs
(GPU/CPU, Demucs segment size, cache location) without flag-creep. Prefer the
torch-native drum tool so only **two** environments exist. Missing-tool errors name the
tool + its install command.

**Stage 3 is net-new stdlib code (~250–350 lines).** Most inputs arrive as **absolute
seconds** already (Basic Pitch CSV; drum onsets), so the merge is largely: collect events
→ assign role → convert seconds→ticks at fixed 120 BPM → write one type-1 MIDI via the
**`Score`-based writer lifted from fable5 `engine.py`**. A **robust MIDI reader** is
needed only where a tool emits MIDI-only (a drum tool) and to **read back our own output
in the oracle**; because third-party MIDI is untrusted it must implement full note
semantics:

- **FIFO active-note pairing** per `(track, channel, pitch)`; treat **`note_on`
  velocity 0 as note-off**; **clamp same-pitch overlaps / re-strikes**; drop **unmatched
  note-offs** safely.
- **Default tempo 500000 µs/qn (120 BPM)** when a track has no tempo event; **reject
  SMPTE division** (negative division word) with a clear error — out of scope for v1.
- Convert each source's events to absolute seconds using **its own tempo+division**;
  **never copy source ticks**.

**Fixed role → channel → program → track-name table (pinned; asserted by the oracle):**

| Role | Channel (0-based) | GM program | Track name |
|------|------|------|------|
| vocals | 0 | 54 (Voice Oohs) | Vocals |
| bass | 1 | 33 (Electric Bass, finger) | Bass |
| guitar | 2 | 27 (Electric Guitar, clean) | Guitar |
| piano | 3 | 0 (Acoustic Grand) | Piano |
| other | 4 | 0 (Acoustic Grand) | Other (sketch) |
| drums | 9 | — (GM percussion) | Drums |

The tool **forces** these program/channel/track-name events; the transcribers' own
programs never define the final arrangement, and distinct channels stop piano/other
(both program 0) colliding.

### 4.4 Long files

v1 processes whole files (no chunking — non-goal §2). A **max duration** is declared;
over-length inputs fail fast with a "split the file and transcribe the parts" message. If
a tool fails on length/memory, its error is surfaced verbatim, not swallowed.

## 6. Decision log

- **D1 — Assemble, don't build.** From-scratch is unsolved for the hard case and breaks
  the ethos. *(Research-backed; Arthur endorsed.)*
- **D2 — stdlib orchestrator; ML tools external + isolated** via one local config (§4.3).
- **D3 — Basic Pitch for all pitched stems, via CSV (drop CREPE).** CSV avoids
  third-party-MIDI parsing + pitch-bend stripping; Basic Pitch already segments notes.
  *Future upgrade:* CREPE for mono vocals/bass if quality demands it.
- **D4 — Always 6-stem, no flag. Honest rationale:** 6-stem pulls guitar/piano out of
  `other` using the same 2–3 dB separation §1 calls corrupting — we **accept degraded
  harmonic transcription to attempt the split**; the residual `other` is a **depleted**
  bucket, and `htdemucs_6s` is Demucs's **experimental** model (its **piano** stem
  especially weak). Guitar/piano tracks are **labelled but low-confidence**. *§9 Q-C:
  default to 4-stem instead?*
- **D5 — Fixed nominal tempo, un-quantized.** No beat tracking (another error source).
- **D6 — Round-trip via ferrosintesis is a diagnostic, not the gate.** The sole gate is
  the no-ML oracle. Synthetic audio flatters models *and* ferrosintesis's modelled timbre
  is alien to Basic Pitch's training — either way it can't be a correctness gate.
- **D7 — Input auto-detect (file=mix, dir=stems).** No flag.
- **D8 — No version bump.** Not part of the ferrosintesis crate.

## 7. Testability

1. **Assemble oracle — no ML, exact, the GATE.** Hand-built synthetic per-stem note
   inputs → assembler → assert **exact** track/channel/program/track-name/tick placement
   and full note recovery. Deterministic, **zero external tools**. Dedicated fixtures for
   each nasty MIDI case in §4.3 (same-pitch overlap, `note_on` vel-0, unmatched note-off,
   missing tempo, SMPTE rejection) and an assertion of the pinned role→channel→program
   table.
2. **Clean-stem round-trip — ML, diagnostic (`--diagnose`).** `ferrosintesis --solo`
   renders a fixture MIDI to clean stems; transcribe; check the tools produced *something
   sane*. **Not a gate.** **Tripwire:** clean-stem mono recovery implausibly low (< ~50%)
   ⇒ the oracle/setup is broken, not a low bar to accept.
3. **Full-mix smoke — full pipeline incl. Demucs, diagnostic.** Runs everything on a
   rendered mix; asserts completion + file set with *loose* recovery. Proves wiring.

Plus an **import-purity** test (orchestrator imports only stdlib). Nothing in a fixture is
left unchecked (the chord pad gets a loose pitch-set recovery assertion).

## 8. Residual risks

- **R1 — Install burden + isolation.** Three ML tools, incompatible deps, per-tool venvs.
  Mitigate: prefer torch-native ADTOF-pytorch; clear install docs + actionable errors.
  **Lean-fallback (corrected):** if trimming, cut the *harmonic* guitar/piano/other layer
  (the 2–3 dB part) and **keep vocals/bass/drums** — drums are high-value; hand-programming
  them is the tedium worth automating.
- **R2 — "Other" split quality is low** (piano especially). Labelled-but-low-confidence;
  sketch track is the honest fallback. Not a defect.
- **R3 — Drum tool has no clean option** (ADTOF-pytorch unpackaged/unclear-licence/5-class;
  omnizart madmom-hell). Resolved by an install spike; drums are cuttable if neither is
  acceptable (R1).
- **R4 — Real-world quality bounded by upstream models.** Output is a **rough draft for a
  DAW**, not a faithful score. Manage expectations.
- **R5 — Format/codec + long-file edges.** ffmpeg normalize (Stage 0); max-duration guard
  (§4.4).
- **R6 — Strategic: off-mission maintenance surface.** Heavy-external-dep ML tooling bolted
  onto a zero-dep generative-composition repo. Quarantined, but a new surface that doesn't
  advance the album mission. Flagged for eyes-open acceptance.
