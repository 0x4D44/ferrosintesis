# HLD: ferrosintesis embedded sample crates

**Status: SIGNED-OFF — Arthur, 2026-07-10**

## Decision

Keep every attack sample embedded in the final binary, but distribute the 178 WAV
files through two small crates.io packages rather than inside the
`ferrosintesis` package itself. Cargo becomes the only downloader and cache;
there is no `build.rs`, runtime download, GitHub fetch, or new third-party code
dependency.

The packages are:

- `ferrosintesis-samples-core` — piano, violin, and flute: 71 WAVs,
  9,555,776 bytes raw, about 6.99 MiB under a gzip proxy;
- `ferrosintesis-samples-orchestral` — brass, reeds, nylon guitar, and drums:
  107 WAVs, 6,601,544 bytes raw, about 5.64 MiB under a gzip proxy;
- `ferrosintesis` — synth code and the sample-selection/parser logic, with no
  WAV payload of its own.

Both proposed sample-package names returned 404 from the official crates.io API
on 2026-07-10. Availability remains first-come-first-served until publication.

## Why this shape

The current `ferrosintesis 0.12.0` package is about 13.2 MB compressed because
all 178 WAVs sit below its package root. crates.io limits each `.crate` archive
to 10 MB. Splitting on the existing bank boundary leaves comfortable headroom
without changing or recompressing audio.

Cargo registry packages already provide the desired compile-time retrieval:
Cargo downloads each exact package version into its global cache, the sample
packages expose their WAVs as `&'static [u8]` through `include_bytes!`, and the
linker embeds the referenced data in the final executable. This preserves the
present single-binary runtime and avoids custom cache, TLS, archive, checksum,
offline, and docs.rs machinery.

## Target layout

```text
crates/
  ferrosintesis/
    Cargo.toml
    LICENSE-APACHE
    LICENSE-MIT
    src/sampler.rs              # parsing, root maps, bank selection, LA voices
  ferrosintesis-cli/
  ferrosintesis-samples-core/
    Cargo.toml
    README.md
    LICENSE-CC0
    src/lib.rs                  # static file inventory + lookup
    samples/*.wav               # piano / violin / flute
  ferrosintesis-samples-orchestral/
    Cargo.toml
    README.md
    LICENSE-CC0
    src/lib.rs                  # static file inventory + lookup
    samples/*.wav               # brass / reeds / nylon / drums
tools/
  ferrosintesis-samples/
    prepare.py
    test_prepare.py
    README.md                   # full provenance + regeneration instructions
```

The WAVs move; they are not copied. The two package READMEs carry the relevant
CC0 provenance so each published archive is self-explanatory. The generator and
its tests remain repo tooling and are not shipped in either sample package.

## Package and feature contract

Each sample package starts at independent content version `0.1.0`, uses
`license = "CC0-1.0"`, and carries its own crates.io description, repository,
README, and legal text. It exposes only a small lookup over its compiled file
table:

```rust
pub const FILE_COUNT: usize = ...;
pub fn get(name: &str) -> Option<&'static [u8]>;
```

`ferrosintesis` keeps the root-frequency tables, dynamic-layer selection,
`OnceLock<Vec<Zone>>` parsing, and all `LaVoice` / `SampleOverlay` behaviour.
Only the byte source changes from a relative local `include_bytes!` to the two
lookup functions. The `'static` ownership model and audio render loop do not
change.

The main manifest gains:

```toml
[features]
default = ["embedded-samples"]
embedded-samples = [
    "dep:ferrosintesis-samples-core",
    "dep:ferrosintesis-samples-orchestral",
]

[dependencies]
ferrosintesis-samples-core = {
    path = "../ferrosintesis-samples-core",
    version = "=0.1.0",
    optional = true,
}
ferrosintesis-samples-orchestral = {
    path = "../ferrosintesis-samples-orchestral",
    version = "=0.1.0",
    optional = true,
}
```

Exact pins make the embedded bytes part of the render identity. A sample-content
change publishes a new sample-package version and a corresponding patch of
`ferrosintesis`; code-only releases may continue to pin the existing sample
versions.

Default features preserve today's sound and CLI behaviour. Consumers choosing
`default-features = false` get the fully modeled synth and do not download or
compile either sample package. The existing runtime `Options.samples` /
`RealtimeOptions.samples` switches remain: they can disable compiled-in samples
but cannot add samples to a build made without the feature. Public docs state
that distinction, and a small `embedded_samples_available()` query lets a host
report it without guessing.

## Versions and publication sequence

The implementation changes shipped package structure but not synthesis, so it
bumps `ferrosintesis` and `ferrosintesis-cli` once from `0.12.0` to `0.12.1`.
The sample packages start at `0.1.0`.

Publication is a separate, explicitly authorised release action:

1. Publish `ferrosintesis-samples-core 0.1.0`.
2. Publish `ferrosintesis-samples-orchestral 0.1.0`.
3. Wait until both versions resolve from the crates.io index.
4. Run `cargo publish -p ferrosintesis --dry-run` against the registry packages.
5. Publish `ferrosintesis 0.12.1` only after that dry run is green.

Before steps 1–2, a verifying `cargo package -p ferrosintesis` cannot resolve
the packaged manifest's new registry dependencies. The implementation gate uses
workspace tests plus `cargo package --no-verify` for the main archive, then the
release gate supplies the missing registry-resolution proof. This staging is
explicit; `--no-verify` is not treated as final publication evidence.

`ferrosintesis-cli` remains `publish = false` in this task.

## Non-goals

- No sample editing, recompression, resampling, renaming, or regenerated audio.
- No voice, controller, mix, CLI-option, or MIDI-parser change.
- No network-capable build script or runtime sample loader.
- No CLI publication in this task.
- No promise that the two currently free crates.io names remain available before
  the authorised publication step.

## Principal risks

- **Name race:** reserve/publish the two sample packages before publishing the
  main crate; do not weaken the names or silently substitute lookalikes.
- **Staged verification:** the main packaged crate cannot receive its final
  registry-resolution proof until the sample packages exist. Keep that release
  gate explicit.
- **Content drift:** exact version pins, inventory tests, and full-corpus byte
  comparison prevent a packaging refactor from becoming a timbre change.
- **Feature drift:** default features must remain sample-on; modeled-only must be
  deliberately requested and independently tested.
- **Licensing:** each asset package must carry CC0 provenance and legal text in
  its own archive, not only in the repository.

## Implementation amendment — concurrent-main reconciliation

This factual amendment supersedes the HLD's package counts, code version, and
publication version. It does not change Arthur's signed architecture: two ordinary
asset crates remain exact-pinned optional dependencies behind the default
`embedded-samples` feature, with compile-time retrieval and no downloader.

While implementation was in flight, `origin/main` added 24 CC0 cello/violin
ensemble attacks for GM 48–49 and advanced the synth version. The implementation
absorbs that landed work as follows:

- `ferrosintesis-samples-core 0.1.0`: 71 WAVs, unchanged;
- `ferrosintesis-samples-orchestral 0.1.0`: 131 WAVs, including the 24 ensemble
  attacks;
- 202 WAVs and 17,487,688 raw bytes total, with every `origin/main` payload moved
  byte-identically and every filename present exactly once in the package lookups
  and sampler routes;
- package archives of 7,102,046 bytes (core) and 7,005,718 bytes (orchestral), both
  below the 10 MB limit and both carrying their CC0 text;
- `ferrosintesis 0.13.2` and the unpublished CLI at `0.13.2`, preserving this
  task's single version bump over the final `0.13.1` main baseline.

The full 88-track catalogue was byte-identical across the final sample-bearing
`origin/main` baseline and the 202-WAV split. After a later unrelated cymbal fix
landed, the changed Night Train drum path, Architecture of Air, and the string-heavy
Choir of Circuitry render also remained byte-identical; the full compile/test gate
was rerun on the final rebase.

The code package has an explicit 17-file, 995,783-byte allowlist containing no WAVs.
Cargo cannot construct its registry package before the two exact asset versions
exist, even with `--no-verify`; the original pre-publication main-package acceptance
line is therefore replaced by that allowlist proof plus the mandatory post-asset
verifying dry run.

The authorised publication sequence is consequently:

1. publish and verify `ferrosintesis-samples-core 0.1.0`;
2. publish and verify `ferrosintesis-samples-orchestral 0.1.0`;
3. run a verifying dry run for `ferrosintesis 0.13.2` against those registry
   packages, inspect the no-WAV archive, then publish it;
4. do not publish `ferrosintesis-cli`.
