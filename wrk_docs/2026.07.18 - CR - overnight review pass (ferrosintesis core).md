### Confirmed findings

#### CR-1 — Renderer panics on a MIDI note key ≥ 128 · Severity **Medium** · Confidence **High** → filed `MM-BUG-KILN-00025`
- **Where:** root cause `crates/ferrosintesis/src/midi.rs:243` (also :237, :275); crash
  sites `crates/ferrosintesis/src/engine.rs:1445` and `:1548`.
- **Problem:** the SMF parser reads note-key data bytes raw (`let key = c.u8()?`) with
  no clamp to 0–127, unlike the channel nibble which is masked `& 0x0F` (midi.rs:233,
  with an explicit "never out of range" comment at :60-63). A NoteOn like `90 C8 64`
  parses to `key: 200`, which then indexes two fixed 128-wide arrays —
  `key_on_at: Vec<[u64;128]>` (engine.rs:1175) at :1445 on melodic channels, and
  `drum_rr: [u8;128]` (engine.rs:1168) at :1548 on drum channels — out of bounds →
  panic on the public `offline::render` "plays any GM file" path. Availability-only
  (safe Rust bounds-check panic, no UB/RCE). **Reproduced by execution** (30-byte
  format-0 file → `index out of bounds: the len is 128 but the index is 200`, exit
  101) and re-confirmed by reading the parser + both index sites.
- **Fix:** mask `key & 0x7F` at the three parser read sites — fixes both crash sites
  at once. Add a parse+render regression test with key=200 on a melodic and a drum
  channel. **Effort: small.**

#### CR-2 — No oracle guards the GM42>GM43 brightness ordering · Severity **Medium** · Confidence **High** → folded into `MM-BUG-KILN-00026`
- **Where:** `crates/ferrosintesis/src/voices.rs:7662-7671` (fix), oracle at `:16272`.
- **Problem:** commit `41d2bc8`'s brightness fix (contrabass was +55% too bright) is
  pure ear-gated constant edits with no automated guard; the brightness oracle asserts
  only that adjacent programs differ (`>=1.05`), never the direction. A revert re-inverts
  the ordering with the suite green. See CR-4 for the compounding wrong-struct issue.
- **Fix:** brightness-ordering oracle (see `MM-BUG-KILN-00026`). **Effort: small.**

#### CR-3 — Stale comment: contrabass output lowpass claimed `None`, code sets 1800 Hz · Severity **Low** · Confidence **High** · (CR-report only)
- **Where:** `crates/ferrosintesis/src/voices.rs:7650-7651` (and field comment `:7621`).
- **Problem:** the comment says the output lowpass "is None for the contrabass", but
  commit `41d2bc8` set the contrabass `out_lp_hz = 1800.0` (the `_ =>` arm at :7671),
  so the constructor (`:7755-7756`) builds `Some(OnePole::lowpass(1800.0, sr))` — the
  contrabass now has the *strongest* output lowpass of the family. Documentation-only,
  zero runtime effect, but these measurement-citing comments are load-bearing for
  future timbre work. Panel corrected Medium → Low (3/3).
- **Fix:** update the comment (both programs carry an `out_lp`: cello 2600, contrabass
  1800) and the `:7621` field comment (no longer cello-specific de-buzz). **Effort:
  trivial.**

#### CR-4 — Brightness fix verified against the wrong struct (MM-BUG-KILN-00004 trap) · Severity **Medium** · Confidence **High** → filed `MM-BUG-KILN-00026`
- **Where:** `crates/ferrosintesis/src/voices.rs:16285` (oracle), `:16250`
  (`render_default_bowed` → `Bowed::new`), `:11161-11162` (`make()` → `BowedString`).
- **Problem:** `make()` ships `BowedString` for GM42/43, but the brightness/body
  oracles render `Bowed::new` (the CC0 alt-bank struct the commit never touched), so no
  oracle measures the shipping voice's brightness. This is the exact wrong-struct trap
  MM-BUG-KILN-00004 fixed for the *vibrato* oracle (migrated to `make()`) — the
  *brightness* oracles were left on `Bowed::new`, and today's brightness commit walked
  into it. Independently confirmed by reading all three sites.
- **Fix:** see `MM-BUG-KILN-00026`. **Effort: medium.**

#### CR-5 — GM43 vibrato-depth bound widened, not recalibrated · Severity **Low** · Confidence **High** · (CR-report only)
- **Where:** `crates/ferrosintesis/src/engine.rs:5295` (`bowedstring_gm43_pitch_bounded`).
- **Problem:** commit `41d2bc8` deepened the vibrato but moved only the oracle's *upper*
  bound (22→42 cents), leaving the floor at 3.0. The pre-change shallow depth measured
  ~10–12 cents — inside `[3, 42]` — so a bass-only re-shallowing regression passes.
  "Recalibrated (not weakened)" is inaccurate for this oracle: the band strictly widened.
  Panel corrected Medium → Low (code correct today).
- **Fix:** raise the floor toward the new ~28–32 cent reference (e.g. `15.0..=42.0`) so a
  reversion fails; keep the 42-cent runaway ceiling. **Effort: trivial.**

#### CR-6 — GM42/43 chorus de-send is unpinned · Severity **Low** · Confidence **High** · (CR-report only)
- **Where:** `crates/ferrosintesis/src/engine.rs:390` (`fx_profile`).
- **Problem:** the `42 | 43 => (0.0, 0.06)` arm sits before the broader `40..=45 | 110 =>
  (0.10, 0.10)` arm; the top-to-bottom ordering is load-bearing and a reorder/edit
  silently refolds the solo cello/contrabass into the fiddle chorus bus, with no test
  failing. The adjacent `gm110_fiddle_routes_to_bowed_...` test already pins
  `fx_profile` values directly, so there is precedent for the guard.
- **Fix:** assert `fx_profile(42,0)==(0.0,0.06)`, `fx_profile(43,0)==(0.0,0.06)`, and
  `fx_profile(42,0)!=fx_profile(40,0)`. **Effort: trivial.**

#### CR-7 — Cello (GM42) deepened vibrato has no cents-depth oracle · Severity **Low** · Confidence **High** · (CR-report only)
- **Where:** `crates/ferrosintesis/src/engine.rs:5282` (test iterates program 43 only).
- **Problem:** the cello depth was raised on par with the bass, but
  `bowedstring_gm43_pitch_bounded` never renders program 42, and the other 42/43 vibrato
  test measures rate/periodicity, not cents-depth. So GM42 has no explicit depth guard.
  (Mitigation, per the refuted finding's empirical test: a *large* GM42 depth revert
  trips the rate oracle — but no oracle asserts a cents floor directly.)
- **Fix:** add program 42 (with a compass-appropriate floor) to
  `bowedstring_gm43_pitch_bounded`'s loop, or a sibling assertion. **Effort: small.**

- **"fx_profile de-chorus also hits the CC0 alt-bank cello/contrabass"**

### Additional low-severity observations (team-lead recon; verified by reading source)

These are marginal and not filed as bugs (conservative); recorded for completeness.

- **midi.rs — non-finite times on a degenerate tempo/division.** A header `division == 0`
  (metric, 0 ticks/quarter) makes `tpq = 0` so `spt` is `inf`; a tempo meta with
  `us == 0` makes `initial_bpm = 60_000_000/0 = inf`. Note events are caught by the
  `seconds.is_finite()` guard (midi.rs:327, returns `TooLong`), but a markers-only file
  can carry `inf` marker times, and `initial_bpm` can be `inf`. Malformed input, no
  panic. Low. *Possible fix: reject `division == 0` alongside the existing SMPTE/format
  guards, and guard `tempos[0].1 == 0`.*
- **wav.rs:17 — `data_len = (interleaved.len()*2) as u32` truncates for renders beyond
  ~6.8 h.** `MAX_SONG_SECONDS` is 24 h, so a long enough render (on a large-RAM box)
  produces a sample count whose byte size exceeds `u32::MAX`, silently writing a wrong
  RIFF/`data` size. Extreme edge (the RIFF format itself caps at 4 GB), so any writer
  hits it; a `debug_assert`/error at the 4 GB boundary would be cleaner. Very low.

### Confirmed findings

#### CR-8 — Numeric CLI args are not range/finiteness-validated · Severity **Low** · Confidence **High** · (CR-report only)
- **Where:** `crates/ferrosintesis-cli/src/main.rs:49-81` (`--wet` / `--delay` /
  `--tail` / `--lufs` / `--tp-ceiling`) and `:43-48` (`--rate`).
- **Problem:** each numeric arg parses with `.and_then(|v| v.parse().ok())` and no
  domain check. Rust's `f32` `FromStr` accepts `"nan"`/`"inf"`, so `--wet nan`,
  `--tail inf`, `--lufs nan`, etc. pass a non-finite value straight into `Options` and
  the render — yielding a silent NaN/garbage or empty WAV rather than an error.
  Negatives/zero are likewise unchecked (`--rate 0` → sample rate 0; `--tail -5` → a
  negative tail into the render's `(seconds + tail) * sr` buffer math). `usage()` is
  reached only on a parse *failure*, never on an out-of-domain value.
- **Impact:** user-error only, offline tool, no crash — but the failure mode is a
  silently wrong output file instead of a clear diagnostic.
- **Fix:** after parsing, validate each domain (e.g. `wet ∈ 0..=1`, `tail`/`delay`
  finite ≥ 0, `rate ≥ 8000`, `lufs`/`tp_ceiling` finite ≤ 0) and `usage()` otherwise.
  **Effort: small.**

- `examples/measure_wav.rs` and `examples/raw_dump.rs` are DEV-ONLY (marked as such);

### Confirmed findings

#### CR-9 — Success tally uses surviving-worker outcomes as the denominator; a panicked worker would under-report yet exit 0 · Severity **Low** · Confidence **High** · (CR-report only; currently unreachable)
- **Where:** `crates/render-catalog/src/main.rs:823` (`flat_map(|h| h.join().unwrap_or_default())`) and `:828-831` (`done: {ok}/{results.len()}` + the exit check).
- **Problem:** the final tally compares `ok` against `results.len()` (outcomes actually
  collected), not `selected.len()` (tracks that should have rendered). A worker thread
  that panicked *outside* `render_one`'s `catch_unwind` has its `join()` return `Err`,
  which `unwrap_or_default()` turns into an empty `Vec` — silently dropping that worker's
  tracks. The tool would then print e.g. `done: 50/50 rendered` and `exit(0)` even though
  more than 50 tracks were selected. **Currently unreachable:** `render_one` is fully
  `catch_unwind`-wrapped and the worker loop only does bounds-guarded indexing
  (`selected.get(i)`, then `totals[..]`/`lyrics[i]` with `i < selected.len()`) plus
  `println!`, so no realistic panic path exists. Defensive only.
- **Fix:** tally against `selected.len()` (e.g. `if ok != selected.len() { exit(1) }`)
  and/or treat a joined-worker `Err` as a hard failure rather than `unwrap_or_default()`,
  so a hypothetical dropped worker surfaces instead of masquerading as success.
  **Effort: trivial.**

### Notes (no new bugs)

- **No security issue:** `ropusenc` is invoked via `Command::new(...).args(&argv)` (no

  can't be re-interpreted as a `ropusenc` flag.
- **Concurrency is sound:** the hand-rolled `AtomicUsize` work queue is partition-tested

- **Minor, not filed:** combining `--album X` with `--only-list` containing a path from
