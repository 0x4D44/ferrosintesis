# HLD — GS rhythm-part drum routing ("Use for Rhythm Part" SysEx)

**Status: SELF-APPROVED**
(Adversarial review: 2 reviewers — the single-flag rename was reversed to two flags on
their cross-refuted CC0-clobber finding. External review: Codex gpt-5.6-sol — mm≤2 guard
and GS-Reset handling folded. No critical findings, no architectural fork.)
Date: 2026-07-18
Task: `task/20260718-TSK-HUM-gs-rhythm-part-drum-routing`
Author: Claude Opus 4.8 (1M)

## Goal (one line)

Honor the Roland-GS **"Use for Rhythm Part"** SysEx so a channel a GS file declares
a drum/rhythm part renders as percussion — the GS counterpart to the XG `CC0=127`
routing already shipped (v0.21.25).

## Background / evidence

- The XG fix (v0.21.25) routes a channel to the drum path when its strip is flagged a
  drum part; the flag was `xg_drum` (set by XG bank MSB 127), and `Active.is_drum =
  ch == 9 || strip.<flag>` gates both mix passes.
- **GS uses SysEx, not a CC**, to declare rhythm parts. ferrosintesis's MIDI parser
  currently **discards every SysEx** (`midi.rs`, the `0xF0 | 0xF7` arm reads the length
  and skips the bytes), so GS rhythm parts are invisible to the engine — a GS file that
  puts drums on, say, channel 11 plays them as a melodic voice.
- **Verified GS format** (Roland F-20 MIDI impl; Roland GS / Wikipedia):
  - "Use for Rhythm Part" = DT1 to address **`40 1x 15`**, value **0**=OFF(normal),
    **1**=MAP1, **2**=MAP2. Full message: `F0 41 <dev> 42 12 40 1x 15 mm <sum> F7`.
  - The block nibble `x` is **not** the MIDI channel (the GS quirk): block `0`→Part 10
    (channel 10, index 9); blocks `1..9`→Parts 1..9 (index 0..8); blocks `A..F`→Parts
    11..16 (index 10..15).
- Corpus reality: scanned all 24 reference MIDIs — **zero** use "Use for Rhythm Part"
  (two use GS Reset + other part params; none the rhythm param). So there is **no
  real file to validate against**; validation is a **synthetic** GS MIDI + unit tests.
  Flagged as a residual risk. (GS rhythm parts are a real, widespread pattern in wild
  MIDI archives — the 24-file sample just lacks one.)

## Scope

**In scope**
- Parse **only** the GS "Use for Rhythm Part" SysEx in the MIDI parser; emit a new
  event; the engine flags the channel a drum part → existing `is_drum` routing.
- Generalize the strip flag `xg_drum` → `drum_part` (origin-agnostic: XG CC0=127 or GS
  SysEx). `Active.is_drum` logic unchanged.

**Out of scope (non-goals)**
- **A general SysEx framework.** Only this one message is decoded; every other SysEx is
  still skipped, exactly as today.
- **GS turning channel 10 melodic** (`on=0` on the default drum channel). Rare; would
  require `is_drum` to track an explicit "ch9 off" state. Deferred + documented; this
  change handles the extra-drum-channel direction (XG parity) only.
- **GS drum *map* selection** (MAP1 vs MAP2) and GS-specific kits — like XG, all
  rhythm parts use the default V3 kit. `on = (mm != 0)`; the map number is not mapped.
- **Checksum validation** of the SysEx — the message is parsed leniently (bounds-checked
  but the Roland checksum byte is not verified); honoring a slightly-off message beats
  rejecting it.

## Approach

1. **`midi.rs` — `EvKind::DrumMode { ch: u8, on: bool }`** (new variant), and in the
   `0xF0 | 0xF7` arm, capture the payload (instead of only skipping) and, when it matches
   the GS "Use for Rhythm Part" shape, emit the event at the current tick (bump `seq`).
   Everything else still skips. The match MUST check the address high nibble is `1`
   (part block), not only `payload[6]==0x15`, or other `40 Yn 15` GS params
   false-positive (correctness *and* the byte-identical invariant):
   ```rust
   // GS "Use for Rhythm Part": 40 1x 15, value 0=off / 1=MAP1 / 2=MAP2.
   if payload.len() >= 8
       && payload[0] == 0x41            // Roland
       && payload[2] == 0x42 && payload[3] == 0x12   // GS DT1
       && payload[4] == 0x40 && (payload[5] & 0xF0) == 0x10 && payload[6] == 0x15  // 40 1x 15
       && payload[7] <= 2               // reject invalid map values (only 0/1/2 are valid)
   {
       let ch = gs_block_to_channel(payload[5]); // helper masks the low nibble
       raw.push((tick, seq, EvKind::DrumMode { ch, on: payload[7] != 0 }));
       seq += 1;
   // GS Reset (40 00 7F): reverts part modes to default — clear every gs_drum
   // (ch10 stays drums via the ch==9 rule). Byte-safe for albums: gs_drum is
   // already false, so the emitted event is an audio no-op and the stable
   // (tick,seq) sort preserves the order of every audio event.
   } else if payload.len() >= 7
       && payload[0] == 0x41 && payload[2] == 0x42 && payload[3] == 0x12
       && payload[4] == 0x40 && payload[5] == 0x00 && payload[6] == 0x7F
   {
       raw.push((tick, seq, EvKind::GsReset));
       seq += 1;
   }
   ```
   ```rust
   // GS "block number" → 0-based MIDI channel. Masks internally so a malformed
   // address byte can never index strips[] out of bounds (ch is always 0..=15).
   fn gs_block_to_channel(block: u8) -> u8 {
       match block & 0x0F { 0 => 9, n @ 1..=9 => n - 1, n => n } // Part10 / Parts1-9 / Parts11-16
   }
   ```
2. **`engine.rs`** —
   - **Add** `Strip.gs_drum: bool` alongside the existing `xg_drum`. Do **not** rename
     `xg_drum` / fold the two: XG's flag is *driven by CC0* (127 sets, any other value
     clears — correct XG semantics), whereas a GS rhythm part still sends ordinary bank
     select (`CC0=0`) on that part, which must **not** un-drum it. The two origins have
     independent lifecycles, so they need independent flags. Compute
     `is_drum = ch == 9 || strip.xg_drum || strip.gs_drum`.
   - Handle the new events:
     `EvKind::DrumMode { ch, on } => self.strips[ch as usize].gs_drum = on;` and
     `EvKind::GsReset => { for s in &mut self.strips { s.gs_drum = false; } }`
     (processed always; not notes, so the `--solo` note-mask arm doesn't apply). No
     `alt_bank`/fx_profile reset is needed — drum voices bypass the melodic strip.
     GS Reset touches only `gs_drum` (the sole GS part-mode state ferrosintesis models);
     its other effects (volumes/pans/effects) aren't modeled, so they're N/A.

The drum voices, mix routing, per-channel gain/pan, and byte-identity properties are all
inherited unchanged from the XG work. Update the drum-pass comments that say "XG-drum"
to "XG/GS drum" (the parallel branch now serves both origins).

### File impact
- `crates/ferrosintesis/src/midi.rs` — new `EvKind::DrumMode`; ~10 lines in the SysEx
  arm; `gs_block_to_channel` helper; parser unit tests.
- `crates/ferrosintesis/src/engine.rs` — new `Strip.gs_drum` (decl + init); extend the
  `is_drum` expression; one match arm in `handle_event`; comment touch-ups; routing test.

### Live/realtime path (documented limitation)
Only the SMF parser (`midi.rs`) is changed. The realtime decoder (`live.rs`) handles
channel messages only and drops SysEx, so **GS drum routing is offline-only** (XG works
on both paths because CC0 is a channel message). The repo's pipeline is offline
(render-catalog / CLI), so this is acceptable; realtime GS input is not a goal (YAGNI).

## Acceptance criteria

1. **Parser (unit tests, driven through the real parser — not a direct helper call).**
   GS "Use for Rhythm Part" on block `0x1A` → `DrumMode { ch: 10, on: true }` (channel
   11); block `0x10` → ch 9; block `0x11` → ch 0 (exercises the `1..=9 → n-1` arm);
   `mm=0` → `on:false`. **Negatives emit no event:** GS Reset (`payload[6]=0x7F`), a
   near-miss offset (`40 1x 16`), a non-part high nibble (`40 2x 15`), and a truncated
   payload (`len<8`, must not panic).
2. **Routing (unit tests).** (a) A synthetic song — GS rhythm SysEx on ch11 + `NoteOn`
   there — renders **byte-identical to the same drum hit on ch9** (`assert_eq!`, single
   hit, mirroring the XG test), and differs from the same note as a melodic voice.
   (b) **CC0-clobber regression:** `SysEx(rhythm,ch11) → CC0=0 → PC → NoteOn` still
   routes to drums (proves the GS flag survives the ordinary bank select a real GS file
   sends — the reason `gs_drum` is separate from `xg_drum`).
   (c) **GS Reset regression:** `SysEx(rhythm,ch11) → GS Reset → NoteOn(ch11)` renders
   **melodic** (the reset cleared `gs_drum`), and invalid `mm=3` emits no `DrumMode`.
3. **Byte-identical albums.** Render-diff over all album MIDIs: **0 diffs** (no album
   sends this SysEx; the parser change only *adds* an event for a byte pattern none of
   them contain, and the field rename is semantics-preserving).
4. **Synthetic GS file.** Build a small GS `.mid` (Reset + Use-for-Rhythm-Part on a
   non-drum channel + drum-key notes), render it, confirm percussion (numeric).
5. `cargo fmt --check`, `clippy --workspace -D warnings`, `cargo test --workspace` green.

## Decision log
- **New event `DrumMode` vs reusing CC:** GS is SysEx; the parser must surface it
  somehow. A dedicated `DrumMode { ch, on }` event is cleaner than faking a CC.
- **Two flags (`xg_drum` + `gs_drum`), NOT one renamed `drum_part`** (reversed after
  adversarial review). Tempting to merge them, but their lifecycles differ: `xg_drum` is
  *defined by* CC0 (127 on, anything-else off), while a GS rhythm part legitimately sends
  `CC0=0` (bank select) without ceasing to be a drum part. A single flag would let that
  `CC0=0` clobber the GS SysEx and silently un-drum the channel — the exact files this
  targets. Independent origins → independent flags; `is_drum` ORs them.
- **Mask the nibble inside `gs_block_to_channel`** (`block & 0x0F`): a synth reads
  arbitrary file bytes and must never panic `strips[ch]` on a malformed address.
- **Match the address high nibble explicitly** (`(payload[5] & 0xF0) == 0x10`): without
  it, other `40 Yn 15` GS params would false-positive — breaking correctness and the
  byte-identical-album guarantee.
- **Reject invalid map values** (`mm > 2` emits nothing) but **do not verify the Roland
  checksum** (external-review call). The 7-byte address match is already highly specific
  and `mm ≤ 2` rejects garbage values; a full checksum check adds real code for a
  corrupt-file edge that cannot affect the byte-identical invariant. Lenient by choice.
- **Handle GS Reset** (`40 00 7F`) by clearing all `gs_drum` (external-review catch): a
  rhythm part set before a mid-song reset must not stay stuck. Byte-safe (no album's
  render changes — verified by reasoning and the render-diff).
- **Running status:** SMF cancels running status on SysEx; the capture arm touches the
  `status` byte exactly as the old skip path did, so this change is neutral. Whether the
  parser *should* clear running status on SysEx is pre-existing and out of scope (→
  scratchpad if it proves a real latent bug).
- **`on = mm != 0`:** MAP1 and MAP2 both mean "this is a rhythm part"; the map/kit
  distinction is a non-goal (parity with the XG kit-number non-goal).

## Residual risks
- **Synthetic-only validation** (no corpus file uses it) — the parser + routing unit
  tests and a hand-built GS file are the evidence; there is no real-world render to A/B.
- **Offline-only** (live/realtime `live.rs` drops SysEx; documented above).
- Assumes the "Use for Rhythm Part" SysEx precedes the channel's notes (well-formed GS
  files place the setup block at song start; same requirement XG's CC0 already has).
- Deferred: GS ch10→melodic, and GS drum-map/kit selection (documented non-goals).
