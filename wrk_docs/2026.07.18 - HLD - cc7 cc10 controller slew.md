# HLD — CC7 volume / CC10 pan controller slew (MM-BUG-KILN-00011)

- **Status:** SELF-APPROVED (2026-07-18). Option B (slew both), prime-on-first-block.
  Adversarial + external (Codex) reviews folded. NOT human-signed-off; the human gate is
  integration, which still needs Arthur's explicit go. See "Revised approach (Option B)",
  "Review outcome", and "External review (Codex) outcome".
- **Date:** 2026-07-18
- **Author:** Claude Opus 4.8 (1M context)
- **Bug:** MM-BUG-KILN-00011 (engine, Should/Medium)

## Goal (one line)

Route CC7 (channel volume) and CC10 (pan) through the same per-block slew that CC11
(expression) already uses, so foreign GM fades and pan sweeps ramp smoothly instead of
stepping at block boundaries — with jump-on-first-author so a set-once controller
renders bit-identically.

## Scope

**In:** CC7 volume and CC10 pan smoothing in `engine.rs` (offline + live share this
handler); haas_delay tracking the slewed pan; unit tests; render-diff verification.

**Out (non-goals):**
- The parked mono-compat concern (pan-authored Haas widening on mono downmix) —
  separate scratchpad item; this change keeps existing Haas behaviour, only making it
  track a slewed rather than stepped pan.
- Any change to CC11/expression, breath, aftertouch, or other controllers.
- Changing the slew time constant or making it configurable (reuse `expr_smooth`).
- Per-sample (vs per-block) interpolation — the block-rate slew is what CC11 uses and
  is sufficient to remove the audible stepping; per-sample is out of scope.

## Approach

> **SUPERSEDED — see "Revised approach (Option B)" at the end of this doc.** This
> section described jump-on-first-author (4 fields), which the review showed diverges
> from last-write-wins on same-tick authoring (finding 2). Kept for the decision trail.

Mirror the established `expr_target`/`expr` (target + slewed-current) pattern for
volume and pan. The single subtlety is **jump-on-first-author**, required to preserve
bit-identical catalog renders (see Decision D1).

**Strip fields (new):**
- `volume_target: f32` — set by CC7; `volume` becomes the slewed current.
- `volume_authored: bool` — first-CC7 latch.
- `pan_target: f32` — set by CC10; `pan` becomes the slewed current.
- `pan_authored: bool` — first-CC10 latch.

Defaults match the existing `volume`/`pan` defaults: `volume_target = (100/127)²`,
`pan_target = 0.5`, both `_authored = false`.

**CC handlers (`engine.rs:1706-1710`):**
```rust
7 => {
    let target = v * v;
    if s.volume_authored {
        s.volume_target = target;          // subsequent → slew
    } else {
        s.volume = target;                 // first → jump (bit-identical to today)
        s.volume_target = target;
        s.volume_authored = true;
    }
}
10 => {
    if s.pan_authored {
        s.pan_target = v;                  // subsequent → slew
    } else {
        s.pan = v;                         // first → jump
        s.pan_target = v;
        s.pan_authored = true;
    }
}
```
(The CC-time `s.haas_delay = …` line is removed; haas is derived per-block below.)

**Per-block slew (next to `engine.rs:2326`):**
```rust
strip.volume += self.expr_smooth * (strip.volume_target - strip.volume);
if strip.pan_authored {
    strip.pan += self.expr_smooth * (strip.pan_target - strip.pan);
    strip.haas_delay = 0.005 * sr * (strip.pan - 0.5).abs() * 2.0;
}
```
- Volume slew runs unconditionally like the expr slew — a provable no-op before the
  first CC7 (target == current == default), so it cannot change a no-CC7 channel.
- Pan slew + haas gated on `pan_authored`: a channel with no CC10 keeps `pan = 0.5`
  and `haas_delay = 0` byte-for-byte as today (pan is written ONLY by CC10 and init).

**Reset (`reset_all_controllers`, CC121):** unchanged — GM CC121 resets neither
volume nor pan, and the `_authored` latches persist (a fade in progress across a CC121
keeps fading). The existing test at `engine.rs:3584` already pins volume/pan surviving
CC121.

## Acceptance criteria

- **AC1 — catalog bit-identical.** render-diff over every album in `render-catalog`'s
  `ALBUMS` table (baseline = `git merge-base origin/main HEAD`), samples-on AND
  `--no-samples`, shows ALL SAME. Catalog channels set CC7/CC10 at most once, so
  jump-on-first-author must leave them unchanged. *Any* diff is a bug.
- **AC2 — smoothing engages.** A channel that sends a second, different CC7 moves
  `volume` only a fraction of the way to the new target after one block (not a jump),
  and converges over many blocks. Same for CC10 pan. (Unit test on `handle_event` +
  block advance.)
- **AC3 — jump-on-first.** The first CC7 sets `volume == v²` immediately (no ramp from
  default); the first CC10 sets `pan == v` and `haas_delay` immediately. (Unit test.)
- **AC4 — haas tracks slewed pan.** After a pan sweep, `haas_delay` equals
  `0.005*sr*(pan-0.5).abs()*2` for the *slewed* pan, and a no-CC10 channel keeps
  `haas_delay == 0`. (Unit test.)
- **AC5 — hygiene.** `cargo fmt --check`, `clippy -D warnings`, full crate suite green.

## Decision log

- **D1 — jump-on-first-author (not pure CC11 mirror).** Copying CC11's always-slew
  would ramp the first CC7 from the default over ~30 ms, changing every catalog
  render. Jump-on-first makes a set-once controller bit-identical while still smoothing
  genuine sweeps. Chosen; it is what makes AC1 achievable.
- **D2 — reuse `expr_smooth`, block-rate.** Same coefficient and update rate as CC11.
  No new time constant, no per-sample interpolation — least machinery, and CC11 proves
  block-rate is enough to kill the stepping.
- **D3 — haas derived per-block from slewed pan, gated on `pan_authored`.** Single
  source of truth (removes the CC-time computation); a no-CC10 channel is provably
  unchanged. The parked mono-compat concern is untouched.
- **D4 — CC121 leaves volume/pan (and the latches) alone.** Correct GM semantics;
  pinned by the existing reset test.
- **D5 — volume slew unconditional, pan slew gated.** Volume's default equals its
  target default so the unconditional slew is a no-op pre-author (simplest, mirrors
  expr). Pan is gated because `haas_delay` derivation must not engage on an unauthored
  channel.

## Review outcome (STEP 3 adversarial — 3 reviewers, refutation applied)

**AC1 is REFUTED and the premise "catalog sets CC7/CC10 at most once" is empirically
false.** I re-scanned every committed catalog + demo MIDI myself (124 files):

- **CC10 pan is a primary spatial device: 24 MIDIs automate it** with multi-value
  moves. Worst cases: Through Lines `Three-Sixty`/`Three-Sixty-One` ch0 = **1219
  events, full 0→127 sweep**; Bright Matter ch0 = 1061 / 1253 events (0→127); Winter
  Guests ch2 = 930 events; Atlas of Becoming, The Signal Fire, Wirewalker, and all 5
  showcase demos. Slewing pan changes the spatial rendering of all 24.
- **CC7 volume: 1 MIDI automates it** — Hollow Hill Part Two ch14 = 82→0→78 (a hard
  cut to silence and back). Slewing softens that cut into a ~30 ms fade.

Surviving findings (each checked against the other reviewers; none refuted):

1. **CRITICAL — premise false / AC1 unachievable as written.** Jump-on-first-author
   makes a *set-once* channel bit-identical, but the catalog does not set-once for
   pan. This is a scope/acceptance-criteria defect, not an implementation bug — it
   forces the decision below. (No hidden pan/volume writer exists — reviewers 1 & 3
   both confirmed `s.pan`/`s.volume` are written only by CC10/CC7 + init — so the
   *mechanism* is sound; the *data* refutes AC1.)
2. **MEDIUM (conditional on slewing pan)** — jump-on-first latches the FIRST value at a
   tick, but the old direct-write is effectively last-write-wins. Ignition Court ch9
   has two CC10 at tick 0 (54 then 64); old renders 64 from t=0, new jumps to 54 then
   slews to 64. Only bites same-tick double-authoring; pin with a test IF pan is slewed.
3. **MINOR** — `volume_target`'s default must be the *bit-exact expression*
   `(100.0f32/127.0).powi(2)`, not a rounded literal, or the "no-op before first CC7"
   is a tiny non-zero slew and every album diffs. (Folded into D6.)
4. **MINOR** — D5's claim that the per-block pan-slew *must* be gated on `pan_authored`
   "or it diffs" is wrong: an unauthored channel has `pan == 0.5` exactly, so the haas
   formula is `0.0` exactly. The gate is an optional micro-opt / defensiveness choice,
   not a correctness requirement. (D5 corrected below.)

**Reframing.** Because both CC7 and CC10 in the catalog are authored at *musical*
resolution (CC-event-spaced, ~100 ms), not per-block, there is no block-rate zipper in
the catalog to fix — the block-boundary stepping the bug describes is a **foreign-GM**
concern (files that stream CC7/CC10 every block). So this fix's real beneficiary is
faithful *foreign* GM playback, and its catalog effect is a side effect to be
minimized, not a benefit. That inverts the cost/benefit and is why the scope is a fork.

### Scope fork (awaiting Arthur)

- **Option A — CC7 volume slew only (my recommendation).** Fixes the demonstrable
  instant-volume-step / fade case (the bug's headline; real catalog instance = Hollow
  Hill Part Two), matches CC11. Blast radius: **1 album re-renders** (expected). All 24
  pan-automation albums stay bit-identical. Leaves pan instant.
- **Option B — slew both CC7 and CC10.** Full bug scope. Blast radius: **~24 albums
  re-render** (pan) + 1 (volume). Permissible under the synth-change policy (spatial
  improvement; renders are git-ignored build output), but it low-passes the authored
  pan trajectories of a dozen+ albums and needs a spot-check that they sound no worse.
  Also requires fixing finding 2 (last-write-wins at a tick).
- **Option C — won't-fix / by-design.** Argue CC-event-resolution pan/volume quantised
  to the 1.45 ms block grid is already fine and close 00011. Weakest: the Hollow Hill
  hard cut to 0 is a plausible click that Option A cheaply removes.

## Revised approach (Option B) — prime-on-first-block

Chosen after Arthur selected Option B. Slew **both** CC7 volume and CC10 pan through
`expr_smooth` (the CC11 coefficient, block-rate ~30 ms), but drive the snap/slew
decision from the **first rendered block after authoring**, not from the first CC event
in the handler. This fixes finding 2 (same-tick last-write-wins) *and* minimises diffs:
only genuine multi-tick sweeps change; set-once and same-tick channels stay bit-exact.

**Strip fields (new, 6):** per controller a target + two latches.
- `volume_target: f32`, `volume_authored: bool`, `volume_primed: bool`
- `pan_target: f32`, `pan_authored: bool`, `pan_primed: bool`

Defaults: `volume_target = (100.0f32/127.0).powi(2)` (the exact `volume` default
expression — D6), `pan_target = 0.5`; both latches `false`.

**CC handlers** — set the target, latch authored, nothing else (no jump, no haas here):
```rust
7  => { s.volume_target = v * v; s.volume_authored = true; }
10 => { s.pan_target    = v;     s.pan_authored    = true; }
```

**Per-block update (next to `engine.rs:2326`)** — snap on the first block after
authoring (captures last-write-wins from any same-tick burst), slew thereafter:
```rust
if strip.volume_authored {
    if strip.volume_primed {
        strip.volume += self.expr_smooth * (strip.volume_target - strip.volume);
    } else {
        strip.volume = strip.volume_target;   // snap: last value authored pre-render
        strip.volume_primed = true;
    }
}
if strip.pan_authored {
    if strip.pan_primed {
        strip.pan += self.expr_smooth * (strip.pan_target - strip.pan);
    } else {
        strip.pan = strip.pan_target;
        strip.pan_primed = true;
    }
    strip.haas_delay = 0.005 * sr * (strip.pan - 0.5).abs() * 2.0;
}
```
- Events for a block are dispatched before `render_block_add` (confirmed: `handle_event`
  at 2626 precedes the render at 2629), so a same-tick burst has fully updated
  `*_target` before the block snaps → snap == last write == old behaviour.
- A channel that never authors CC7/CC10 skips the block entirely → `volume`/`pan`/
  `haas_delay` stay at their defaults byte-for-byte (confinement).
- The CC-time `haas_delay` line (old `engine.rs:1709`) is removed; haas is derived once
  per block from the slewed pan (single source of truth, tracks the sweep).
- `reset_all_controllers` (CC121) still leaves volume/pan and the latches alone.

## Acceptance criteria (Option B, revised)

- **AC1 — confinement + faithful setup.** render-diff over every album + demo
  (baseline = merge-base), samples-on AND `--no-samples`: channels that never author
  CC7/CC10, and channels that author them only at a single tick (incl. same-tick
  redundant writes), render **bit-identical**. Only genuine multi-tick CC7/CC10 sweeps
  diff. Expected diffs: the 24 pan-automation MIDIs + Hollow Hill Part Two (CC7). A diff
  on any *non*-authoring channel/album is a bug.
- **AC2 — smoothing engages.** A mid-piece second CC7/CC10 (different value, later tick)
  moves `volume`/`pan` a fraction toward target after one block and converges over many.
- **AC3 — prime / last-write-wins.** First block after authoring snaps to the *last*
  target authored before that block (no glide from default); a same-tick 54-then-64 pair
  yields 64 at the start, matching the old direct-write. (Unit test — pins finding 2.)
- **AC4 — haas tracks slewed pan.** After a pan sweep `haas_delay` equals the formula on
  the *slewed* pan; a no-CC10 channel keeps `haas_delay == 0`.
- **AC5 — hygiene.** `cargo fmt --check`, `clippy -D warnings`, full crate suite green.
- **AC6 — quality (numeric only; this box has no ears).** The slewed pan/volume is a
  monotone-tracking, bounded-lag smoothing of the stepped trajectory (no overshoot, no
  DC on silent channels). Audible "sounds no worse" on the 24 albums is **unverified**
  (no ears) and carried to Arthur as a residual risk.

- **D7 — prime-on-first-block over jump-on-first-author.** Costs 2 extra fields vs the
  superseded design but makes same-tick and set-once channels bit-identical (only real
  sweeps diff) and fixes finding 2. Under Option B — where faithful playback is the
  whole point — minimising unnecessary diffs and honouring last-write-wins is worth the
  two bools. Slews stay open-coded inline (reviewer 3: a 7th/8th inline slew is the right
  altitude; do not add a helper).

## External review (Codex, gpt-5.6-sol xhigh) outcome

Codex reviewed the algorithm (it could not open the local files — Windows sandbox
launcher missing — so it assessed the described state machine, not the source). Verdict:
"the prime/slew state machine is broadly sound." Folded items:

- **[SIGNIFICANT → folded] Compat claim is narrower than "only multi-tick sweeps diff".**
  Precise invariant: **a channel is bit-identical iff it authors no CC7/CC10 change after
  its priming block.** A *later* same-tick burst (channel already primed) slews, not
  last-write-wins; a first-ever *mid-song* value still snaps. AC1 reworded; AC3 test
  matrix widened to {initial set-once, late-first-mid-song, later-post-prime burst,
  CC121-then-reuse}.
- **[SIGNIFICANT → folded as AC7] Moving Haas tap needs its own oracle.** Verified in
  source: `DelayLine::tap` is **linearly interpolated** (`dsp.rs:334`); `haas_delay` is
  captured once per block (`engine.rs:2352`) and near centre `haas < 1.0` disengages the
  delay (`engine.rs:2377`), so the L↔R side-flip happens while the tap ≈ 0. Crucially the
  slew makes the tap move ~0.5 sample/block vs **today's ~10-sample instant jump per CC10
  event** — strictly smoother than baseline. New AC7 proves it numerically rather than by
  assertion.
- **[SIGNIFICANT → folded into AC6] "Render-diff can't prove improvement."** AC6 upgraded
  from "no ears, unverified" to a numeric boundary-discontinuity oracle; diff files are
  classified by *post-prime change*, not mere CC7/CC10 presence.
- **[MINOR → noted] 30 ms TC.** Reasonable for the catalog (Codex: ~2 CC-unit steady lag,
  ~90 ms to 95% after a step; attenuates autopan above ~5 Hz). Keep the shared
  `expr_smooth`; a pan-specific ~10 ms TC is a *follow-up only if* a specific album's
  short/deep pan visibly undershoots (checked by AC7's trajectory measurement).
- **[MINOR → no change] 6 fields acceptable** — three real lifecycle states (unseen /
  pending-prime / active); an enum wouldn't materially simplify this open-coded engine.

### Acceptance criteria — deltas from the review

- **AC1 (reworded).** Bit-identical iff a channel authors no CC7/CC10 change after its
  priming block. Expected diffs = channels with a post-prime CC7/CC10 change (the 24 pan
  MIDIs + Hollow Hill Part Two). Any diff on a channel with no post-prime change is a bug.
- **AC3 (widened).** Test {initial set-once at t0; first CC mid-song → snaps; a post-prime
  same-tick 54→64 burst → slews toward 64; CC121 then reuse}.
- **AC6 (numeric).** For a synthetic auto-pan, the slewed pan/haas trajectory has *fewer/
  smaller* per-block-boundary discontinuities than the un-slewed baseline (monotone
  tracking, no overshoot). Replaces "no ears".
- **AC7 (new — Haas tap).** On a bright signal auto-panned across centre, block-boundary
  discontinuity of the far-side (Haas-delayed) channel is **no worse than baseline** (and
  expected smaller). Confirms the per-block-moving linear-interpolated tap does not click.
