## Goal (one line)

Let Arthur hear the six amp knobs move **in a mix, in real time**, so Part B's defaults are chosen
by ear in seconds rather than by a render-listen-describe-adjust loop that takes minutes.

## Why a tool rather than more renders

Part B's question — *what should GM29 and GM30 actually default to?* — is an ear-driven search over
a six-dimensional space. Static renders answer one point per round trip. The bottleneck is feedback
latency, not synthesis. A knob collapses it.

Arthur's ask: *"a small GUI app with knobs I can twiddle, switches to choose the different GM
program and a built in sample track with guitars, bass and drums that loops."*

## Scope

**In:**
- Native window: six knobs, program (29/30) and bank (main/lead) switches, transport, guitar
  solo/mute, an A/B snapshot pair, and an export button.
- A purpose-built looping backing track — rhythm guitar, lead guitar, bass, drums.
- Realtime audio out.

**Out (non-goals):**
- Any change to `ferrosintesis`. The synth already exposes everything needed (`write_byte`,
  `render_add`, `prewarm_samples`); if this tool seems to need a synth change, that is a signal the
  design is wrong.
- Editing base voicing parameters that are not NRPN knobs (`tilt`, `bias`, cab[0], the Qs). The six
  knobs now have wide measured ranges; add more only if six prove insufficient.
- Showing ABSOLUTE resolved values (`g1 = 18.3`). `DriveBase` is private, and exposing it would widen
  a published crate's API for a dev tool. The knob values plus program/bank fully determine the
  sound, so they are sufficient to reproduce and to derive defaults from.
- MIDI input, presets on disk, VST/plugin anything.

## Approach

### 1. The synth is driven by real MIDI bytes, and that is the point

Every control crosses as the actual byte sequence an album would author — a knob is
`CC99 0x30 / CC98 <idx> / CC6 <val>`, a program switch is `0xCn 29`, a bank switch is `CC0`. So the
tool **cannot drift from what a `.mid` gets**: if it sounds good here, authoring those numbers
reproduces it exactly. It also means the lab exercises the shipped authoring path rather than a
parallel one.

### 2. Threading — the one genuinely hazardous part

`RealtimeSynth` buffers `write_byte` into a `Vec` consumed at the next `render_add` block, so the
synth must be owned by **exactly one** thread. Putting it behind a `Mutex` shared with the UI is the
obvious wrong answer: a UI thread holding that lock during a repaint causes priority inversion and
audible dropouts.

So:

- **The audio thread owns the synth**, and with it the sequencer and all playback state.
- **The UI thread sends commands** through a lock-free single-producer/single-consumer ring. The
  audio callback drains it at the top of each block.
- The ring carries a small command enum rather than bare bytes, because solo/transport are not MIDI:
  `Midi(u8)`, `Solo(bool)`, `Play(bool)`, `Panic`.
- The ring is hand-rolled on `std` atomics (~40 lines). A byte/enum SPSC queue does not justify a
  dependency, and hand-rolling keeps the realtime path auditable.
- `prewarm_samples()` runs during setup, off the audio thread — it exists precisely so the embedded
  banks do not decode lazily inside the callback and blow the deadline.

### 3. The sequencer lives on the audio thread

Scheduling is "at frame N, emit these bytes", which is sample-accurate and free. Driving the loop
from the UI thread would jitter events by a frame interval (~16 ms) — inaudible on a pad, obvious on
a snare.

### 4. The backing loop

Eight bars, authored as a committed `.mid` and embedded with `include_bytes!`, so the tool is
self-contained:

| channel | part | why |
|---|---|---|
| 0 | rhythm guitar, GM30 main | the chug — where a rig either sits in the mix or does not |
| 1 | lead guitar, GM29 alt (lead bank) | the singing line — the register Arthur's original complaint was about |
| 2 | bass, GM33 | masks the low-mids, which is where Body lives |
| 9 | drums | cymbals sit exactly where Presence and Cab Tone live |

Bass and drums are not decoration: they occupy the bands the cabinet knobs move, so a rig judged
solo will be judged wrong. Solo/mute is there to switch between the two judgements deliberately.

### 5. Export is the actual deliverable

The tool's output is not audio, it is numbers. A button copies the current state as a line I can
paste straight into a Part B change, plus the `engine.py` NRPN calls an album would use. Two
snapshot slots (A/B) with instant toggle, because ears cannot compare against a 30-second-old
memory — the exact failure mode that made round 1 sound like "no difference".

### 6. Crate layout — deliberately OUTSIDE the workspace

`crates/amp-lab/`, `publish = false`, and **excluded from the workspace members**.

`cargo test --workspace --locked` is the integration gate for this repo. Adding egui + cpal to the
workspace would make every future integration — by any agent, forever — build a ~200-crate tree for
a dev tool it never runs. Excluding it keeps the gate exactly as fast as it is today, at the cost of
the lab needing its own `cargo run` and lock file. It still `path`-depends on `ferrosintesis`, which
works fine across a workspace boundary.

amp-lab is not among them.

## Acceptance criteria

1. It makes sound: the loop plays, seamlessly, indefinitely.
2. Every knob audibly changes the guitar while playing, with no dropout, click or xrun on change.
3. Program (29/30) and bank (main/lead) switches take effect live.
4. Solo/mute isolates the guitar and restores the mix.
5. A/B toggle switches between two stored settings instantly.
6. Export produces a line that, pasted as NRPN into a `.mid`, renders **the same sound** — verified
   once by rendering an exported setting offline and comparing against the lab.
7. No application lock or explicit syscall on the audio thread after setup. Steady
   rendering, controller traffic and panic handling allocate exactly zero; NoteOn may
   allocate only while constructing a voice, held by the ≤16-allocation-per-note
   regression ratchet. Amp-lab is explicitly best-effort soft realtime and counts xruns.
8. `cargo test --workspace` at the repo root is **unaffected** (the lab is excluded) and still green;
   the lab builds and runs on Windows.

## Decision log

- **Everything crosses as real MIDI bytes.** Makes lab-vs-album divergence structurally impossible
  and exercises the shipped path.
- **Audio thread owns the synth; UI talks to it through a lock-free ring.** A shared `Mutex` is the
  standard way to get dropouts; `write_byte`'s buffering already assumes single ownership.
- **Sequencer on the audio thread** for sample-accurate drums.
- **Voice construction is the measured soft-realtime exception.** The shared engine's
  heterogeneous `Box<dyn Voice>` path may allocate on NoteOn; every other measured
  callback shape stays allocation-free, the per-note count is ratcheted, and xrun
  telemetry remains active. `LIVE_MAX_VOICES` bounds concurrent voices, not allocations
  per callback, so this is not represented as a hard-realtime guarantee
  (MM-BUG-KILN-00092).
- **Hand-rolled SPSC ring** — a byte queue does not justify a dependency.
- **Lab excluded from the workspace** so the repo's integration gate does not grow a 200-crate tree
  for a tool it never runs.
- **No absolute-value display in v1** — it would mean widening a published crate's API for a dev
  tool. Knob values plus program/bank are sufficient to reproduce.
- **Export and A/B are v1, not polish.** Without them the tool produces opinions instead of numbers,
  and opinions are what we already have.

## Residual risks

- **Realtime headroom is inferred, not measured.** Offline runs ~8.5× realtime, so a callback should
  be comfortable, but that is an average over a whole track — a dense moment with the 4× driven
  shaper on two channels could spike. Mitigation: a voice-count/load readout in the UI, and drop to
  a larger buffer if it xruns. Measure before trusting.
- **cpal device quirks on Windows** (exclusive vs shared mode, odd default rates) are the usual
  source of "no sound" — the UI must surface the chosen device and rate rather than failing silently.
- **The loop is a composition and my taste may not suit the judgement.** If the riff fights the
  knobs, it is cheap to re-author — but a bad loop could mislead the whole Part B decision, which is
  the same class of error as a bad probe in round 1.
