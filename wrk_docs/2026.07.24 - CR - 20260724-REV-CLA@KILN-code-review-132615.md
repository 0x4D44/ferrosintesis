### CR-1 — The 44.1-kHz rain recording runs at the output sample rate

- **Severity:** Medium
- **Confidence:** High
- **Where:**
  `D:\worktrees\midi-music\20260724-REV-CLA@KILN-code-review-132615\crates\ferrosintesis-samples-rain\README.md:3`;
  `D:\worktrees\midi-music\20260724-REV-CLA@KILN-code-review-132615\crates\ferrosintesis\src\sampler.rs:43`;
  `D:\worktrees\midi-music\20260724-REV-CLA@KILN-code-review-132615\crates\ferrosintesis\src\voices.rs:11753`;
  `:11913`; `:11980`;
  `D:\worktrees\midi-music\20260724-REV-CLA@KILN-code-review-132615\crates\ferrosintesis\src\engine.rs:1708`;
  `D:\worktrees\midi-music\20260724-REV-CLA@KILN-code-review-132615\crates\ferrosintesis\src\live.rs:58`
- **Tracked as:** new Open bug `MM-BUG-KILN-00086`.
- **Problem:** the decoded 44.1-kHz PCM advances by one source frame per output
  frame. There is no `44_100 / output_rate` conversion. The 202,860-frame
  recording therefore takes 4.226 seconds at 48 kHz instead of 4.6 seconds, and
  2.113 seconds at 96 kHz.
- **Concrete fix:** use a fractional, wrapped source cursor advanced by
  `44_100 / sr`, with interpolation. Add a 44.1/48/96-kHz source-phase and
  rendered-control oracle, preserving exact 44.1-kHz reads.
- **Effort:** Medium.

### CR-2 — First realtime GM 96 use can decode the WAV inside the callback

- **Severity:** Medium
- **Confidence:** High
- **Where:**
  `D:\worktrees\midi-music\20260724-REV-CLA@KILN-code-review-132615\crates\ferrosintesis\src\sampler.rs:110`;
  `:2662`; `:4739`;
  `D:\worktrees\midi-music\20260724-REV-CLA@KILN-code-review-132615\crates\ferrosintesis\src\voices.rs:11880`
- **Tracked as:** existing Open bug `MM-BUG-KILN-00073`; no duplicate filed.
- **Problem:** `rain_loop()` lazily decodes into a `OnceLock<Vec<f32>>`, but
  `prewarm()` omits it. The coverage oracle enumerates public `*_bank`
  accessors, so it cannot see this differently-shaped cache. A first sampled
  GM 96 NoteOn can therefore decode and allocate in the deadline-bearing
  realtime path despite the prewarm contract.
- **Concrete fix:** follow `MM-BUG-KILN-00073`: prewarm the rain loop and derive
  coverage from every realtime-reachable lazy cache rather than an accessor
  naming convention.
- **Effort:** Medium, dominated by making the coverage oracle total rather than
  by the one-line prewarm call.

## Not reported

- **Rain-bed velocity response — needs re-verification, not confirmed.** The
  recording gain is independent of NoteOn velocity while the crystal core is
  velocity-sensitive. That implementation fact is clear, and
  `velocity_law.rs:360-364` calls GM 96's response undiagnosed. No accepted
  dynamic-response contract or reference measurement establishes the correct
  curve, so this review did not turn a voicing choice into a bug.
- **Identical rain phase across simultaneous notes — needs re-verification, not
  confirmed.** Every voice starts the same loop at position zero, so
  simultaneous notes stack the bed coherently. The current design is explicitly
  per-note and no overlap-level or shared-channel contract defines the desired
  behavior. A product/oracle decision must precede a defect claim.
- **Untrusted-WAV parser attack — refuted for this area.** Runtime bytes come
  from compile-time `include_bytes!`; the crate exposes no file, network, shell,
  or MIDI-device input. The committed header was inspected as PCM16 mono
  44.1 kHz.
- **Steady-state allocation or unbounded loop state — refuted.** The crate
  returns static bytes, decoded PCM is cached once, playback uses a bounded
  cursor, and note-off drains the envelope to termination. CR-2 is specifically
  the first-use decode before that steady state.
- **Filename collision in the global embedded lookup — refuted.**
  `rain_loop.wav` is unique among the current sample crates, and the optional
  dependency, feature, lookup, and consumer chain all include the rain crate.
