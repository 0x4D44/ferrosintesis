## Confirmed findings

### CR-1 — Medium: Headroom rebakes trust mutable sources and invalid caches

- **Confidence:** High
- **Where:**
  `D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-134004\tools\ferrosintesis-samples\prepare.py:746`,
  `D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-134004\tools\ferrosintesis-samples\prepare.py:1366`,
  `D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-134004\tools\ferrosintesis-samples\prepare.py:1379`,
  `D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-134004\tools\ferrosintesis-samples\prepare.py:2943`,
  and
  `D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-134004\crates\ferrosintesis-samples-headroom\PROVENANCE.md:46`
- **Tracked as:** `MM-BUG-KILN-00139`
- **Problem:** The 45 unique Headroom FLAC inputs follow mutable GitHub
  `master` URLs and have no expected digests. Warm FLAC and decoded-WAV cache
  entries are accepted by existence alone. ffmpeg writes directly to the final
  cache WAV, so an interrupted conversion can leave a partial file that the
  next run trusts. The cache path is keyed by unrelated `VSCO_REV`.
- **Impact:** Clean and warm machines can consume different or arbitrary
  inputs despite the documented deterministic recipe. A failed conversion can
  persist across runs or silently feed incomplete PCM into a future rebake.
- **Concrete fix:** Pin an immutable Headroom revision and source hashes; give
  it a recipe-keyed cache; verify warm entries; transcode to a temporary file;
  validate the PCM contract; atomically replace the final cache entry; and add
  changed-source, altered-cache, truncation, and interruption regressions.
- **Effort:** Medium

The source-identity and interrupted-write facets remain one bug because they
share the same cache-acceptance invariant and fix surface. This is not evidence
that the current committed WAVs are wrong.

### CR-2 — Low: Headroom rebakes retain obsolete generated WAVs

- **Confidence:** High
- **Where:**
  `D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-134004\tools\ferrosintesis-samples\prepare.py:3106`,
  `D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-134004\crates\ferrosintesis-samples-headroom\Cargo.toml:10`,
  and
  `D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-134004\tools\ferrosintesis-samples\gen_crate_lib.py:29`
- **Tracked as:** `MM-BUG-KILN-00140`
- **Problem:** Generation writes current mapped outputs but never rejects an
  obsolete owned `headroom_*.wav`. Cargo packages every sample, and table
  regeneration re-enumerates every remaining WAV.
- **Impact:** A sample removed or renamed for provenance, licensing, or quality
  reasons can remain published and become self-consistent with regenerated
  inventory metadata.
- **Concrete fix:** Derive the expected output set before writing and fail
  closed with the names of unexpected owned files. Add extra-file and rename
  regressions that prove the failure precedes all writes.
- **Effort:** Small

The current inventory contains no stale file. Closed `MM-BUG-KILN-00123` fixed
the same defect class only in `_bake_darkened_grand`; its guard does not execute
for Headroom.
