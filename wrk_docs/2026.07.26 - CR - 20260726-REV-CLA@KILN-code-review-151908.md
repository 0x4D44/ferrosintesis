## Confirmed findings

### CR-1 — The rebake does not reject obsolete owned outputs

- **Severity:** Low
- **Confidence:** High
- **Where:**
  `D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-151908\tools\ferrosintesis-samples\prepare.py:2709`;
  `D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-151908\crates\ferrosintesis-samples-honkytonk\Cargo.toml:10`;
  `D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-151908\tools\ferrosintesis-samples\gen_crate_lib.py:29`
- **Tracked as:** Open bug `MM-BUG-KILN-00143`.
- **Problem:** `_bake_honkytonk` overwrites only the names currently derived
  from `HONKYTONK_NOTES`. It never rejects an existing
  `honkytonk_*.wav` whose note was removed or renamed. Cargo packages the
  leftover, and a later `gen_crate_lib.py` run enumerates and embeds it, making
  the generated inventory tests self-consistent.
- **Impact:** a payload retired for provenance, licensing, or quality reasons
  can remain in the published crate.
- **Concrete fix:** derive the complete expected output set before writing;
  fail closed with every unexpected owned filename. Add extra-output and
  renamed-note regressions that prove rejection happens before the first write.
- **Effort:** Small.

The devil's advocate confirmed this is not deduplicated by
`MM-BUG-KILN-00123` or `MM-BUG-KILN-00140`: their guards are family-specific
and never execute for `_bake_honkytonk`.

### The WAV guard does not require a `fmt ` chunk

The crate-local check at
`D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-151908\crates\ferrosintesis-samples-honkytonk\src\lib.rs:87`
checks only length and RIFF/WAVE magic. The consumer parser at
`D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-151908\crates\ferrosintesis\src\sampler.rs:43`
validates PCM fields only when a `fmt ` chunk exists. A data-only RIFF can
therefore bypass the advertised format guard.

The current files all carry valid `fmt ` and `data` chunks, and the input is a
trusted compile-time asset rather than external runtime data. This is shared
future-regression hardening, not a present runtime defect. Strengthen the
generated template once for every asset crate and make `parse_wav` require
exactly one supported `fmt ` contract.

### The nine PCM-to-root mappings lack a bank-wide pitch oracle

The manual mapping at
`D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-151908\crates\ferrosintesis\src\sampler.rs:1635`
is decoded by prewarm, but prewarm asserts cache reachability rather than pitch.
The sampled O-PITCH leg at
`D:\worktrees\midi-music\20260726-REV-CLA@KILN-code-review-151908\crates\ferrosintesis\src\voices.rs:27003`
uses one case per program; the dedicated honky-tonk character check probes only

A focused oracle should measure the sample-owned onset for all nine roots and
