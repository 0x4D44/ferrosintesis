# Bounded-memory offline rendering

**Status: SELF-APPROVED**

## Goal

Make ferrosintesis's shipping offline renderers use memory that is effectively
independent of track duration: render float audio to bounded-memory disk scratch,
measure loudness as blocks are produced, then normalize, measure/limit true peak,
dither, and write the final WAV through bounded buffers.

## Scope

- Add a high-level `offline::render_to_wav` path for peak or loudness normalization.
- Move `ferrosintesis-cli` and `render-catalog` to that path.
- Preserve atomic CLI replacement and failed-render cleanup.
- Preserve the existing public buffer APIs for callers that deliberately want samples
  in memory.
- Preserve the current normalization, true-peak limiter, deterministic dither, and WAV
  byte semantics. Representative streaming output must match the existing buffered path
  byte-for-byte.

Out of scope:

- Realtime synthesis.
- A new limiter sound or normalization policy.
- Changing sample-bank caching; its process-lifetime cache is bounded and not the
  duration-dependent problem.
- Version changes; integration owns the one version bump.

## Approach

### 1. Stream the synth into float scratch

Refactor the engine's existing event/render loop behind one internal block driver. The
buffer API continues to render directly into its caller-owned full buffer. The new path
renders one interleaved stereo block at a time and passes it to an I/O sink.

The shared driver retains the existing 64-frame block size, event quantization/order,
zeroed block input, and final partial-block truncation. Those are audio invariants, not
I/O tuning parameters.

The high-level offline path writes each block as little-endian `f32` to a uniquely
reserved scratch file beside the requested WAV. While writing it, it feeds:

- a streaming BS.1770 meter holding only the 400 ms K-weighted window plus its small
  100 ms-hop energy table.

Each overlapping 400 ms window is re-summed from zero in chronological `f64` order,
matching the buffered implementation. A rolling subtract/add sum is forbidden because
its different rounding can move a gate decision.

Raw true peak can be observed during rendering, but it cannot decide whether the
post-gain limiter is needed: `f32` scalar multiplication rounds each sample before the
FIR. The limiter therefore measures the actually scaled scratch and takes the existing
`env > ceiling` branch exactly.

### 2. Normalize scratch in bounded disk passes

Keep the existing normalization loop and limiter constants. Apply scalar gain to the
float scratch in fixed-size chunks.

When limiting is required, one limiter pass:

1. scans float audio and writes one raw `f32` gain per frame to a second scratch file;
2. applies the existing anticipatory-attack recurrence backwards over that gain file;
3. applies the release recurrence forwards;
4. multiplies audio by the resulting gain in fixed-size chunks.

Repeat exactly as the current limiter and loudness-recovery loops require. This replaces
duration-sized RAM with duration-sized disk scratch while retaining the same per-sample
operation order. The first render's loudness result avoids a redundant initial
measurement pass. Every limiter decision is made from a scan of the actually rounded
scaled samples; there is no `raw_true_peak * gain` shortcut.

Peak normalization uses the same float scratch but needs only one sequential read.

### 3. Stream the final PCM WAV

Factor the WAV header and incremental PCM writes into an internal writer. Read normalized
float scratch in chunks, run the existing deterministic TPDF dither state in sample
order, and write little-endian `i16` directly to the final WAV. Scratch files are
RAII-owned and removed on success, error, or panic unwinding.

The public API is:

```text
render_to_wav(
    song: &Song,
    opt: &Options,
    output: &Path,
    normalization: Normalization,
) -> io::Result<Stats>
```

with a progress-callback twin. `Normalization` is a public non-exhaustive struct with
private state and `loudness(target_lufs, ceiling_dbtp)` / `peak(target)` constructors,
matching the crate's sealed `Options` convention.

The library call is atomic: it reserves a sibling temporary final file, renders and
syncs it, then renames it over `output`. An existing output survives any failure before
the rename; no partial WAV is exposed at the requested path. Its `io::Error` reports
invalid RIFF size or the underlying scratch/final I/O failure, and successful return
contains the render `Stats`.

The CLI retains its input/output alias rejection, then calls the library API directly.
`render-catalog` retains a temporary WAV lifetime for the encoder, but places that WAV
beside the destination Opus rather than in `%TEMP%`; the float and gain scratch therefore
stay on the caller-selected output filesystem too.

Before synthesis begins, checked `u64` arithmetic verifies that the final stereo `i16`
data and `36 + data_len` fit classic RIFF's 32-bit fields. Oversized output returns
`InvalidInput`; RF64 is explicitly out of scope. The existing public `write_wav` gets
the same checked arithmetic so it cannot retain the wrapped-header bug.

All fixed-size reads use `read_exact`; in-place read/modify/write uses one explicitly
seeked unbuffered file handle rather than overlapping buffered readers/writers. Every
`BufWriter` is explicitly flushed, its error checked, and the completed final temporary
file is `sync_all`ed before rename. Scratch names follow the existing hidden
`.<name>.<pid>.<sequence>.tmp` convention. Normal errors and unwind panics clean them;
process termination can leave an identifiable orphan, which is a residual risk rather
than grounds for deleting possibly-live files from another process.

Peak transient storage is 16 bytes per frame per concurrent render: 8-byte stereo float
audio, 4-byte gain curve while limiting, and 4-byte stereo PCM final. A 60-minute
44.1 kHz render therefore needs about 2.54 GB of output-filesystem space while active.
The existing iteration caps bound pass amplification, but pathological high-crest input
can still trade substantial disk I/O for exact output and bounded RAM.

## File impact

- `crates/ferrosintesis/src/engine.rs` — shared block render driver and stateful dither
  seam.
- `crates/ferrosintesis/src/loudness.rs` — bounded streaming loudness/true-peak meters
  and disk limiter primitives.
- `crates/ferrosintesis/src/wav.rs` — incremental PCM WAV writer.
- `crates/ferrosintesis/src/offline.rs` — public high-level normalization mode and
  render-to-WAV API; scratch ownership and orchestration.
- `crates/ferrosintesis-cli/src/main.rs`, `output.rs` — retain alias protection and
  invoke the library's atomic streaming render.
- `crates/render-catalog/src/main.rs` — invoke the same streaming library path.
- README/API docs only where the old buffer-first pipeline is stated as the normal path.

## Acceptance criteria

1. CLI and catalog default loudness renders never allocate a vector proportional to total
   track frames; their audio working buffers are fixed-size plus the bounded sample cache
   and small loudness block-energy table.
2. CLI legacy peak normalization is also bounded-memory.
3. Streaming loudness and true-peak measurements match the buffered meters across
   adversarial chunk boundaries.
4. Representative silence, un-limited tone, and transient-limited fixtures produce
   byte-identical `i16` output through buffered and scratch-backed normalization.
5. Differential fixtures cover more than one loudness-recovery iteration, more than one
   limiter pass, threshold-adjacent true peaks, degenerate sub-400 ms/zero-frame audio,
   arbitrary chunk boundaries, and legacy peak normalization.
6. A short MIDI rendered through old buffer+normalize+WAV and new render-to-WAV produces
   byte-identical WAV bytes and identical render `Stats`.
7. Partial/failed output and both scratch files are cleaned; an existing output is
   preserved on failure.
8. Short scratch reads are errors; explicit flush/sync failures propagate rather than
   being swallowed.
9. Output exceeding classic RIFF limits is rejected before rendering with checked
   arithmetic.
10. Fixed audio/gain/PCM chunk capacities are asserted independently of declared frame
    count; the only duration-scaled RAM is the explicitly bounded BS.1770 hop table.
11. Existing buffer APIs and their tests remain green.
12. Focused tests, formatting, clippy for the three affected crates, and their tests
    pass.

## Decision log

- **Disk passes over a new limiter:** preserve the current sound and deterministic output.
  A one-pass lookahead redesign is smaller in I/O but changes gain curves everywhere.
- **Keep buffer APIs:** they are published and useful; only shipping entry points need the
  bounded path.
- **Scratch beside the final WAV:** this uses the caller-selected filesystem, keeps
  permissions predictable, and avoids silently filling an unrelated system drive.
  Catalog staging moves beside the destination Opus so this statement is true there too.
- **One gain value per frame on disk:** it is the smallest direct representation that
  preserves the current backward attack and forward release recurrences exactly.
- **Atomic public path:** a high-level rendering API should not leave a partially written
  requested WAV or destroy a prior good result.
- **Classic RIFF preflight, not RF64:** rejection fixes the existing wrapped-header bug
  without adding another output format.
- **Measure scaled true peak:** algebraic scaling is mathematically valid over exact
  reals, but not byte-equivalent after per-sample `f32` rounding.
- **No dependency:** standard-library buffered I/O is sufficient.

## Review record

### Adversarial review

Two independent reviews completed, followed by one mutual-refutation pass. A third
replacement attempt returned after the original reviewer recovered, but did not run the
required refutation and is therefore unverified rather than counted.

Surviving findings folded into this design:

- Preflight classic RIFF's 32-bit size limit; the parser's 24-hour cap exceeds it.
- Define the public API's atomic overwrite, partial-output, result, and error contract.
- Re-sum every overlapping BS.1770 window in the buffered implementation's exact order;
  do not use a rolling floating-point sum.

Clarification folded in from an initially unverified finding:

- Do not infer the limiter branch from raw true peak times scalar gain. Measure the
  actually rounded scaled scratch.

Refuted findings:

- The bounded 100 ms-hop energy table is compatible with “effectively independent”:
  the 24-hour input cap bounds it near 6.9 MiB, versus roughly 61 GiB removed.
- Required engine block, limiter recurrence, FIR boundary, and persistent dither state
  are already enforced by byte-identical old/new acceptance; they remain implementation
  invariants.
- Specific random/fault-injection mechanics and adaptive concurrency are useful test or
  operational choices, not missing correctness requirements in this design.

### External cross-family review

One read-only Claude Opus review completed without subagents.

Accepted:

- State the 16-byte-per-frame scratch/final disk budget and bounded but potentially high
  pass amplification.
- Move catalog staging off `%TEMP%` and beside its destination.
- Require explicitly seeked in-place I/O, `read_exact`, checked `flush`, and `sync_all`.
- Extend byte-equivalence coverage to multi-iteration loudness, multi-pass limiting,
  peak normalization, degenerate lengths, and threshold boundaries.
- Apply checked RIFF sizing to the existing public `write_wav`, not only the new API.
- Keep `Stats` unchanged; the CLI can read final file metadata for its size report.
- Seal `Normalization` behind constructors rather than exposing enum fields.

Rejected:

- Retaining the complete render buffer after removing only derived intermediates. It
  would still consume about 1.2 GiB for the reproduced hour track and does not meet the
  confirmed duration-independent-RAM goal.
- A fixed-lookahead in-memory limiter as a supposedly exact substitute. Its proposed
  finite bound assumes an amplitude/reduction range the public buffer API does not
  enforce; disk-backed reverse recurrence preserves the current algorithm directly.
- A new typed non-I/O error solely for RIFF preflight. `io::ErrorKind::InvalidInput`
  correctly represents an invalid requested file, provided the CLI reports it as a
  render error rather than “error writing.”

Residual risks:

- Exactness costs repeated disk I/O on pathological high-crest material.
- A hard process termination can leave clearly named scratch orphans; automatic sweeping
  could delete another live process's files and is not included.
