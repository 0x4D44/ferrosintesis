## 2. The reopen tax — a bookkeeping defect, not a quality signal

**This section is the corrected version. My first draft claimed "five of six reopens were caused by
a sandbox that could not run cargo or python, and all five closed unchanged." A skeptic briefed to
refute it returned NARROWER TRUE CLAIM with four independent kills. The corrected finding is
smaller, sharper, and points at a one-line fix.**

Six bugs were reopened `Fixed → Open` this window. **Four are execution artefacts; two are
substantive.**

| Bug | Reopen | Verifier could not run | Closed unchanged? |
|---|---|---|---|
| 00150 | `7e1c2bd` | cargo denied | **yes** (`1f80bfe`, ledger-only) |
| 00152 | `2345960` | python denied (cargo ran: 788 passed) | **yes** (`1f80bfe`) |
| 00153 | `3e14945` | python denied (all 5 cargo steps green) | **yes** (`1f80bfe`) |
| 00151 | `2791854` | python **and** cargo denied | **no** — needed a 9-line test + a provenance fix (`cff3c70`) |
| **00016** | `e9cfdd9` | **nothing — ran the full suite** | **no** — real production fix `1e2029f` (+61 lines) |
| **00038** | `2564079` | nothing — needs an *ear* | **no** — still Blocked |

**The denial is real, not an agent's excuse.** The harness string is quoted verbatim in the ledger
(`bugs/MM-BUG-KILN-00151.md:84`): *"Permission to use Bash has been denied because Claude Code is
running in don't ask mode"*, with the denied commands listed. But it was **per-session and partial** —
three different denial shapes across four sessions — so "cargo and python were denied" is a false
generalisation.

**`00016` is the one that kills the simple story.** Its verifier ran `cargo test --workspace` to
completion (773 passed / 0 failed / 36 ignored) and raised a specific contract defect:
acceptance item 6 was unevidenced because *"the retained post-output click burst was never lesioned,
and the new identity oracle measures 6–30 ms, excluding the 0–3 ms window the burst occupies"*
(`bugs/MM-BUG-KILN-00016.md:89`). The follow-up fix reproduced the doubt **numerically** before
fixing it. That is a verifier doing exactly its job, and it must not be counted as tooling noise.

### The actual defect, and it is one line of the state machine

The pattern for the four blocked verifies is identical:

```
Fixed    (role=fix    model=codex@xhigh)
  -> Open    (role=verify model=claude verdict=doubt)      <- verifier could not EXECUTE
  -> Blocked (role=fix   model=codex@xhigh
              verdict=fix_failed reason=no_work)           <- re-fixer finds the fix already landed
```

`verdict=doubt` **reopens the bug and burns a fix attempt**. The re-dispatched fixer then correctly
reports `no_work`, which the machine scores as `fix_failed` and parks as `Blocked`. Three good,
landed fixes sat wrongly `Blocked` until a human-driven Codex session with execution permission
rescued them at 00:13 today.

**The schema already has the right path and it was never taken.** `bugs/README.md:46-49`:
*"`Verify retry after` temporarily parks indeterminate verification **without blocking future fix
attempts**."* All six reopened bugs carry `Verify retry after: -` and `indeterminate=0` while
carrying `doubt=1`.

**Cost, measured:** `Attempts: fix=3` on **five** bugs; **14** `record failed fix attempt` commits
against ~66 fix-shaped units — roughly a **21 % attempt-inflation tax**, paid entirely for a
booking decision. `00150` alone logged three `no_work` runs.

**Read for the plan:** the remedy is not more drain cycles and not a model change. It is (a) give the
verify runner execution permission, and (b) route a non-executable verify to `Verify retry after`
rather than to `Open`. Either alone helps; (b) is the durable one, because a verifier will always
sometimes be unable to run something.
