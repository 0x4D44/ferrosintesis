## 1. Scope and method

Assigned primary scope was exactly `crates/ferrosintesis-samples-bottle/` — a six-file
first-party asset crate that embeds one CC0 Freesound blown-bottle recording for GM 76.
It is small: 85 lines of `src/lib.rs`, one 145,574-byte WAV, and three documents.

Because the crate's whole contract is defined by its consumer, the review also read the
bottle-specific regions of `crates/ferrosintesis/src/sampler.rs` (the zone/loop machinery
at `:30-95`, the retired onset bank at `:2843-2860`, prewarm at `:3186-3210`, and the
active voice at `:4550-4820`), plus `licensing.rs`, `provenance.rs`, `gen_crate_lib.py`,
`bake_bottle_loop` in `prepare.py`, and the matching Python tests.

Four independent reviewers covered correctness/panic-safety, test-coverage/provenance,
performance/realtime, and devil's advocacy. The lead then re-read every cited path.
**Two reviewers were partly wrong and their claims were cut** — see §4. No reviewer was
skipped or rate-limited.

This pass did not run the application, generators, tests, builds, or renders. Where a
conclusion rests on reasoning rather than observation it says so.

## 2. What is in good shape

Worth recording, because three separate suspicions did not survive checking:

- **The realtime hot path is correctly engineered.** An independent recomputation of
  `find_bottle_loop`'s cost from its own constants (`sampler.rs:4599-4612`) gives 764 `ls`
  positions × 20 `k` values = 15,280 candidate pairs → **30,560 square roots and
  67,384,800 multiply-accumulates**. That matches the figure in the doc comment at
  `sampler.rs:44-46` exactly. The MM-BUG-KILN-00064 fix (ratio-check before search, memoize
  via `Zone::sustain_loop`, force at `prewarm()`) holds up: `sampler.rs:3204-3206` resolves
  the bottle's loop off the audio thread.
- **The upstream source hash really is verified in `cargo test`.**
  `provenance.rs:426` (`every_committed_source_is_pinned_by_a_packaged_document`) hand-rolls
  SHA-256, hashes every file under `tools/ferrosintesis-samples/*-src` — which includes
  `freesound-src/bottle_G3.wav` — and requires the digest to appear in a packaged
  `PROVENANCE.md`. Editing the hash text in `PROVENANCE.md`, or swapping the source file,
  fails `cargo test`. It even carries its own adversarial control
  (`the_coverage_check_rejects_an_unpinned_source`, `:450`) proving a gutted document fails.
- **The Python bake suite is gated, not decorative.** `.deltic-integrate.toml:59` and `:71`
  both run `python3 -m unittest discover -s tools/ferrosintesis-samples`, so
  `test_bottle_loop_reproduces_the_committed_asset` — which asserts equal length and ≤24 LSB
  drift against the committed bytes — runs on every integration touching `crates/` or `tools/`.
- **`BottleLoopVoice::render` is lean.** O(1) per sample, and the brightness filter is
  correctly gated behind `bright_active` rather than run unconditionally.
- **No unintended divergence from `SaxLoopVoice`.** `find_bottle_loop` and `find_sax_loop`
  are line-for-line identical apart from the window constants; the render wrap logic matches
  the sax's non-grain-motion branch. Grain motion is deliberately GM 67-only.

### Low — The shipped WAV's note label is a semitone wrong

- **Confidence:** High (settled by two independent controls in the same file)
- **Location:** `…\crates\ferrosintesis-samples-bottle\samples\bottleloop_G3.wav`, keyed at
  `…\crates\ferrosintesis\src\sampler.rs:4577`; repeated in `README.md:8`,
  `PROVENANCE.md:7,27` and `sampler.rs:4571-4572`
- **Problem:** the file is named `G3` but its measured root is **205.0 Hz**. Scientific G3 is
  196.00 Hz, so the label is 77.7 cents flat of the actual content; the nearest note is G#3
  (207.65 Hz, 22 cents away). Two controls in the same `sampler.rs` settle both halves:
  - `violin_G3_f.wav => 196.00` (`sampler.rs:368`), under the comment "Roots measured by
    autocorrelation in the prep script" — the repo labels 196.00 Hz as G3.
  - `pizzbass_G#3.wav => 205.95` (`sampler.rs:922`) — the repo labels ~205 Hz as G#3.
  So under the convention the file itself uses, 205.0 Hz is G#3.
- **Which half is wrong:** the label, not the measurement. `bottle_loop_pitch_integrity`
  (`sampler.rs:8304-8323`) renders keys 48/55/60/67, repitches by `target_hz / 205.0`, and
  asserts the Goertzel-located pitch within **±45 cents** of nominal. If the recording's true
  fundamental were 196.0 Hz, every key would land 77.7 cents flat and the test would fail.
  *(Inference, not observation: I did not execute the suite. It rests on trunk being gated
  green, which this repo's integration contract enforces.)*
- **Impact:** cosmetic but load-bearing for a human — the filename is a public `get()` key and
  a `bank!` key, and a maintainer reading it would reasonably assume 196 Hz.
- **Concrete fix:** rename the asset and both keys to `bottleloop_G#3.wav`, or — cheaper and
  non-breaking — leave the name and add an explicit "labelled G3, measured 205.0 Hz ≈ G#3"
  note to `PROVENANCE.md` and the `bank!` line. Renaming touches the packaged asset, the
  `bank!` key, `prepare.py:5115` (`BOTTLE_LOOP_OUT`) and the Python test's expectations.
- **Effort:** Small (note) / Medium (rename).

### Low — `with_sample_rate(0)` reaches a library panic through safe public API

- **Confidence:** High for the chain (every link read); **not executed**
- **Location:** `…\crates\ferrosintesis\src\engine.rs:1791` and
  `…\crates\ferrosintesis\src\live.rs:59`; panics at `…\src\sampler.rs:4752`
- **Problem:** both builders take a bare `u32` and store it with no validation and no
  documented precondition — the whole doc comment is "Set the output sample rate in Hz.
  Default 44100." With `sr = 0`, `base_step = ratio * 44100.0 / sr` (`sampler.rs:4697`) is
  `+∞` (IEEE-754, no trap). In `render`, `self.pos += eff_step` makes `pos` infinite, and the
  single-subtraction wrap `if self.pos >= self.loop_end as f32 { self.pos -= loop_len }`
  (`:4769-4771`) cannot recover (`∞ − finite = ∞`). On the next sample of the same block
  `let j = self.pos as usize` saturates to `usize::MAX` (Rust's float→int cast has saturated
  since 1.45) and `self.data[j]` (`:4752`) panics on a 72,765-element `Vec`. Block sizes are
  always > 1 (`LIVE_BLOCK = 64`), so the second sample is always reached.
- **Why it matters here:** `Options`/`RealtimeOptions` are deliberately *sealed* (private
  fields, builder-only) precisely so the library controls validity, and the error enums are
  `#[non_exhaustive]` so adding a variant is a minor bump. A panic is the one failure mode
  that design was meant to exclude. `RealtimeError` currently has only `OutputTooSmall`.
- **Not bottle-specific:** `SaxLoopVoice::new` (`sampler.rs:4294`) carries the identical
  formula. The right layer is the option builders, not the voice.
- **Concrete fix:** validate in `with_sample_rate` — clamp to a documented floor, or return a
  new `#[non_exhaustive]` error variant at the render entry point. **Constraint for the
  fixer:** `Options::sr` is `f32` on purpose (`engine.rs:1759-1767`) to keep renders
  byte-identical; a guard must not alter the arithmetic for valid rates.
- **Effort:** Small.

### Low–Medium — The realtime-safety oracle enumerates by naming convention

- **Confidence:** High (predicate read directly)
- **Location:** `…\crates\ferrosintesis\src\sampler.rs:6611-6616`
- **Problem:** `every_sustain_loop_search_is_memoized_and_prewarmed` is the oracle that
  guarantees no NoteOn pays a ~67M-MAC loop search inside the audio callback. It discovers
  what to check by text-scanning for `fn find_` … `_loop`:

  ```rust
  .filter_map(|l| l.trim().strip_prefix("fn find_"))
  .filter_map(|rest| rest.split('(').next())
  .filter(|name| name.ends_with("_loop"))
  ```

  A future loop search named anything else (`locate_plateau`, `plateau_window`) is invisible
  to all three of its assertions — including check (b), the prewarm coverage that is the
  actual realtime guarantee. The `assert!(declared.len() >= 2)` vacuity guard proves at least
  two were found, not that all were.
- **Why this is the repo's known defect class:** CLAUDE.md records that `pub fn *_bank` was
  holed for exactly this reason (MM-BUG-KILN-00073), and the sibling bank oracle was then
  hardened to scan `static … : OnceLock<`, which a rename cannot evade. The loop-search
  oracle never got the same treatment. The bottle is covered today only because
  `find_bottle_loop` happens to match.
- **Secondary:** `LOOP_SEARCHES.fetch_add` (`sampler.rs:4588`) is hand-copied into each
  finder body (`:4135`, `:5507`). Omit it in a new finder and the cost oracles silently
  report zero for that instrument.
- **Concrete fix:** derive the finder set from the `LoopFinder` type — scan for the fn-pointer
  signature or for `sustain_loop(` call sites — rather than the name; add the adversarial
  self-test (an off-pattern finder that *should* fail the scan, and does).
- **Effort:** Small–Medium.

## 6. Ready-to-file requirements (Draft) — BLOCKED on the same allocator

Durable debt, deliberately kept out of `bugs/`:

1. **Restore the generator's aggregate-byte pin to the four hand-written sample crates.**
   `gen_crate_lib.py:142,164-176` emits `EXPECTED_BYTES` plus a size assertion. Enumerating all
   25 sample crates rather than just the reported one — as CLAUDE.md's "enumerate all of L"
   rule requires — exactly four lack it: **bottle, musescore, orchestral2, strings**. The other
   three at least derive `FILE_COUNT = SAMPLES.len()`; bottle hardcodes `1`. Effort: Small.

2. **Give hand-edited sample crates a regeneration guard.** `gen_crate_lib.py:217-220` does an
   unconditional `open(out, "w")` overwrite with no merge and no diff check. Re-running it on
   bottle would silently delete the hand-written provenance paragraph (`lib.rs:3-7`) and the
   hand-added `embedded_names_are_unique` test, because the generator's `--doc` flag accepts
   only a single line. `regen_samples_table.py` already solves this for other crates with
   `BEGIN/END GENERATED SAMPLE INVENTORY` markers; bottle has none. Nothing currently detects
   that the committed file has *already* drifted. Effort: Small–Medium.

3. **Write down the bake-to-constants invariant for the bottle.**
   `find_bottle_loop`'s window is expressed in **absolute seconds** (`START_LO_S 0.45`,
   `START_HI_S 0.90`, `BODY_END_S 1.45`, `sampler.rs:4599-4603`) against a file that is exactly
   1.6500 s. These are a second, independent hand-derivation of facts already recorded in
   `prepare.py`'s bake recipe, in another language, in another crate, with no test connecting
   them. A shorter re-bake fails safe (the guard at `:4607` returns `None` and GM 76 falls back
   to the modeled Wind voice). The unsafe case is a re-bake that stays geometrically valid but
   shifts the swell/fade timing: the search still returns a seam, just possibly no longer "past
   the blow swell, into the settled body". Nowhere is it written that these five constants, the
   205.0 Hz root, and `BOTTLE_LOOP_GAIN = 0.65` must be re-derived together on any re-bake.
   Effort: Small (comment + PROVENANCE cross-reference) / Medium (derive the window from the
   recipe).
