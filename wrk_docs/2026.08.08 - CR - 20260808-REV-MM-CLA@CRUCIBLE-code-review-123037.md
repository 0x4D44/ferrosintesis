## 2. Confirmed defects

### CR-1 — Two dulcimer assets inject a NoteOn discontinuity

- **Severity:** Medium
- **Confidence:** High
- **Priority:** Should
- **Location:** `crates/ferrosintesis-samples-ccby/src/lib.rs:34,43`; assets `crates/ferrosintesis-samples-ccby/samples/dulcimer_D5.wav` and `dulcimer_F#4.wav`; render path `crates/ferrosintesis/src/sampler.rs:3817,3857-3961`; layer gain `crates/ferrosintesis/src/voices.rs:10193`
- **Problem:** The two WAVs begin at PCM values -1272 and +2120, respectively: 4.3% and 7.2% of each normalized peak. `LaVoice` starts at source position zero, gives the sample sole ownership before the crossfade, and reads frame zero directly. At velocity 127, the 0.45 dulcimer gain turns those values into approximately -35 dBFS and -31 dBFS instantaneous steps from silence.
- **Why this survived:** The current slope-bounded zero-frame micro-fade at `tools/ferrosintesis-samples/prepare.py:2111-2133` was added on 2026-08-01, but that fix regenerated only the six bass assets named by `MM-BUG-CRUCIBLE-00021`. This crate last changed on 2026-07-29.
- **Concrete fix:** Re-bake the dulcimer family with the current `trim_to_onset`, then add a derived opening-continuity oracle over every generated onset bank. It should reject a silence-to-first-frame step larger than ordinary early motion without erasing the attack.
- **Effort:** Small.
- **Ready bug title:** `Two dulcimer samples inject a NoteOn discontinuity`.
- **Proposed area:** `CC-BY dulcimer samples / onset de-click`.

### CR-2 — Every sampled Rhodes/dulcimer NoteOn allocates scratch storage in the realtime block

- **Severity:** Medium
- **Confidence:** High
- **Priority:** Should
- **Location:** `crates/ferrosintesis/src/sampler.rs:3831,3850-3967`; realtime call site `crates/ferrosintesis/src/live.rs:295-307`; GM 4 and GM 15 wrappers `crates/ferrosintesis/src/voices.rs:14436-14448,14688-14700`
- **Problem:** `LaVoice` is constructed with `buf: Vec::new()`. Its first `render()` calls `resize(out.len(), 0.0)`, so a fresh sampled NoteOn allocates a second heap buffer inside the deadline-bearing realtime block even after `prewarm_samples()` and `reserve_realtime_storage()` have run. The engine-owned boxed voice allocation is expected; this additional `Vec` growth is not reserved or reusable across voices.
- **Scale:** The realtime block is 64 frames, so each new sampled voice requests a 256-byte scratch allocation. A burst repeats the allocator call once per voice. After `fade_end`, the sample path is dead and model weight is exactly one, but every block still clears the scratch buffer, renders the model into it, and copies it into the caller's buffer for the rest of the note.
- **Concrete fix:** Keep crossfade scratch inline or chunked so construction needs no extra heap allocation, and delegate directly to `sustain.render(out)` after the sample handover. Add an allocation-count oracle for fresh GM 4 and GM 15 NoteOns after both realtime setup calls; allow only the engine-owned boxed-voice allocation.
- **Effort:** Medium.
- **Ready bug title:** `LaVoice allocates scratch storage inside realtime NoteOn rendering`.
- **Proposed area:** `ferrosintesis / realtime sampled voices`.

### CR-3 — Scoped Rhodes/dulcimer rebakes retain retired packaged WAVs

- **Severity:** Low
- **Confidence:** High
- **Priority:** Could
- **Location:** source inventory `tools/ferrosintesis-samples/prepare.py:1106-1110`; missing guards `:5421-5430`; selected source/write path `:5505,5629-5674`; re-embedding `tools/ferrosintesis-samples/gen_crate_lib.py:84-89`; insufficient scoped oracle `crates/ferrosintesis/src/inventory.rs:1017-1056`
- **Problem:** `FREESOUND_SOURCES` is derived from current files. `main()` validates Steinway, Kawai, Headroom, and bass outputs before writing, but not Rhodes or dulcimer. Removing or renaming a source therefore makes a selected rebake write the current set while leaving the old family-owned WAV in the shared CC-BY crate. `gen_crate_lib.py` then scans the destination and blesses the obsolete file in `SAMPLES`, `FILE_COUNT`, and the aggregate-byte canary.
- **Current state:** No stale file is present today. The failure is the shipped retirement/rebake path. This is a family-scoping residual of closed `MM-BUG-CRUCIBLE-00022`, whose fix covers only finger/pick bass.
- **Concrete fix:** Before any selected Freesound side effect, validate the combined expected Rhodes/dulcimer set for their shared output crate. Strengthen the Rust source oracle to bind each selected family and source table to its own guard. Add a temp-output negative control containing a retired `rhodes_old.wav` and prove failure occurs before fetch or write.
- **Effort:** Small-medium.
- **Ready bug title:** `CC-BY rebakes retain retired Rhodes and dulcimer WAVs`.
- **Proposed area:** `sample generation / CC-BY output inventory`.

## 3. Confirmed prevention debt

These are not current bad outputs, so they belong in Draft requirements rather than the bug queue.

### RD-1 — Attribution coverage is crate-wide, not work-complete

- **Confidence:** High
- **Location:** the two current credit blocks at `crates/ferrosintesis-samples-ccby/NOTICE:8-12`; token extraction `crates/ferrosintesis/src/licensing.rs:466-514`; parent checks `:638-650,740-746`; crate check `:774-804`
- **Gap:** The oracles require any one distinctive title/source token and any one licensor-owned signal per crate. Deleting the dulcimer block while retaining the Rhodes title, author, URL, and licence still satisfies those predicates, but the published crate then omits iternetcone's required credit.
- **Required behavior:** Every independently licensed work/family in an attribution-bearing sample crate must carry its own author, work, source, and licence through the crate notice and consolidated parent surfaces. Derive the obligations from canonical provenance and add a negative fixture that keeps Rhodes while deleting dulcimer.
- **Proposed requirement:** Could / light; `Every CC-BY work must retain complete attribution independently`.

### RD-2 — Source hashes are not bound to the owning packaged provenance

- **Confidence:** High
- **Location:** provenance concatenation `crates/ferrosintesis/src/provenance.rs:381-412`; global substring predicate `:415-440`
- **Gap:** The oracle concatenates every sample crate's `PROVENANCE.md`, then checks whether each committed-source hash occurs anywhere. Moving a CC-BY source hash into an unrelated sibling crate remains green even though the diagnostic says to put it in the owning crate.
- **Required behavior:** Every committed source hash must occur in the `PROVENANCE.md` packaged by its owning sample crate. Preserve owner identity during enumeration and add a sibling-hash-laundering negative control.
- **Proposed requirement:** Could / light; `Bind every committed source hash to its owning sample crate`.

## 4. Report-only hardening

- `crates/ferrosintesis/src/sampler.rs:55-81` trusts the embedded RIFF parser's inputs: it indexes short `fmt ` bodies, clamps oversized chunks, ignores the declared RIFF end and PCM format code, and drops an odd data byte. Current assets are valid and compile-time trusted, so this is Low prevention debt, not a current runtime incident. A strict fallible chunk walker would fail earlier and explain the asset error.
- `crates/ferrosintesis-samples-ccby/src/lib.rs:101-134` still binds filenames only to aggregate bytes and RIFF/WAVE magic. Nineteen files share the same size, so an equal-size payload swap stays green. This is the already-recorded generated-family gap from the 2026-07-24 CR; no duplicate ledger record was proposed.
- Package names, consumer zone literals, and provenance rows currently agree, but no exact set-parity oracle binds all three. A source-derived equality check would catch a newly packaged but unused zone. This remains report-only because current sets match.
