## 2. Confirmed defects

### CR-1 — The mandatory gate can accept fret-noise WAVs that violate `BAKE-SHA256`

- **Severity:** Low
- **Confidence:** High
- **Priority:** Could
- **Location:** `crates/ferrosintesis-samples-fretnoise/src/lib.rs:187-220`; `tools/ferrosintesis-samples/test_fretnoise_bake.py:18-24,70-112`; `.deltic-integrate.toml:50-52,59,71`; `crates/ferrosintesis-samples-fretnoise/BAKE-SHA256:1-12`
- **Problem:** The Rust test named `embedded_bytes_match_the_committed_files` compares only byte lengths. The aggregate canary and RIFF/WAVE checks also accept a different same-length payload. Exact committed-file hashing exists only in a Python module that skips wholesale when NumPy is absent, and its real-bank check skips unless the exact canonical Windows/Python/NumPy bake environment is present. The mandatory integration gate explicitly accepts those skips. A changed same-length WAV can therefore disagree with its packaged SHA-256 pin while every required check stays green.
- **Existing-ledger check:** Closed `MM-BUG-KILN-00095` added the pins and canonical re-bake verifier, but it did not make committed-output authentication environment-independent. Implemented `MM-REQ-KILN-00031` cites the length-only Rust test as byte-identity evidence. Neither record covers this residual gate path.
- **Concrete fix:** Add a stdlib-only test that strictly parses `BAKE-SHA256`, requires exact filename-set equality, and hashes every committed WAV. Keep canonical NumPy re-baking as the stronger optional test. Add a same-length payload mutation negative control. The Rust test may also compare full on-disk bytes to each labelled `include_bytes!` row, but that does not replace pin verification because both copies can change together.
- **Effort:** Small.
- **Ready bug title:** `Mandatory gate can accept fret-noise WAVs that violate BAKE-SHA256`.
- **Proposed area:** `fret-noise sample integrity gate`.

## 3. Confirmed prevention debt

### RD-1 — The cited shared refresher cannot refresh this crate's inventory shape

- **Confidence:** High
- **Location:** `crates/ferrosintesis-samples-fretnoise/src/lib.rs:18-72`; `tools/ferrosintesis-samples/regen_samples_table.py:21-25,136-146`; `reqs/MM-REQ-KILN-00031.md:73-87`
- **Gap:** The refresher accepts only a fixed array declared with `FILE_COUNT` and a numeric `FILE_COUNT` literal. Fret-noise uses a slice plus `FILE_COUNT = SAMPLES.len()`, so the refresher exits with `no SAMPLES array in the expected shape`. The implemented requirement says this tool already refreshes hand-written crate inventories and uses that claim to reject a fret-noise generator mode. The current drift tests prevent a stale table from landing, but adding or retiring a take still needs an undocumented manual Rust edit.
- **Required behavior:** Teach the refresher to preserve the slice/derived-count shape and add a fret-noise-shaped fixture, or document and guard a different complete refresh path. Correct `MM-REQ-KILN-00031`'s resolution evidence when that work lands.
- **Effort:** Small–Medium.
- **Ledger routing:** Report-only here. `MM-REQ-KILN-00031` already owns the desired inventory-source-of-truth outcome, so minting another requirement would duplicate it.
