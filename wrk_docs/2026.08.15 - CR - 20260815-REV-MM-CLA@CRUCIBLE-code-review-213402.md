`packaged_family_counts` (`…\inventory.rs:648`) keys families on the filename prefix

`trombone`, `trumpet`, `tuba`, `vlnens`. So all three completeness checks — manifest

Every other branch of `public_inventory_surface_errors` is also inert here:

So `every_public_sample_inventory_surface_is_complete_or_delegated` asserts **nothing**

**Two-sided proof it is a real hole, not a design choice that happens to be safe.** The

**(c) The crate description omits 27 of 158 files.** `Cargo.toml:6` reads
`description = "Embedded CC0 string, brass, reed, and guitar samples for ferrosintesis"`.
The 10 `harpsi_*` (harpsichord, GM 6) and 17 bagpipe files (`drone_*`, `chanter_*`, GM

**(d) The onset/crossfade claim is wrong for the bagpipe.** `README.md:15-18` says

**(e) The module docs repeat the same wrong claim.** `src/lib.rs:1` reads "Embedded CC0

### 3. Medium — `PROVENANCE.md`'s guard promise is false twice, and the guard reads 2 of 5 columns

- **Confidence:** High
- **Locations:**
  `…\crates\ferrosintesis-samples-orchestral\PROVENANCE.md:3-5`;
  `…\crates\ferrosintesis\src\inventory.rs:667-698` (the parser),
  `:1116-1142` (the only live test),
  `…\crates\ferrosintesis\src\lib.rs:98-116` and `…\.cargo\config.toml:5-6` (the cfg gate)
- **Tracking:** unfiled — see blocker

`PROVENANCE.md:3-5` tells the reader: *"Machine-checked by
`crates/ferrosintesis/src/inventory.rs`: a family that ships without a row here fails the
build."* Both halves overstate what is enforced.

**(a) It is not a build check, and it is conditional.** `inventory` — with `licensing`,
`manifest`, `payload`, `provenance`, `render_profile` and `balance` — is
`#[cfg(all(test, ferrosintesis_repository_tests))]` (`…\crates\ferrosintesis\src\lib.rs:98`).
The cfg comes solely from `[build] rustflags` in `…\.cargo\config.toml:6`. Cargo's
documented precedence is that the `RUSTFLAGS` environment variable **replaces**
`build.rustflags` rather than merging, so a run that sets `RUSTFLAGS` for any unrelated
reason drops all seven oracle modules — the suite goes green with fewer tests and no
diagnostic. Nothing asserts the gate is live. *This gate is outside the assigned area and
is already recorded, unfiled, in two DAILY reports
(`…\wrk_docs\2026.07.30 - DAILY - KILN-Windows - Repo state report.md:858` and
`…\wrk_docs\2026.08.01 - DAILY - KILN-Windows - Repo state report.md:420`); it is cited
here only because this crate's shipped documentation asserts the guarantee it removes.*

**(b) The row check reads only the family pattern and the count.**
`provenance_family_rows` (`…\inventory.rs:667-698`) parses cell 0 and cell 1 and never
inspects cells 2–4 (Instrument, Source, Licence). Replace `PROVENANCE.md:10-31` with a
bare two-column table of 15 correct counts and the suite stays green — deleting the VSCO
commit `4403009…`, both FreePats SHA-256s, and the Discord-SFZ rev `05d5ed8…` that
`README.md:66-68` calls *"load-bearing, not a convenience"* because that repository is a
mixed CC0/CC-BY aggregation with no repo-level LICENSE. Finding 2(f) is this hole firing:
a wrong Instrument cell is unreadable to the oracle.

`licensing.rs` does not backstop it — `crate_requires_attribution`
(`…\crates\ferrosintesis\src\licensing.rs:174-188`) returns false for a CC0-only
declaration, so this crate is skipped by every licensing oracle by design.

This is MM-BUG-KILN-00071's shape ("mentioned is not credited") reproduced inside the
module that cites MM-BUG-KILN-00069.

- **Concrete fix:** (i) correct `PROVENANCE.md:3-5` to "fails the repository test suite";
  (ii) require each provenance row's Source cell to be non-empty and to carry a pin token
  (a 40-hex rev, a 64-hex SHA-256, or a dated archive name), and write the gutted
  two-column fixture that must fail. The cfg-gate sentinel is the separate, already-known
  item.
- **Effort:** Small for (i)+(ii), ~1–2 h with the adversarial fixture.

### 4. Low — the crate's WAV test admits an empty, silent, or truncated file

- **Confidence:** High on the predicate gaps; the impact is bounded by a runtime check
  elsewhere (see below)
- **Location:** `…\crates\ferrosintesis-samples-orchestral\src\lib.rs:535-548`
- **Tracking:** unfiled — see blocker

`every_sample_is_a_nonempty_wav_with_the_expected_aggregate_size` checks `len() >= 12`,
the `RIFF` and `WAVE` signatures, and one aggregate byte total. Defects it admits:

- **A 12-byte header-only file.** The literal `RIFF\0\0\0\0WAVE` passes a test whose name
  promises "nonempty".
- **An all-silent file.** No amplitude, RMS, or non-zero-sample check exists anywhere in
  the crate.
- **A truncated `data` chunk** whose declared length exceeds the bytes present —
  `parse_wav` clamps with `.min(bytes.len())` (`…\crates\ferrosintesis\src\sampler.rs:63`)
  and renders the short buffer silently.
- **Any of those, if another file's length changes to offset it.** `EXPECTED_BYTES`
  (`src/lib.rs:517`) is one sum across 158 files; it cannot localize, and offsetting edits
  cancel.

`EXPECTED_BYTES` also has weak provenance: `…\tools\ferrosintesis-samples\gen_crate_lib.py:102`
computes it from the same `os.listdir` that emits the `SAMPLES` table, and the generator's
own docstring says the tests are "self-consistent by construction". Its genuine, narrow
power is catching a WAV edited on disk *without* re-running the generator. It is no
independent evidence of what the bank should hold.

- **Bounded by:** the README's mono/16-bit/44.1 kHz promise **is** enforced, transitively
  — `parse_wav` asserts it (`sampler.rs:68-71`), and this pass confirmed all 158 files are
  reachable from a `bank!` table that `prewarm()` initializes. So a stereo or 48 kHz
  re-bake fails the ordinary test suite today. That protection is a consequence of full
  reachability, not a packaging-time property: a future packaged-but-unread WAV would
  bypass it entirely, which is exactly what the retired `drum_*` overlays did for months
  (`PROVENANCE.md:33-47`).
- **Concrete fix:** have `gen_crate_lib.py` emit a per-file `(name, bytes, channels, rate,
  bits, peak)` table and assert it in the generated test — per-file localization, format
  checked at packaging time rather than by a renderer panic, and silence caught. Keep the
  aggregate as a cheap cross-check.
- **Effort:** Small, ~2 h including the generator change.

## Ledger-filing blocker

**No bug or requirement record was created, and the findings above have not entered the
Open queue.**

`deltic bugs new` and `deltic reqs new` are the only sanctioned ID allocators — they see
the single per-host number space that `bugs/`, `reqs/` and `issues/` share across every
worktree on this box. Both need a shell, and every shell call in this session is refused:

```
Permission to use PowerShell has been denied because Claude Code is running in don't ask mode.
```

The Bash tool returns the identical refusal. A subagent was dispatched specifically to test
whether the denial was session-wide; it hit the same wall on both tools. `deltic` itself
never executed — there is no exit code or partial state to inspect.

Hand-deriving `max+1` over `bugs/` was considered and **rejected**: the number space is
shared with `reqs/` and `issues/` and is allocated per host, not per worktree, so a
hand-picked number can collide with a sibling worktree's concurrent allocation — and
because the two records land at different paths, git merges both halves without a
conflict. That is the exact failure the "never hand-derive a number" rule exists to
prevent.

Each finding above therefore carries its full observation, evidence, impact, concrete fix,
and effort, so a follow-up pass with shell access can mint the records directly from this
document. **Finding 2 has now been reported twice and filed zero times** — the 2026-07-27
pass hit the same class of blocker (write denial under `bugs/`, recorded at
`…\wrk_docs\2026.07.27 - CR - 20260727-REV-CLA@KILN-code-review-074202.md:180`). Two
review passes have now spent effort on a defect that is still not in the queue the fix
loop drains.
