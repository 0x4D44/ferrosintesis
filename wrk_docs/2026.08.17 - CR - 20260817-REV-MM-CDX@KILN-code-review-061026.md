## Confirmed findings

### CR-1 — concurrent B1 rebakes share mutable decode and slice intermediates

- **Severity:** Low
- **Confidence:** High
- **Where:** `D:\worktrees\ferrosintesis\20260817-REV-MM-CDX@KILN-code-review-061026\tools\ferrosintesis-samples\prepare.py:4848`; `D:\worktrees\ferrosintesis\20260817-REV-MM-CDX@KILN-code-review-061026\tools\ferrosintesis-samples\prepare.py:5723`
- **Tracking:** `MM-BUG-KILN-00266` (new, Open)
- **Problem:** every worktree selects the host-global `%TEMP%\b1_upright` directory.
  The decode and slice path then rewrites fixed take WAVs, the fixed `slices/`
  directory, and fixed manifest names without a lock or per-run isolation. The slicer
  is explicitly passed `--no-hash`.
- **Impact:** two concurrent documented B1 regenerations can read while the peer
  truncates or replaces an intermediate. A run can fail spuriously, or—across
  different worktree revisions—consume a peer's complete decoded take, slice, or
  manifest and publish a structurally valid bank from the wrong source revision.
  Current inventory and RIFF/tail checks authenticate shape, not intermediate origin.
- **Concrete fix:** allocate a process-unique decode/slice directory for each B1
  invocation and remove it in `finally`. Alternatively, lock and authenticate an
  immutable cache. Add a two-process overlap regression covering decode, slicing, and
  manifest reads.
- **Effort:** Small–Medium.
