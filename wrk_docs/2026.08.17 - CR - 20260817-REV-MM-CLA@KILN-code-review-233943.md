## Summary

Eight confirmed findings, seven filed as bugs and one as a Draft requirement. The crate's
core is in good shape: the alias-safety work from MM-BUG-KILN-00097/00120 is sound, the WAV
decoder in `examples/support/wav.rs` is carefully bounds-checked, packaging is self-contained,
and `render_profile.rs` already stops the CLI restating library defaults.

Two themes run through what remains.

**The CLI does not report what it actually did.** It prints an echo time the render did not
use, silently clamps four other knobs, drops file paths from its own error messages, and — on
Windows — aborts renders the synthesizer could have performed.

**The checks around the CLI do not reach it.** The oracle meant to keep its help text honest
never reads the help text. The licensing oracles' enumeration predicate cannot see the crate
that actually ships the executable, which has no `NOTICE`. And the integration gate runs
neither the crate's example tests nor the `--no-default-features` build its own README
advertises, which leaves its single unit test asserting `true == true`.

## 1. Windows identity probe's exclusive input open aborts a render whenever any process is reading the MIDI

- **Severity:** Medium · **Confidence:** high on the code path and the Windows rule;
  the runtime failure was **not** reproduced (this pass does not run the app)
- **Where:** `D:\worktrees\ferrosintesis\20260817-REV-MM-CLA@KILN-code-review-233943\crates\ferrosintesis-cli\src\output.rs:60`
- **Effort:** ~1–2 h including the regression

`platform_same_file` holds the input with `OpenOptions::new().read(true).share_mode(0)`.
Windows sharing is bidirectional: `dwShareMode = 0` denies every access mode, so
`CreateFile` fails with `ERROR_SHARING_VIOLATION` if **any** existing handle holds access
that share mode denies — an ordinary `FILE_SHARE_READ` holder is enough. The `?` propagates,
`reject_input_alias` returns `Err`, and `main.rs:112-115` exits 1 before `offline::load` is
reached.

The render would otherwise have succeeded: the library opens the MIDI with a plain
`std::fs::File::open` (`crates\ferrosintesis\src\midi.rs:251`), whose default share mode
tolerates a read-sharing third party.

This is the **residual of MM-BUG-KILN-00120, not a duplicate**. That bug fixed the *output*
probe and closed on the reasoning that the blast radius was narrow because "ordinary players
and editors share read" (`bugs\MM-BUG-KILN-00120.md:102-106`). That reasoning inverts on the
input side — read sharing is precisely what collides with `share_mode(0)`. The author
reasoned about third-party interference for the output (`output.rs:56-59`) and guarded it
with drop-and-retry; the symmetric input case is unguarded.

Reachability is the common case: `output.rs:28-32` returns early only when the output is
`NotFound`, so the exclusive open runs on every ordinary Windows re-render.

**Test gap.** `share_mode` appears exactly once in the crate's tests —
`crates\ferrosintesis-cli\tests\output_safety.rs:130`, holding the **output**. Nothing holds
the input.

**Fix:** pre-filter on `std::os::windows::fs::MetadataExt` (`file_size`, `creation_time`,
`last_write_time`, `file_attributes` — all stable; hard links share all of them) so the
probe stops running on the common path, and treat a sharing violation on the guard open as
*inconclusive* rather than fatal. Full detail in the bug.

## 2. The CLI prints and silently accepts option values the render did not use

- **Severity:** Medium · **Confidence:** confirmed by source
- **Where:** `…\crates\ferrosintesis-cli\src\main.rs:125-128`, `:141`, `:146-152`
- **Effort:** ~2 h with regressions

`--delay 60000` prints `echo 60000 ms` and renders **10000 ms**: `delay_s` is printed at
`main.rs:141` before `with_echo` clamps it at `main.rs:150`. The default branch
(`main.rs:127`) pre-clamps to 0.20–0.62, so only *user-supplied* values diverge — exactly
where the number needs to be right.

The other four knobs are clamped in total silence. `--rate 500000` → 384000, `--wet 5` →
1.0, `--tail 99999` → 3600, `--wet nan` → 0.32 (both `"nan"` and `"inf"` parse as `f32`, and
`sanitize_knob` substitutes the default for non-finite input). The clamps live at
`engine.rs:1838-1841`, `1845-1848`, `1853-1856`, `1869-1872`, all via `sanitize_knob`
(`engine.rs:1766-1772`).

The library states plainly that reporting is the caller's job — `engine.rs:1760-1761`: *"The
accessors report the clamped value, so a caller that cares can see what it actually got."*
The CLI never calls `opt.sample_rate()`, `opt.reverb()`, `opt.tail()` or `opt.echo()`.

**Fix:** move the verbose header after `opt` is built and print `opt.echo()`; warn once per
knob whose accessor disagrees with the request.

## 3. `--help` to stderr with exit 2; no `--version`; unknown flags become the input path

- **Severity:** Low · **Confidence:** confirmed by source
- **Where:** `…\crates\ferrosintesis-cli\src\main.rs:20-25`, `:104`, `:105-106`
- **Effort:** ~1–2 h

One root cause: the arg loop has no notion of an unknown flag, and `usage()` does double duty
as help output and error output.

- `usage()` is `eprintln!` + `exit(2)`, and `-h`/`--help` calls it. `ferrosintesis --help`
  writes zero bytes to stdout and returns failure — `--help | less` and any exit-status probe
  break.
- No `--version`/`-V` arm exists and `CARGO_PKG_VERSION` is never referenced in the crate
  (verified by grep). `--version` becomes the *input path* and dies with a bare
  `os error 2`.
- `main.rs:105` has no leading-`-` guard, so the first unrecognised token becomes the
  filename. The same unknown flag placed *after* the input is correctly rejected — whether
  the CLI notices a typo depends purely on argument order.

This matters more than it would in an internal tool: `ferrosintesis-cli` is published on
crates.io and is the only installable entry point (`cargo install ferrosintesis` installs
nothing).

## 4. Pre-load I/O errors drop the file path the library deliberately preserves

- **Severity:** Low · **Confidence:** confirmed by source
- **Where:** `…\crates\ferrosintesis-cli\src\main.rs:112-115`, `…\src\output.rs:27`
- **Effort:** ~30 min

`reject_input_alias` runs before `offline::load` and canonicalizes first, so a missing input
dies inside the alias check and is printed as a bare `io::Error`. The library goes out of its
way to carry the path — `midi.rs:247-251` wraps it in `MidiError::Io { path, source }`,
`error.rs:108` formats `"{path}: {source}"`, and `error.rs:172` asserts `"song.mid: no such
file"` under the comment *"Display keeps the path, which is what the CLI prints."* That
comment has been false for every pre-load I/O failure since the alias check was inserted
ahead of `load`.

It costs something where the message is the only evidence: a shell loop over many albums
reports `os error 2` naming no track, and finding 1's `os error 32` never says which of the
two files is locked.

## 5. `the_cli_help_text_states_the_real_defaults` proves neither half of its name

- **Severity:** Low · **Confidence:** confirmed by tracing the oracle over a counterexample
- **Where:** `…\crates\ferrosintesis\src\render_profile.rs:379-405`
- **Effort:** ~1 h

Two independent holes.

*No value is bound to its flag.* Lines 383-387 flatten every `//!` line plus every line
containing `usage:` into one blob; lines 393-397 then ask only whether *some* token anywhere
in that blob parses to the wanted value. `flag` is used solely in the panic message. So this
adversarial doc-comment — every default against the wrong flag — passes all three assertions:

```
//!     ferrosintesis input.mid [-o out.wav] [--rate 0.32] [--wet 44100]
//!                 [--delay MS] [--tail 6] [--solo CH[,CH...]] [-q]
```

Traced: `split_whitespace` → `0.32]`, `44100]`, `6]`; the `trim_matches` closure at line 394
keeps alphanumerics, `.` and `-` → `0.32`, `44100`, `6`; `num` parses all three; the `--rate`
iteration wants 44100 and finds it in the `--wet` slot, and vice-versa. A doc naming no flags
at all (`//! Released 2026; 44100 lines, 0.32 s, 6 movements`) also passes.

*It does not read the help text.* `--help` prints only `usage()` (`main.rs:20-25`), whose
text is `[--rate N] [--wet X] [--tail S]` — it states **no** defaults for those three flags.
The oracle is satisfied entirely by the crate-level `//!` comment, which no user ever sees.

The correct shape sits 40 lines above it: `the_readme_options_table_states_the_real_defaults`
(`render_profile.rs:328-377`) locates the row starting `` | `{builder}` `` and reads cell 3 —
value bound to key.

This is the exact failure mode CLAUDE.md names after KILN-00071/00072/00073: *"write the
adversarial document that should fail your oracle, and check that it does."* It was never
done for this one. Not a present mismatch — the CLI's current doc-comment is correct — so
this is drift risk plus a mis-scoped subject.

## 6. The published CLI package carries no `NOTICE`, and no oracle can see that

- **Severity:** Medium · **Confidence:** confirmed by source and directory listing
- **Where:** `…\crates\ferrosintesis-cli\Cargo.toml:14`; `…\crates\ferrosintesis\src\licensing.rs:55-86`
- **Effort:** a human decision, then ~2 h

`crates/ferrosintesis-cli/` has no `NOTICE` file and packages none. Its `README.md:60-61`
points at "the library's `NOTICE`" — a different package. `crates/ferrosintesis/` does hold
and package one (`Cargo.toml:13`), but that crate has no `[[bin]]`;
**`ferrosintesis-cli` is the crate that produces the executable**, with every
attribution-bearing sample bank linked in by default.

No oracle asks. `licensing.rs` derives its set from `default_sample_crates()`
(`licensing.rs:55-86`), which parses the `embedded-samples` feature list, then requires
documents from each bank plus `ferrosintesis/NOTICE` and `ferrosintesis/README.md`
(`:322-337`, `:432-444`). `ferrosintesis-cli` is neither a bank nor the parent, so it is
structurally unreachable. The predicate is right for "which banks need crediting" and wrong
for "which published packages ship the credited material" — CLAUDE.md's KILN-00071/72/73
lesson, one level up.

**This needs Arthur's call before a patch.** Whether attribution must travel inside the CLI
package, versus being satisfied at build time when cargo has already fetched all 24 asset
crates, is a licensing judgement — the obligation attaches to whoever redistributes the built
binary, not to `cargo install`. The bug says so explicitly so no autonomous fix pass invents
an answer.

## 7. The gate runs neither the example tests nor the CLI's advertised feature build

- **Severity:** Medium · **Confidence:** measured (test counts), read (gate commands)
- **Where:** `…\.deltic-integrate.toml:58`, `:70`, `:56-57`, `:68-69`;
  `…\crates\ferrosintesis-cli\src\main.rs:191-200`
- **Effort:** ~1 h plus a runtime measurement

`cargo test -p ferrosintesis-cli` runs 16 tests; `--all-targets` runs **21**. The five extra
are the `#[cfg(test)]` block in `examples/calmeter.rs:212-254`. The gate
(`.deltic-integrate.toml:58`, `:70`) is `cargo test --workspace --locked` — no
`--all-targets` — so those five never run, and `calmeter.rs:120`'s "Pure — unit-tested below"
is false where it counts. Clippy *does* pass `--all-targets` (`:55`, `:67`), so the example
binaries still compile; whether clippy also type-checks the `#[cfg(test)]` module was **not**
measured.

Separately, `main.rs:191-200` asserts `ferrosintesis::embedded_samples_available() ==
cfg!(feature = "embedded-samples")`, and the library side is the same `cfg!` on the same
feature (`lib.rs:88`). Under every gated command both are `true` — `assert_eq!(true, true)`.
The gate runs `--no-default-features` for `-p ferrosintesis` only (`:56-57`, `:68-69`), never
for the CLI, though `README.md:52` advertises
`cargo install ferrosintesis-cli --no-default-features` as a shipped configuration.

Watch out when fixing: `crates/render-catalog/Cargo.toml:15` takes `ferrosintesis` with
default features on, so a workspace-wide `--no-default-features` run can unify
`embedded-samples` back on in the library while the CLI's `cfg!` stays false — use
`-p ferrosintesis-cli`, not a workspace flag.

## 8. WAV-decoder test debt

- **Severity:** Low · **Confidence:** confirmed by re-deriving the header offsets and byte
  counts by hand
- **Where:** `…\crates\ferrosintesis-cli\tests\wav_reader.rs:7-9`, `:88-92`, `:104-108`;
  `…\examples\support\wav.rs:132-138`; `…\examples\calmeter.rs:181-183`
- **Effort:** ~2 h

`tests/wav_reader.rs:7-9` derives each fixture's `byte_rate` with the same formula
`decode_wav` validates against (`support/wav.rs:132-133`), so that assertion can only agree
with itself — the shape CLAUDE.md names verbatim. The one test that corrupts a header field
overwrites bytes `32..34`, which is `block_align`, so the alignment check at `:126` returns
first and the byte-rate branch is never reached.

`rejects_missing_or_truncated_format_and_missing_data` (`:88-92`) builds a 24-byte fixture
declaring a RIFF size of 24, so `riff_end = 32 > 24` and it trips **"truncated RIFF body"**
(`support/wav.rs:35-39`), not the truncated-`fmt` branch its name implies (`:66-71`, still
uncovered). The assertion is only `.contains("truncated")`, which matches five different
messages — the mis-aim is invisible.

`calmeter.rs:181-183` builds its temp path from `process::id()` and a nanosecond nonce with
no discriminating label, unlike every sibling helper in the crate, so its two `read_wav_*`
tests race for one filename. Latent only because those tests never run — fixing finding 7 is
what makes this bite, so land the two together.

## Reported but not filed as bugs

**`raw_dump::write_f32_wav` narrows the RIFF sizes with an unchecked `as u32`.**
`…\crates\ferrosintesis-cli\examples\raw_dump.rs:24` computes
`(interleaved_stereo.len() * 4) as u32` and writes `36 + data_bytes` at line 27 and
`data_bytes` at line 38, while the sample loop at lines 39-41 writes every sample regardless.
Past 1,073,741,823 f32 values (536,870,911 stereo frames ≈ 3.38 h at 44.1 kHz) both declared
sizes are silently wrong and the file is longer than it claims. This repo's own decoder errors
only when `riff_end > bytes.len()`, never when it is smaller
(`examples\support\wav.rs:30-39`), so the result is a silent short read. **Not filed:**
`raw_dump` is dev-only calibration tooling run on short probes, and reaching the threshold
means holding 4.3 GB of `f32` in RAM first — real, but not reachable in practice. Worth a
`try_into` if anyone is in the file.

**`examples/support/wav.rs` rejects `WAVE_FORMAT_EXTENSIBLE` (tag 0xFFFE).** Lines 94-103
match only `(1, 16)` and `(3, 32)`; the `SubFormat` GUID that would identify an extensible
chunk as IEEE float is never inspected. **Not filed:** the failure is loud and precise, only
`calmeter` is affected (`measure_wav` passes `require_pcm16_stereo = true` and rejects all
float by design), and the in-repo producer of calmeter's input writes plain tag 3
(`raw_dump.rs:31`). A format gap in a dev-only reader, not a correctness defect.

**`main.rs` has one test and it is about a feature flag.** Test counts across the crate:
`tests\wav_reader.rs` 7, `examples\calmeter.rs` 5, `tests\output_safety.rs` 4,
`src\output.rs` 4, `src\main.rs` 1. Nothing exercises argument parsing — not `--solo`, not
`--rate`, not `--help`, not an unknown flag. **Not filed separately:** each bug above
prescribes the regression its own fix needs, which is the cheaper route to the same coverage.

**Nothing exercises the verbose path.** Every test in `tests\output_safety.rs` passes `-q`
(lines 48, 94, 139). So `main.rs:129-143`, the progress closure at `:160-167` — the only call
to `render_to_wav_with_progress` anywhere — the `song.title().is_empty()` branch, and the
`fs::metadata(&output)…unwrap_or(0)` at `:176-178` all have zero coverage. **Not filed
separately:** MM-BUG-KILN-00296's fix lands directly in that block and must bring a test with
it, which closes most of this.

**The `#[cfg(not(any(unix, windows)))]` arm silently disables the protection the module
exists for.** `src\output.rs:74-77` returns `Ok(false)`, so on such a
platform a hard-linked output would destroy the source MIDI — exactly what
`reject_input_alias` was written to prevent. The degradation is narrow (canonicalize still
catches symlink and `..` aliases) and no such target is built here. Note also that
`rejects_supported_symbolic_link_alias` (`output.rs:140-159`) has no `#[cfg]` arm for that
platform: neither block creates the link, so `expect_err` at `:157` would panic there.
**Not filed:** unreachable on every platform the workspace targets.

**The anti-restatement oracle is narrower than it reads.** `render_profile.rs:211` checks
only `with_sample_rate`, `with_reverb`, `with_tail`, `with_solo` — not `with_echo` or
`with_samples` — and does not look at the normalization literals at all. Its detector is
`num(arg).is_none()`, so `.with_tail(TAIL_DEFAULT)` via a local const passes cleanly, as does
`.with_reverb(0.32 /* default */)` (the trailing `/` defeats the
`trim_end_matches(is_ascii_alphabetic)` at `:74`). Related nit: `Normalization::peak(0.891)`
at `main.rs:154` is a bare magic literal stated nowhere else in the repo — it is
10^(−1/20), so `README.md:39`'s "−1 dBFS" is really −1.0009 dB. **Not filed:** the values are
currently correct and MM-BUG-KILN-00295 already covers the oracle module; worth folding in
when someone is in that file.

## Not reported (refuted during verification)

- **Scratch files could clobber an unrelated file beside the output.** REFUTED.
  `TempFile::reserve` opens with `.create_new(true)` (`…\crates\ferrosintesis\src\scratch.rs:463`),
  which never opens or truncates an existing file; on `AlreadyExists` it bumps the sequence
  (`:467`) and after 100 collisions errors rather than reusing a name (`:471-477`). Names are
  already collision-resistant (`.{output}.{pid}.{seq}.{role}.tmp`, `:456-459`). The only
  residue is litter: a kill mid-render skips `Drop` (`:485-489`) and leaves a dot-prefixed
  `.tmp` beside the output.
- **`--peak-normalize` silently ignoring `--lufs` / `--tp-ceiling`.** REFUTED as a defect.
  The mechanic is real (`main.rs:153-157`) but the precedence is documented in both
  user-facing surfaces — `usage()` at `main.rs:22` and `README.md:39`, repeated at
  `README.md:42-43` — and mode-override is ordinary CLI behaviour. One residual noted, not
  filed: under `--peak-normalize` an out-of-range `--lufs 50` never reaches
  `validate_normalization` (`scratch.rs:88-112`), so the same typo errors in the default mode
  and is accepted in peak mode.
- **Arithmetic or slice bug in `calmeter`'s `measure()` / onset computation.** REFUTED.
  `onset - onset % chunk` is u64 minus its own remainder (cannot underflow); `chunk` is only
  ever 1, 64 or 512 (`calmeter.rs:82-92`); the early return at `:138` guarantees
  `slice_start < slice_end`; `note_lo.min(hi)` at `:150` correctly collapses an out-of-range
  note window to an empty range rather than panicking; float→int casts saturate. Two
  non-defects recorded for completeness: an `onset_frames` above 2^63 would wrap the `as i64`
  at `:320` (unreachable from any generated plan), and a note window entirely past EOF prints
  `glue_ok = 1` for audio that does not exist — but prints `sounded = 0` on the same row, so
  the row is discardable downstream.
- **CLI restating library defaults / loudness-target drift between the CLI and
  `render-catalog`.** REFUTED — already guarded.
  `the_loudness_target_is_stated_consistently` (`render_profile.rs:457-500`) pins
  `target_lufs = -18.0` across `main.rs`, `render-catalog`, `quickstart.rs` and the README,
  and requires the `.opus` `ENCODER_SETTINGS` tag to be *derived* from the constant. The
  ceiling divergence (-1 vs -4.5 dBTP) is deliberate and documented at its declaration.
