## Findings

### CR-1 — Sample-crate tests never compare the embedded bytes to the packaged file, so a mis-pointed `include_bytes!` passes every oracle — *READY TO MINT*

- **Severity:** Medium · **Confidence:** High · **Effort:** Small
- `D:\worktrees\ferrosintesis\20260818-REV-MM-CLA@CRUCIBLE-code-review-044222\crates\ferrosintesis-samples-bottle\src\lib.rs:37-90`
- Generator source: `D:\worktrees\ferrosintesis\20260818-REV-MM-CLA@CRUCIBLE-code-review-044222\tools\ferrosintesis-samples\gen_crate_lib.py:197-210`

All three of bottle's tests assert over names only. `inventory_matches_packaged_samples`
(`:38`) compares on-disk *names* to `SAMPLES` *names* and never touches the byte half of the
tuple. `embedded_names_are_unique` (`:71`) is names only. `every_sample_is_a_nonempty_bank_file`
(`:81`) checks a length floor, four magic bytes, and `get(name) == Some(bytes)` — which is a
tautology over the same array. Nothing reads `samples/bottleloop_G3.flac` at test time.

**Failure scenario.** Point an `include_bytes!` at a different file while leaving its name
string unchanged. Every test stays green. `EXPECTED_BYTES`, where present, does not help: a
*swap* of two entries inside one crate preserves the aggregate. For bottle the blast radius is
small (one file), but this shape is emitted by `gen_crate_lib.py` into all 24 sample crates —
in `-orchestral` (158 files) or `-drumkit` (128) swapping two `include_bytes!` arguments ships
one instrument playing another's recording, and no in-package oracle ever notices.

**Fix.** One line inside the loop that already exists at `:82`:
`assert_eq!(bytes, &fs::read(samples_dir.join(name)).unwrap()[..]);` — emitted from the
generator so all 24 crates gain it, not hand-added to bottle.

### CR-2 — Bottle's published API documents WAV keys and bytes after the FLAC conversion — *READY TO MINT*

- **Severity:** Low · **Confidence:** High · **Effort:** Small
- `...\crates\ferrosintesis-samples-bottle\src\lib.rs:20-22` — "Returns the embedded WAV
  bytes for an exact file name." / "Names include the `.wav` suffix and are case-sensitive."
- `...\crates\ferrosintesis-samples-bottle\README.md:8` — "The WAV is a mono 16-bit 44.1 kHz
  looped take"
- `...\crates\ferrosintesis-samples-bottle\PROVENANCE.md:27` — "Baked to `samples/bottleloop_G3.wav`"

The crate ships exactly one bank file, `samples/bottleloop_G3.flac`, and that is the only key
`get` accepts. A consumer of the published `0.2.0` crate who follows the rustdoc and calls
`get("bottleloop_G3.wav")` receives `None`, and the crate exposes no way to enumerate names
(`SAMPLES` is private; only `FILE_COUNT` is public), so the working key is undiscoverable from
the crate's own documentation. The in-repo consumer succeeds only because
`...\crates\ferrosintesis\src\sampler.rs:4485` uses the undocumented `.flac` spelling.

**This is the un-swept straggler of an existing 12-bug sweep.** Sibling crates each already
have this bug filed — gong `MM-BUG-KILN-00238`, grand `00243`, headroom `00247`, honky-tonk
`00250`, musescore-grand `00253`, musescore `00258`, orchestral2 `00264`, sax `00268`, strings
`00270`, drumkit `00282`, fret-noise `00291`. Following this repo's own doctrine ("when a bug
reports X is missing from list L, enumerate all of L before fixing"), I enumerated the whole
set. Twelve crates still carry the stale rustdoc; **four of them have no bug filed at all**:

| Crate | stale `get()` rustdoc | bug filed |
|---|---|---|
| `-bottle` | `src/lib.rs:20-22` | **none** |
| `-core` | `src/lib.rs:278-280` | **none** |
| `-clavinet` | `src/lib.rs:61-63` | **none** |
| `-drumkit2` | `src/lib.rs:215-217` | **none** |
| gong, grand, sax, strings, orchestral2, musescore, fretnoise, drumkit | see table above | filed |

`-b1-upright` (`src/lib.rs:228`) says WAV and is **correct** — it is the deliberate
non-migrated crate. The other eleven crates already carry the reworded
"Returns the embedded sample bytes for an exact (case-sensitive) name."

**Fix.** Reword all three bottle documents to the FLAC contract. Raise the three sibling gaps
(`-core`, `-clavinet`, `-drumkit2`) too, or close the whole class with CR-9 below.

### CR-3 — The `.gitignore` sample-bank un-ignore block is stale, and bottle's line makes a stray bake artifact committable — *READY TO MINT*

- **Severity:** Low-Medium · **Confidence:** High (measured) · **Effort:** Small
- `D:\worktrees\ferrosintesis\20260818-REV-MM-CLA@CRUCIBLE-code-review-044222\.gitignore:52-79`

The explanatory NOTE at `:52-60` says the `!…samples/*.wav` negations "cover a SHRINKING set —
`b1-upright` … and `drumkit`/`drumkit2`". I globbed
`crates/ferrosintesis-samples-*/samples/*.wav`: **52 files match, every one of them in
`-b1-upright`.** `drumkit` and `drumkit2` ship zero `.wav`. The note is wrong about two of the
three crates it names, and the negation lines for every migrated crate — including bottle's at
`:79` — are dead.

Bottle's line is not merely dead, it is load-bearing in the wrong direction. A bake on a host
without `ffmpeg` leaves `bottleloop_G3.wav` in the crate (see CR-6); the global `*.wav` ignore
would have hidden it, but `:79` un-ignores it, so `git add crates/ferrosintesis-samples-bottle`
commits it and `Cargo.toml:10`'s `samples/**` would package a duplicate container.

**Fix.** Reduce the negation block to `-b1-upright` and correct the NOTE to match. Enumerate
the whole block — deleting only bottle's line repeats the defect the NOTE itself warns about.

### CR-4 — Bottle's `lib.rs` is hand-written and has drifted from the generator every other crate uses — *READY TO MINT (as the CR-9 requirement, or a bug)*

- **Severity:** Low · **Confidence:** High · **Effort:** Small
- `...\crates\ferrosintesis-samples-bottle\src\lib.rs:13-15`

`tools\ferrosintesis-samples\gen_crate_lib.py` is the single source of truth for a sample
crate's `lib.rs`. Bottle's file was hand-written when the crate was created (2026.07.20) and
never regenerated, so it is missing three things the generator emits:

| Generator emits | Bottle has |
|---|---|
| `static SAMPLES: [(&str, &[u8]); FILE_COUNT]` (`gen_crate_lib.py:139`) | `static SAMPLES: [(&str, &[u8]); 1]` (`lib.rs:15`) — the count written as a literal **twice** |
| `/// Returns the embedded sample bytes for an exact (case-sensitive) name.` (`:150`) | the stale WAV wording (CR-2) |
| `//! Generated by tools/ferrosintesis-samples/gen_crate_lib.py …` header (`:120`) | a bespoke header, no generator marker |

**Bottle is the only one of 24 sample crates whose array length is a literal** (verified by
regex across every `crates/*/src/lib.rs`). The cohort uses two better shapes: most bind the
length to `FILE_COUNT`; `-musescore`, `-strings` and `-orchestral2` go further and derive
`pub const FILE_COUNT: usize = SAMPLES.len();` over a slice
(`...\crates\ferrosintesis-samples-musescore\src\lib.rs:18,142`). Only 11 crates carry the
generator header at all, so bottle is one of many un-regenerated files — but the most drifted.

**Fix.** Regenerate via `gen_crate_lib.py`. Note it would replace bottle's bespoke crate-level
header with the generic `--doc` line; `legal_doc_line`'s docstring (`gen_crate_lib.py:46`)
records that ten crates deliberately keep bespoke headers, so preserve bottle's and take the
rest.

### CR-5 — The 12-byte length floor is the RIFF minimum applied to a FLAC-only crate

- **Severity:** Low · **Confidence:** Medium-High · **Effort:** Trivial
- `...\crates\ferrosintesis-samples-bottle\src\lib.rs:83`

`assert!(bytes.len() >= 12, …)` — 12 is exactly where `bytes[8..12]` stops panicking for the
RIFF branch. The shortest well-formed FLAC stream is 42 bytes (4-byte `fLaC` marker + 4-byte
metadata-block header + 34-byte mandatory STREAMINFO), so `fLaC` followed by eight bytes of
garbage passes a test whose message calls it "a sample". Subsumed in practice by CR-1, which
is the real fix; worth correcting to 42 in the FLAC branch while there.

Related: the crate asserts nothing about rate, channels, bit depth, duration or decodability —
every property its own `README.md:8` and `PROVENANCE.md:27` claim, and the 205.0 Hz root
`sampler.rs:4485` hardcodes. Those *are* guarded, but only in the parent crate
(`bottle_loop_pitch_integrity`, `sampler.rs:8446`). The standalone published crate proves only
"one file, expected name, plausible first four bytes". Reported as context, not a defect.

### CR-6 — A documented re-bake on a host without ffmpeg leaves a committable `.wav` in the crate

- **Severity:** Low · **Confidence:** High on the code path; not executed · **Effort:** Small
- `PROVENANCE.md:29` → `...\tools\ferrosintesis-samples\prepare.py:5362` → `:4426`

`bake_bottle_loop` writes `bottleloop_G3.wav` with pure stdlib (`prepare.py:5362`). Conversion
to FLAC and deletion of the WAV happen later, in `publish_pending_banks` (`:4412`, `:4449`),
whose first act is `_require_ffmpeg()` (`:4426`), which raises. Its own docstring (`:4418`)
acknowledges "a failure part-way leaves the WAV". The bank is then two files against
`FILE_COUNT == 1`, so `inventory_matches_packaged_samples` (`lib.rs:66`) goes red — the system
fails closed, but the failure reads as a baffling red test after a documented tool run, and
CR-3's `.gitignore:79` is what makes the residue committable.

**Not filed separately:** this is the bottle instance of the already-open
`MM-BUG-KILN-00252` ("FLAC migration tool can leave a partial mixed bank after a late
failure"). The novel half is the `.gitignore` interaction, which CR-3 carries.

### CR-7 — The repo-wide oracle that polices sample directories still calls FLAC files "not a `.wav`"

- **Severity:** Low · **Confidence:** High · **Effort:** Trivial
- `...\crates\ferrosintesis\src\inventory.rs:22-23`, `:141`, `:160-164`

Module prose says the sweep enumerates `crates/ferrosintesis-samples-*/samples/*.wav`; the test

### CR-8 — The packaged SHA-256 pin is auditable in a checkout but decorative in the published crate

- **Severity:** Low · **Confidence:** Medium that it is a defect; the facts are certain
- `...\crates\ferrosintesis-samples-bottle\PROVENANCE.md:25`, `...\crates\ferrosintesis\src\provenance.rs:383-385`, `:417-423`

`PROVENANCE.md:25` pins `tools/ferrosintesis-samples/freesound-src/bottle_G3.wav`, a path absent
from the `0.2.0` archive, for a source `PROVENANCE.md:20` says is un-refetchable without a
Freesound login. The enforcing oracle's doc claims "evidence that ships with the crate is
evidence a downstream consumer can actually audit", but its predicate is `docs.contains(hash)` —
it checks the hash *string* appears somewhere in a packaged document. It never checks the bytes
are reachable, nor that the hash sits beside the right filename. Bottle's provenance could name
the wrong source file next to the right hash and still pass. Judgement call for Arthur: either
the module doc over-claims, or the oracle should bind hash to filename.

### CR-9 — No oracle enforces sample-crate `lib.rs` regeneration parity — *REQUIREMENT CANDIDATE*

- **Severity:** design / technical debt · **Confidence:** High · **Effort:** Medium

`gen_crate_lib.py` derives every sample crate's `lib.rs` from the files on disk, but **nothing
asserts that a committed `lib.rs` still matches what the generator would emit today**. The cost
is measurable: the 2026.08.16 container rename left 12 crates with stale rustdoc, prompting a
crate-by-crate sweep that filed 12 near-identical bugs and still missed four crates (CR-2), and
bottle additionally kept a literal array length no other crate has (CR-4).

This is exactly the pattern CLAUDE.md names as the recurring defect here — "hand-maintained
lists are the recurring defect; derive them" — except the hand-maintained artefact is the
*sweep* rather than a list. A parity oracle would have closed all of CR-2, CR-4 and CR-7 at
once and made the 12-bug sweep unnecessary. Precedent: `MM-REQ-KILN-00299` does the same thing
for the CLI's documented flag set.

**Caveat the implementer must respect.** Do *not* simply regenerate every crate: the generator
also emits `EXPECTED_BYTES` (`gen_crate_lib.py:172`), and `MM-BUG-CRUCIBLE-00039` (Open) shows
that pin encodes the ffmpeg vendor-string length, so a re-bake on a different ffmpeg fails the
crate's own size oracle. Bottle is one of only four crates *without* `EXPECTED_BYTES`, which
under 00039 is arguably a feature. Settle 00039 first, or scope the parity oracle to the
shape-and-prose parts and exclude the byte pin.

## Not reported — angles checked that came back clean

These were pressed on deliberately and are **not** defects. Recording them so the next pass
does not re-spend the effort.

- **The FLAC migration did not hole the provenance family-count oracle.**
  `inventory.rs:648 packaged_family_counts` counts `.wav` **and** `.flac` (`:654`), so bottle's
  `| bottleloop_* | 1 |` row is still derived from disk and cannot drift.
- **Licensing correctly excludes this CC0 crate, and fails closed.**
  `licensing.rs:174-188` derives the obligation from `PROVENANCE.md` against a closed vocabulary
  (`ATTRIBUTION_LICENSES`, `:144`) and asserts agreement with the manifest. Both sets are empty
  for bottle. A mistyped `"CC0"` or `"CCO-1.0"` is *not* filtered by the `!= "CC0-1.0"` guard at
  `:133`, so it would disagree with the empty provenance set and trip the assert at `:178`.
- **Bottle does *not* have the sibling "regeneration leaves the FLAC bank stale" defect.**
  `_publish_and_report` calls `publish_pending_banks()` on every path that writes a bank
  (`prepare.py:5436`), and the single-file bank's WAV and FLAC share a stem, so the converted
  file overwrites cleanly with no orphan.
- **The pinned CC0 source exists and needs no `-text`.**
  `tools\ferrosintesis-samples\freesound-src\bottle_G3.wav` is present and is binary PCM;
  `.gitattributes` correctly scopes `-text` to text evidence only.
- **The `include` list is complete and guarded.** `every_sample_crate_package_path_exists`
  (`inventory.rs:1625`) and `packaged_cc0_legal_text` (`:622-643`) cover it. `license-file` being
  unset is correct — `license = "CC0-1.0"` is valid SPDX.
- **Stray files and subdirectories under `samples/` are caught.**
  `packaged_sample_directories_hold_only_top_level_lowercase_wavs` (`inventory.rs:141`) rejects
  subdirectories and any non-`.wav`/`.flac` file, so a leftover `.part` cannot ship.
- **Cross-crate basename shadowing is guarded well.** `no_two_asset_crates_ship_the_same_wav_basename`
  (`payload.rs:452`) scans the filesystem, covers `.flac` and `ALIASES`, and carries an
  anti-vacuity floor. Bottle sits 18th in `embedded_wav`'s first-match-wins chain
  (`sampler.rs:252`), so 17 crates could shadow it — this is what stops them.
- **`FILE_COUNT` is not dead API-wise in a way that matters** — no consumer outside each crate's
  own tests reads it, but that is a uniform 24-crate convention, not a bottle defect.
