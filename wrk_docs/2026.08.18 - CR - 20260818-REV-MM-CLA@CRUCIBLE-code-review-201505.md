## Verdict

The crate is sound. Its runtime contract, licensing evidence, version pin and
regeneration path all hold up under adversarial reading. What has not held up is its
**prose**: the 2026-08-16 WAV→FLAC migration converted the payload and left the published
documentation describing the old container — including the rustdoc on the crate's only
public function. That is the whole of what is wrong here, and it is a repo-wide list
defect, not a clavinet defect.

Two bugs filed. No requirement captured — the one design gap worth tracking is already
covered by an existing Draft req, which itself needs a correction (see Finding 4).

## Findings

### 1 — The crate's only public function documents a file-name suffix its payload no longer uses

**Severity Low · Confidence High · Confirmed** · `MM-BUG-CRUCIBLE-00044`

`crates/ferrosintesis-samples-clavinet/src/lib.rs:61-63` reads "Returns the embedded
**WAV** bytes for an exact file name. / Names include the **`.wav`** suffix and are
case-sensitive." Every embedded name ends `.flac`
(`crates/ferrosintesis-samples-clavinet/src/lib.rs:14-59`). The lookup is an exact
case-sensitive compare (`src/lib.rs:64-69`), so a caller following the published doc asks
for `clavinet_C2.wav` and gets `None` with no diagnostic. This is the crate's entire
public API, live on docs.rs for the released `0.2.0`.
`crates/ferrosintesis-samples-clavinet/PROVENANCE.md:9` repeats it in the packaged
provenance file — "The 11 WAVs in `samples/`".

Per CLAUDE.md's "enumerate all of L before fixing", the set was enumerated rather than
patched at the reported site. **Twelve** asset crates carry the same two stale lines while
embedding only FLAC: `-core` (278, 280), `-drumkit` (562, 726, 740, 742, 754), `-drumkit2`
(215, 217), `-gong` (23, 25), `-grand` (235, 237), `-fretnoise` (78, 80), `-clavinet` (61,
63), `-orchestral2` (14, 410, 412), `-bottle` (20, 22), `-musescore` (16, 144, 146), `-sax`
(314, 316), `-strings` (19, 188, 190). `-b1-upright` is the deliberate WAV exception and
its wording (`src/lib.rs:228`) is correct. Same root cause in prose:
`crates/ferrosintesis/src/lib.rs:52` ("1156 WAVs across twenty-five") and the "N WAVs" /
"The WAVs under `samples/`" statements in ten crates' `README.md` / `PROVENANCE.md`.

**Fix.** Adopt the container-neutral wording the newer crates already use — "Returns the
embedded sample bytes for an exact (case-sensitive) name"
(`crates/ferrosintesis-samples-rain/src/lib.rs:17`,
`-honkytonk/src/lib.rs:51`, `-mandolin/src/lib.rs:175`) — then add the derived oracle in
Finding 2 so it cannot drift again. **Effort ~1-2 h.**

### 2 — The bank's format assertion no longer proves anything

**Severity Low · Confidence High · Confirmed** · `MM-BUG-CRUCIBLE-00045`

`crates/ferrosintesis-samples-clavinet/src/lib.rs:113-127` accepts RIFF **or** FLAC per
file, and its only size guard is `EXPECTED_BYTES`, a hand-maintained sum (verified correct
today: the eleven on-disk sizes total 529,574 bytes). Nothing pins the container, and
`crates/ferrosintesis/src/payload.rs:56-66` counts `wav` and `flac` alike, so the
workspace-level oracle does not catch it either. An uncompressed WAV dropped back into a
FLAC bank asserts clean once the constant is bumped — and a constant bump is exactly what
an editor does mechanically. The permissive check was right during the migration; it is
now a no-op for every crate except `-b1-upright`, whose custom `b1t` chunk a FLAC container
cannot hold (`.gitignore:52-58`).

This matters in proportion to what the migration bought: 43.5 MiB off the binary
(`crates/ferrosintesis/CHANGELOG.md:18`). The regression it fails to catch is silent and
multi-megabyte.

**Fix.** One derived oracle discharges this and Finding 1. Fold into
`crates/ferrosintesis/src/payload.rs`, which already walks exactly this directory set via
`licensing::default_sample_crates()` (`payload.rs:42-67`): derive each crate's container
from its `samples/` directory, assert magic matches extension, assert FLAC for every
default-embedded crate bar a commented `-b1-upright` allowlist, and assert no crate's
`lib.rs` / `README.md` / `PROVENANCE.md` names a container its bank does not ship. Keep the
vacuous-pass guard the sibling oracles use, and — per CLAUDE.md — write the adversarial
fixture that *should* fail it (a WAV planted in a FLAC bank; a `.flac` file that is really
a RIFF) and check that it does. **Effort ~1 h, shared with Finding 1.**

### 3 — Nothing ties an embedded file to a zone table, so dead payload would be silent

**Severity Low · Confidence High · Systemic gap, no live defect** · reported, no new ticket

The crate exports only `get(name)` and `FILE_COUNT`; `SAMPLES` is private
(`crates/ferrosintesis-samples-clavinet/src/lib.rs:12-69`). The consumer hard-codes the
eleven filenames in its zone table (`crates/ferrosintesis/src/sampler.rs:5501-5511`). The
two directions fail asymmetrically: a zone naming a **missing** file panics loudly at
prewarm (`sampler.rs:232-254`), but a file **embedded and never named** is silent — dead
bytes in every default binary, and the register it served degrades quietly because
`nearest()` repitches from a neighbouring zone. The crate's own
`inventory_matches_packaged_samples` compares disk against `lib.rs`, never `lib.rs` against
the zone table.

The devil's advocate checked the obvious refutation and it holds:
`crates/ferrosintesis/src/payload.rs` guards totals and cross-crate basename collisions
(`payload.rs:522-535`), `sampler.rs` guards accessor and prewarm coverage
(`sampler.rs:6304-6318`, `6413-6427`); none of them cross-checks embedded filenames against
zone-table usage. It also confirmed there is **no live defect here** — the eleven names in
`sampler.rs:5501-5511` match `lib.rs:14-59` exactly.

**Not filed as a new requirement, deliberately.** `MM-REQ-KILN-00222` (Draft) already
requires proving "every filename-to-root mapping consumed by ferrosintesis" for this crate.
See Finding 4 — but note the wider observation: roughly fifteen near-identical per-crate
"assets must be independently verifiable" reqs exist (`00164`, `00167`, `00170`, `00183`,
`00185`, `00186`, `00188`, `00189`, `00194`, `00211`, `00222`, `00225`, `00230`, `00231`,
`00242`, `00286`, `00290`). One generic derived oracle would discharge most of them, and
the per-crate proliferation is the same hand-maintained-list smell CLAUDE.md warns about.
Worth a human decision at Gate 1 rather than a sixteenth ticket from me.

### 4 — `MM-REQ-KILN-00222` was overtaken by the FLAC migration and now specifies the wrong container

**Severity Low · Confidence High · Confirmed · Ledger correction, not code**

`reqs/MM-REQ-KILN-00222.md:19-21` requires an oracle that "validate[s] complete **RIFF**
and **PCM16 mono 44.1 kHz** structure and extents" over "the eleven packaged clavinet
**WAVs**", and cites `src/lib.rs:78-120` for the existing "RIFF/WAVE magic" check. The req
was raised `2026-08-16T13:45:18Z`; the banks became FLAC at `2026-08-16T20:49:44+01:00`
(`9046cd14`), about six hours later. It was accurate when written and is stale now: an
implementer following it would build a RIFF-structure oracle for a FLAC bank, and the cited
range has moved to `src/lib.rs:78-127`.

This pass writes no tracked files, so the req was left untouched. **Action for the human /
next fix pass:** re-word `MM-REQ-KILN-00222` for FLAC before anyone claims it, and re-check
the sibling per-crate reqs raised before 2026-08-16T20:49 for the same staleness.

## Not reported (checked and refuted)

- **`prepare.py` writes `.wav` into a FLAC bank.** Refuted. `_bake_clavinet`
  (`tools/ferrosintesis-samples/prepare.py:4669-4705`) writing WAV is the documented
  intermediate: `write_wav_mono` (`prepare.py:4372-4403`) registers the bank directory and
  `publish_pending_banks` (`prepare.py:4412-4452`) encodes, decodes back, compares PCM
  bit-exactly, then removes the WAV. Deliberate two-phase design, restartable by
  construction.
- **The regen guard compares `.wav` expectations against a `.flac` directory.** Refuted —
  `_validate_generated_output_inventory` normalises both sides through `packaged_name`
  (`prepare.py:5569-5590`).
- **`NOTICE` attribution is only shallowly checked.** Refuted, and the guard is stronger
  than I assumed. `crates/ferrosintesis/src/licensing.rs:772-823` requires non-empty credit
  tokens, that the MIT text is actually named, and `carries_licensor_owned_signal`
  (`licensing.rs:259-273`) — a source URL or a real `Copyright (c)` line — precisely so a
  gutted NOTICE cannot pass on a bare crate-name match (`MM-BUG-KILN-00115`). The crate's
  `NOTICE:6-12` carries multiple copyright lines and passes on content.
- **README's fallback claim.** Verified true, not drift: `--no-samples` or `CC0 != 0` does
  route GM7 to the modeled voice — `crates/ferrosintesis/src/engine.rs:2296`,
  `voices.rs:14480-14486`, and the dedicated test `sampler.rs:10755-10776`.
- **`PROVENANCE.md`'s `clavinet_t60` pointer.** Verified live at `prepare.py:913`.
- **Version pin.** Verified consistent: crate `Cargo.toml:3` = `0.2.0`,
  `crates/ferrosintesis/Cargo.toml:65` pins `=0.2.0`, released in `417c0b22`. The minor
  bump is correct — `get()`'s accepted name set changed, which is a public-API change.
- **Root frequencies.** Verified: the eleven roots at `sampler.rs:5501-5511` are standard
  12-TET A440 values in the G1→G6 order `PROVENANCE.md:43` and `src/lib.rs:3` claim.
- **`include = [...]` completeness.** Verified sufficient for the packaged crate's own test
  and its NOTICE obligations; separately guarded by
  `crates/ferrosintesis/src/inventory.rs` (`every_sample_crate_package_path_exists`,
  `every_sample_crate_ships_a_packaged_provenance`).
- **Stale `.gitignore:61` un-ignore line** (`!crates/ferrosintesis-samples-clavinet/samples/*.wav`).
  Vestigial after the FLAC move, but harmless, and the file's own comment
  (`.gitignore:52-58`) already says the set is shrinking. Not a defect.
- **Manifest metadata** (no `keywords`/`categories`). Matches every sibling asset crate;
  house style, not a finding.
- **Case-insensitive filesystems, `--no-default-features`.** No collision among
  `C2..C6`/`G1..G6`; the crate declares no features of its own.
