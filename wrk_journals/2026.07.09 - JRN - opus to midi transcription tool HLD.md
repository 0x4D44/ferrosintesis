# 2026.07.09 — JRN — OPUS→MIDI transcription tool (HLD)

Engineer's log for the design task: an HLD for a tool that transcribes arbitrary
external audio (OPUS/WAV/… mixes or stems) into multi-track MIDI.

## Context
- Preceded by a 6-dimension research workflow (12 agents, adversarially verified)
  on the state of automatic music transcription. Key verified findings:
  - Monophonic (melody/bass) and solo-piano transcription are effectively solved
    (CREPE ~99.7% clean pitch; ByteDance piano onset-F1 ~0.967).
  - Multi-instrument transcription with instrument-ID is an open research problem:
    2025 AMT-Challenge SOTA ~0.60 F1; precision collapses 0.91→0.46 from 1→3
    simultaneous instruments.
  - Per-instrument separation of the "other" bucket caps at ~2–3 dB SDR
    (guitar/piano) — often unusable; Facebook's own 6-stem docs admit piano
    "is not working great."
  - Best assemblable path = SEPARATE then TRANSCRIBE PER STEM (Demucs + Basic
    Pitch + a drum ADT), all free/permissive.
  - A pure/zero-dep Rust transcriber is not viable (pure DSP is monophonic-only;
    competitive quality needs the Python ML stack).

## Decisions taken with Arthur (step 1)
- Approach: assemble existing free tools, do NOT build a transcriber. (Endorsed.)
- "Other" stem: **attempt the split** (6-stem) + sketch fallback for residual.
- Input: **both** a mix (auto-separate) and pre-made stems (skip separation).

## Key UNDERSTAND finding
- `render_opus.py` is the exact template: a **stdlib-only** Python orchestrator that
  shells out to external binaries (`ferrosintesis`, `ropusenc`). The transcription
  tool is its inverse and follows the identical pattern — stdlib-only orchestrator,
  ML tools as external user-installed prerequisites (like `ropusenc`), nothing
  third-party in committed source. This resolves the "where does it live / deps"
  question by precedent; no new architectural tension.
- Repo already has stdlib MIDI read/write (`engine.py` `parse_midi`/`write_midi`),
  so the MIDI-assembly stage stays stdlib.

## Design simplification during drafting
- Dropped CREPE from v1. Basic Pitch already does note segmentation and handles
  monophonic stems acceptably, emitting MIDI directly; a CREPE path would add a
  prerequisite AND a hand-rolled f0→note segmenter (a new error source). CREPE +
  segmentation logged as a future quality upgrade for the mono stems.
- Result: v1 external tools = ffmpeg + Demucs + Basic Pitch + one drum ADT. The
  orchestrator is shell-out + a stdlib MIDI merge; no DSP in our code.

## External review outcome (Codex, all 8 folded)
Decorrelated fresh eyes; fetched the actual ADTOF-pytorch/Demucs repos. "Buildable and
mostly honest — spec gaps, not architectural blockers." No re-review needed. Folded:
1. A2 self-contradiction — the no-ML oracle is now the SOLE build gate; round-trip/smoke
   are opt-in `--diagnose` diagnostics.
2. Robust MIDI note-off semantics — FIFO per (track,ch,pitch), note_on vel-0 = off,
   overlap clamp, unmatched-off drop, default 500000 µs/qn, reject SMPTE.
3. Pinned role→channel→program→track-name table; forced, oracle-asserted.
4. Long files — declared max duration + "split it" error; no chunking (non-goal).
5. Tool paths — one gitignored transcribe.local.json (paths/device/extra args) + example;
   no env vars / flags.
6. Drum tool honesty — ADTOF-pytorch unpackaged/unclear-licence/5-class vs omnizart
   madmom-hell; decide by install spike.
7. Stem discovery — alias→role matching, duplicate/missing errors, zero-note = empty
   (no DSP, stays stdlib-pure).
8. Simplification — ingest Basic Pitch CSV (absolute seconds) instead of parsing its
   MIDI + stripping pitch-bends.

## Adversarial review outcome (all survivors folded in)
Three highly convergent lenses; none refuted. Substantive changes:
1. **Dependency isolation** — Demucs/Basic Pitch/drum-ADT have incompatible dep graphs
   (torch vs TF/tflite vs madmom); can't share one env. Per-tool venvs, invoke by path.
   Prefer torch-native ADTOF-pytorch to share Demucs's env (2 envs not 3).
2. **No-ML assemble oracle is the PRIMARY test** — Stage-3 merge is the only code we
   author and it's deterministic; the round-trip tested it *through* a nondeterministic
   ML model. Added an exact-answer stdlib oracle; demoted round-trip to diagnostic.
3. **A2 was a tautology** ("threshold = whatever we first measure"). Split into absolute
   floor (from Basic Pitch's *published* numbers) + regression guard + "too-low ⇒ broken
   oracle" tripwire.
4. **Lean-fallback was backwards** — drums are the highest-value stem (9–12 dB, mature
   ADT); the harmonic guitar/piano split is the cuttable layer, not drums.
5. **D4 "nothing is lost" was false** — 6-stem depletes `other`; htdemucs_6s piano is
   officially weak. Rationale corrected; 4-vs-6 default surfaced as a sign-off question.
6. **Stage-3 is net-new ~200–300 lines** — engine.py `parse_midi` is a counter, not an
   extractor. Enumerated traps: drop 0xE0 bends, per-stem tempo→seconds→120BPM, drums=
   channel index 9, distinct channels so piano/other (both prog 0) don't collide.

## Surprises / notes
- The round-trip oracle (render a known MIDI with ferrosintesis → transcribe →
  compare) is a genuinely nice free test asset — but per the research it validates
  our plumbing/note-recovery logic, NOT real-world accuracy (synthetic audio
  flatters the models, and rewards matching the synth's own timbre). Framed that
  way in the doc.
