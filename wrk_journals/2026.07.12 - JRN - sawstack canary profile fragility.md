# 2026.07.12 - JRN - sawstack canary profile fragility

## Task

`cargo test --workspace` reported one red: `altbank::tests::sawstack_v1_canary_frozen`.
Reported hypothesis: a pad(89)/SawStack golden that trunk drifted via a landed
task (bfd77a9, "sustaining lead voice") without re-freezing.

## What I found (the hypothesis was wrong)

The red is **not** a drift from any landed commit. It is a build-**profile**
artefact.

- `origin/main` (87f8903, fetched) passes the canary in **debug** and **fails in
  release**. I built both.
- The canary FNV-hashes the whole f32 render and `assert_eq!`s a golden `u64`.
  - debug render of pad(89)  -> `0x63cb52bc25cbdd4f` (the pinned value)
  - release render of pad(89) -> `0x66cf721ab5a542fb`
- Those two hex values are **exactly** the pair the test's own comment says it has
  been "re-pinned" between: `0x66cf721ab5a542fb -> 0x63cb52bc25cbdd4f`. The comment
  blamed "reed-rasp and GM43-waveguide/bowed work". That attribution is wrong —
  the pad render is bit-identical across all those commits *within a profile*; it
  only differs *between* profiles.

Root cause: `[profile.release]` (opt-level 3 + LTO) reorders the SawStack's
floating-point ops (summed detuned saws + filters), so the last bits differ and
the FNV hash flips. A bit-exact hash of f32 DSP output is not a valid golden. The
chronic re-pin history (`2f4c19c` -> `13b400d` -> the brass-rasp task) is people
pinning from whichever profile they happened to run, each flip making the *other*
profile red. The user runs the release gate (audio suites are always run in
release — debug rendering is glacial); the last pin was from debug, so release
was red.

bfd77a9 is purely additive (new `DRIVE_LEAD` const + a new `29|30 =>` arm); it
cannot and does not touch the pad(89) or choir(52) path. Confirmed the canary is
green in debug on: trunk, the stage1-pipe wind-rework worktree (uncommitted), and
electric-guitar-v2 (v0.15.0).

## Fix

Replaced the exact-bit hash with a **profile-independent feature freeze**
(`altbank.rs`, `sawstack_v1_canary_frozen`). It renders pad(89) and choir(52)
exactly as before (key 60, vel 100, seed 7, no samples) and pins a 6-feature
aggregate vector per voice — `[rms, centroid, flatness, band@f0, band@2f0,
hp>2kHz]` — compared with a **1e-3 relative tolerance**.

Justification for the tolerance: measured across debug and release the aggregates
agree to ~7 significant figures (relative spread ~1e-7 — per-sample reorder noise
averages out over 66150 samples). 1e-3 is ~10^4x that spread, yet the two voices'
features differ by 30–130% (pad rms 7.9e-2 / centroid 542 Hz vs choir 3.5e-2 /
1248 Hz), so any real cross-voice contamination trips it by orders of magnitude.
The canary keeps its purpose (catch a change to another voice leaking into the
shared pad-delegation / choir_v2 path) while no longer false-positiving on the
build profile.

Validated: canary green in **both** debug and release; `clippy -p ferrosintesis
--all-targets -D warnings` clean; full `cargo test --workspace --release` green.

Test-only change — no shipped-code edit, so no version bump.

## Latent risk logged (not fixed here — out of scope)

`drums.rs` has the same frozen-bit-hash pattern (`v1_drum_render_is_frozen`,
`brush_render_is_frozen`). They currently pass in BOTH profiles (the drum DSP is
bit-stable across opt levels today), so they are not broken — but they are the
same fragile *class*: a future drum change that introduces reorder-sensitive math
would flip them red on one profile only. Parked in `scratchpad.md` for a separate
triage; the durable rule is in `lessons_learnt.md`.
