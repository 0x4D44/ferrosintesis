# 2026.07.13 — JRN — ferrosintesis pre-1.0 API pass for crates.io

## Why

Arthur asked whether we should publish the synth to crates.io "as the first version".
A six-lens read-only audit (36 agents, adversarially verified) said: nothing legally or
mechanically blocks a publish, but the *library's public face* is not ready, and a 1.0
would freeze four semver landmines. Decision: do the pre-1.0 API pass, publish **0.17.0**,
earn 1.0 later. This journal covers the pass. **Nothing has been published.**

## What the audit found (and got wrong)

Refuted worries — all three of my priors were wrong, which is why the audit was worth running:

- **Package size fits.** Real `cargo package` measurement (not the audit's gzip proxy):
  samples-core **7,102,046 B** (6.77 MiB), samples-orchestral **7,005,718 B** (6.68 MiB),
  against the 10,485,760 B cap. ~33% headroom each. Merging the two banks WOULD bust it.
- **Sample licensing holds up.** 202 WAVs, all CC0, chased to source: 195 from VSCO 2 CE
  (commit-pinned `4403009…`), 7 from FreePats (SHA-256-pinned). `prepare.py` maps every
  output file to an upstream URL; 202 mapped, 202 on disk, zero orphans.
- **Publish mechanics are clean.** No `build.rs`, no `include_bytes!` escaping a crate root,
  no bare path deps, zero third-party dependencies.

The one real blocker is mechanical and unchanged: ferrosintesis exact-pins the two sample
crates at `=0.1.0` and neither is on crates.io yet, so publish order is forced —
**samples-core → samples-orchestral → ferrosintesis**.

## What I changed

The theme: the crate was an excellent engine with a CLI-shaped API bolted to `pub`.

1. **A real error type.** `offline::load`/`parse` returned `Result<_, String>`, which does not
   implement `std::error::Error` — a downstream user could not match on a kind or `?` it into
   `anyhow`. Added `MidiError` (`src/error.rs`), `#[non_exhaustive]`, `Display` + `Error` with a
   source chain. The parser's error sites mapped cleanly onto real variants (`NotMidi`,
   `UnsupportedFormat(u16)`, `UnsupportedTimeDivision`, `MissingTrack{index}`,
   `BadStatusByte(u8)`, `UnexpectedEof`, `Io{path, source}`) — no `Parse(String)` cop-out was
   needed. `Io` keeps the path so the CLI's `error: song.mid: ...` message survives.
2. **`#[non_exhaustive]` + a builder on `Options`.** Adding an 8th render knob after a 1.0 would
   have been a major bump. Also `Stats`, `Progress`, `RealtimeOptions`, `RealtimeError`.
   **Non-obvious:** `#[non_exhaustive]` forbids *functional update* (`..Default::default()`) from
   a foreign crate too, and `let mut o = Options::default(); o.sr = x;` trips clippy's
   `field_reassign_with_default` under our `-D warnings` gate. So a `with_*` builder is not
   sugar — it is the only clean construction path. Fields stay `pub` for reading.
3. **The library no longer writes to stderr.** `Options.verbose` drove an `eprintln!` from inside
   the render loop. Replaced with `render_with_progress(song, opt, &mut dyn FnMut(Progress))`;
   the CLI now owns its own progress printing. `render()` delegates with a no-op closure, so the
   audio is bit-identical.
4. **Docs.** Crate-level `//!` with a doctest that actually parses and renders an in-memory SMF
   (not `no_run` — it proves the headline example works on every `cargo test --doc`), and `///`
   on every public item, including the audio contract (interleaved stereo f32 at `opt.sr`).
5. **README split.** The 23 KB design essay moved to `crates/ferrosintesis/DESIGN.md`; a new
   crates.io landing page took its place. **Written by Fable 5** on a consult (see below).
6. **MSRV declared: 1.87.** Verified, not asserted — see the surprise below.
7. Version 0.16.0 → **0.17.0**, with the `ferrosintesis-cli` and `render-catalog` dependency pins
   moved in lockstep (both pin the lib; the audit's proposed fix named only the CLI and would
   have left the workspace unresolvable).

## Surprises

**The manifest could not be parsed by the MSRV we were about to declare.** `cargo +1.87 check`
failed with `invalid inline table` — `ferrosintesis-samples-orchestral` was declared as a
*multi-line* inline table:

```toml
ferrosintesis-samples-orchestral = {
    path = "...", version = "=0.1.0", optional = true,
}
```

Multi-line inline tables are invalid TOML 1.0; only recent cargo accepts them. Every one of the
36 audit agents missed this, because none of them ran an older toolchain — they all reasoned
against the manifest with a 1.95 cargo, which parses it happily. Fixed by putting the dependency
on one line, with a comment saying why. **This would have shipped a crate that a user on our own
declared MSRV could not build.**

**The MSRV itself was wrong by inspection.** The audit's verifier grepped for `OnceLock` and
`is_some_and` and concluded "≥1.70". That is a lower bound, not the answer: clippy's
`incompatible_msrv` lint (which only fires once `rust-version` is *set*) immediately found
`is_multiple_of` (stable 1.87) and `is_none_or` (1.82) in `altbank.rs` and `voices.rs`. True floor
is **1.87**, now verified by a real `cargo +1.87 check --workspace`.

**The repo has been carrying a performance claim that is off by 8x.** DESIGN.md (formerly the
README, and therefore about to become the crates.io landing page) said "Renders ~14 minutes of
stereo 44.1 kHz audio in under 20 seconds" — ~42x realtime. Measured on Big Weather's "First
Light Freeway": **245.8 s of audio in 46.8 s wall = 5.25x**. The old number presumably predates
the orchestral voices and the sample layer. Fable carried it into its README draft in good faith
(it had no way to know); I only caught it because I ran the render rather than trusting the text.
Both documents now carry the measured figure.

## Second pass: what the adversarial review caught

I reviewed my own commit with a 24-agent, 5-lens adversarial workflow (behaviour, semver,
errors, docs, publish), each finding re-verified by a fresh agent told to refute it. It was
worth it: it found a hole in the very thing this pass existed to close, and four factual
errors in the README's GM table.

**The `#[non_exhaustive]` pass was half-done.** `#[non_exhaustive]` on an *enum* seals it
against new **variants**. It does nothing for the **fields inside** a variant. So
`MidiError::Io { path, source }` and `RealtimeError::OutputTooSmall { needed, got }` were
still exhaustively matchable and constructible downstream — and the single most obvious
future improvement to a MIDI parser's error (telling the caller *where* in the file it
failed) would have been a major bump. Fixed: every data-carrying variant now carries its own
`#[non_exhaustive]`, tuple variants became struct variants (`UnsupportedFormat { format }`,
`BadStatusByte { status }`), and `OutputTooSmall` gained the `frames` field it should always
have had (free today, a major bump tomorrow).

**`Options` was the worst of both worlds.** `#[non_exhaustive]` blocks *construction* but not
*field assignment*, and the fields were `pub` — so the builder was optional sugar while every
field NAME and TYPE became a 1.0 commitment. The bill was already visible in the diff:
`Options::sr: f32` beside `RealtimeOptions::sample_rate: u32`, and a `with_reverb` builder
setting a field called `wet`. Fixed by sealing: fields are `pub(crate)`, the `with_*` builders
are the only construction path, and accessors (`sample_rate()`, `reverb()`, `echo()`, …) are
the only read path. Same treatment for `RealtimeOptions`. The rule is now explainable:
**input structs are sealed with builders; output structs (`Stats`, `Progress`) keep `pub`
fields** — they cannot be constructed downstream anyway, so adding a field is already safe.

**A ~60-byte MIDI could abort the process.** Pre-existing, and not something we cared about
while the only inputs were our own albums — but publishing is exactly what changes the threat
model, and the new `MidiError` advertises "hand me untrusted bytes". The tempo map is fully
attacker-controlled: `us = 0xFFFFFF` with `division = 1` and a tick delta near `u32::MAX`
yields `song.seconds ≈ 7.2e10`, and `render` then does `vec![0f32; total * 2]` — a ~25 PB
allocation. `f64 as usize` saturates rather than being UB, so it is not unsound, but the
allocator calls `handle_alloc_error`, which **aborts** — not a catchable panic, so even
render-catalog's `catch_unwind` would not have saved it. `parse` now rejects a tempo map
implying more than 24 hours (`MidiError::TooLong`), and `render`'s allocation is documented.

**Four wrong rows in the GM table — in the section headed "GM coverage, honestly".**
Inherited from the old README, carried into the new one by Fable in good faith, and each one
verified false against the code:
- GM 38/39 are **SynthBass** (saw + sine sub through a swept resonant lowpass), not
  Karplus-Strong. The voice's own header comment says so.
- GM 42/43 (cello, contrabass) are a **stick-slip digital waveguide** with dedicated arco
  sample banks — not polyBLEP bows, and not "model-only" as DESIGN.md claimed. This is the
  crate's most sophisticated model and both documents undersold it.
- GM 45 is a **pizzicato pluck**, not a bow.
- GM 72–79: only **72 and 73** get the flute sample bank. 74–79 are deliberately model-only,
  and the code explains why (a repitched transverse-flute transient destroys a stopped pipe's
  or a whistle's identity in exactly the window where the ear decides what it is).
- GM **108 (kalimba) was missing from the table entirely** — a hole between the "46, 104–107"
  row and the row that picks up 109.
DESIGN.md carried the same errors plus one more: it still described the output as
**peak-normalised to −1 dBFS**, which stopped being true at v0.16 (it is loudness-normalised
to −18 LUFS under a −1 dBTP ceiling), and it omitted `--lufs` / `--tp-ceiling` /
`--peak-normalize` from its flag table. All corrected.

**Also done from the review:** `#![warn(missing_docs)]` (the whole `live` module shipped
undocumented — `RealtimeSynth` and all six of its methods now carry docs, including that
`render_add` is *additive*); a compile-time `Send + Sync` assertion on both error types (the
enums are designed to grow, and a future variant carrying an `Rc` would silently break every
async caller); and `crates/ferrosintesis/examples/quickstart.rs`, which is the README's
quick-start as a **compiled** example, so the crate's landing-page code can never rot.

## The render-diff inventory (the check the review said I owed)

The review's fairest hit was process, not code: *"this claim is verified by reading, not by
observing."* The repo's own policy mandates a render-diff for any `engine.rs` change. Run it:

Baseline = a throwaway worktree at `origin/main` (1679ff7), release binary. Compared against
the v0.17.0 release binary over the six `demos/ferrosintesis_reference` MIDIs (which exist to
exercise every voice family, the kit, and the controllers one at a time) plus one track from
each album.

**Result: 10 identical, 0 differing.** The refactor does not move a single sample. And the
property is now pinned in the code forever by
`engine::tests::render_with_progress_is_bit_identical_to_render`, so a future change that let
the progress callback (or the counter that fires it) touch engine state fails the build rather
than silently re-voicing the catalog.

Two independent arguments now back the claim: inspection (`active_voice_count(&self)` is a
pure `self.active.len()`; `next_report` is written and read in three lines and never feeds the
DSP) and observation (bit-exact compare).
