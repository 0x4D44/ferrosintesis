# 2026.07.13 — JRN — ferrosintesis pre-1.0 API pass for crates.io

## Why

Arthur asked whether we should publish the synth to crates.io "as the first version".
A six-lens read-only audit (36 agents, adversarially verified) said: nothing legally or
mechanically blocks a publish, but the *library's public face* is not ready, and a 1.0
would freeze four semver landmines. Decision: do the pre-1.0 API pass, publish **0.17.0**,
earn 1.0 later. This journal covers the pass. **Nothing has been published.**

## What the audit found (and got wrong)

Refuted worries — all three of my priors were wrong, which is why the audit was worth running:

- **Package size fits.** Real `cargo package` measurement (not the audit's gzip proxy):
  samples-core **7,102,046 B** (6.77 MiB), samples-orchestral **7,005,718 B** (6.68 MiB),
  against the 10,485,760 B cap. ~33% headroom each. Merging the two banks WOULD bust it.
- **Sample licensing holds up.** 202 WAVs, all CC0, chased to source: 195 from VSCO 2 CE
  (commit-pinned `4403009…`), 7 from FreePats (SHA-256-pinned). `prepare.py` maps every
  output file to an upstream URL; 202 mapped, 202 on disk, zero orphans.
- **Publish mechanics are clean.** No `build.rs`, no `include_bytes!` escaping a crate root,
  no bare path deps, zero third-party dependencies.

The one real blocker is mechanical and unchanged: ferrosintesis exact-pins the two sample
crates at `=0.1.0` and neither is on crates.io yet, so publish order is forced —
**samples-core → samples-orchestral → ferrosintesis**.

## What I changed

The theme: the crate was an excellent engine with a CLI-shaped API bolted to `pub`.

1. **A real error type.** `offline::load`/`parse` returned `Result<_, String>`, which does not
   implement `std::error::Error` — a downstream user could not match on a kind or `?` it into
   `anyhow`. Added `MidiError` (`src/error.rs`), `#[non_exhaustive]`, `Display` + `Error` with a
   source chain. The parser's error sites mapped cleanly onto real variants (`NotMidi`,
   `UnsupportedFormat(u16)`, `UnsupportedTimeDivision`, `MissingTrack{index}`,
   `BadStatusByte(u8)`, `UnexpectedEof`, `Io{path, source}`) — no `Parse(String)` cop-out was
   needed. `Io` keeps the path so the CLI's `error: song.mid: ...` message survives.
2. **`#[non_exhaustive]` + a builder on `Options`.** Adding an 8th render knob after a 1.0 would
   have been a major bump. Also `Stats`, `Progress`, `RealtimeOptions`, `RealtimeError`.
   **Non-obvious:** `#[non_exhaustive]` forbids *functional update* (`..Default::default()`) from
   a foreign crate too, and `let mut o = Options::default(); o.sr = x;` trips clippy's
   `field_reassign_with_default` under our `-D warnings` gate. So a `with_*` builder is not
   sugar — it is the only clean construction path. Fields stay `pub` for reading.
3. **The library no longer writes to stderr.** `Options.verbose` drove an `eprintln!` from inside
   the render loop. Replaced with `render_with_progress(song, opt, &mut dyn FnMut(Progress))`;
   the CLI now owns its own progress printing. `render()` delegates with a no-op closure, so the
   audio is bit-identical.
4. **Docs.** Crate-level `//!` with a doctest that actually parses and renders an in-memory SMF
   (not `no_run` — it proves the headline example works on every `cargo test --doc`), and `///`
   on every public item, including the audio contract (interleaved stereo f32 at `opt.sr`).
5. **README split.** The 23 KB design essay moved to `crates/ferrosintesis/DESIGN.md`; a new
   crates.io landing page took its place. **Written by Fable 5** on a consult (see below).
6. **MSRV declared: 1.87.** Verified, not asserted — see the surprise below.
7. Version 0.16.0 → **0.17.0**, with the `ferrosintesis-cli` and `render-catalog` dependency pins
   moved in lockstep (both pin the lib; the audit's proposed fix named only the CLI and would
   have left the workspace unresolvable).

## Surprises

**The manifest could not be parsed by the MSRV we were about to declare.** `cargo +1.87 check`
failed with `invalid inline table` — `ferrosintesis-samples-orchestral` was declared as a
*multi-line* inline table:

```toml
ferrosintesis-samples-orchestral = {
    path = "...", version = "=0.1.0", optional = true,
}
```

Multi-line inline tables are invalid TOML 1.0; only recent cargo accepts them. Every one of the
36 audit agents missed this, because none of them ran an older toolchain — they all reasoned
against the manifest with a 1.95 cargo, which parses it happily. Fixed by putting the dependency
on one line, with a comment saying why. **This would have shipped a crate that a user on our own
declared MSRV could not build.**

**The MSRV itself was wrong by inspection.** The audit's verifier grepped for `OnceLock` and
`is_some_and` and concluded "≥1.70". That is a lower bound, not the answer: clippy's
`incompatible_msrv` lint (which only fires once `rust-version` is *set*) immediately found
`is_multiple_of` (stable 1.87) and `is_none_or` (1.82) in `altbank.rs` and `voices.rs`. True floor
is **1.87**, now verified by a real `cargo +1.87 check --workspace`.

**The repo has been carrying a performance claim that is off by 8x.** DESIGN.md (formerly the
README, and therefore about to become the crates.io landing page) said "Renders ~14 minutes of
stereo 44.1 kHz audio in under 20 seconds" — ~42x realtime. Measured on Big Weather's "First
Light Freeway": **245.8 s of audio in 46.8 s wall = 5.25x**. The old number presumably predates
the orchestral voices and the sample layer. Fable carried it into its README draft in good faith
(it had no way to know); I only caught it because I ran the render rather than trusting the text.
Both documents now carry the measured figure.

## Fable 5 consult

Delegated the README + crate-level rustdoc to Fable (a *craft* deliverable — the crate's only
landing page — not mechanical work). Briefed it with the exact post-change API, the competitive
positioning, and the voice to keep; demanded the reasoning and a flagged list of anything it
inferred rather than read.

It delivered well, and its self-flagged uncertainty list was the valuable part. I verified each:
- GM 88–103 row ("splits between bell-like modal voices and sustained washes") — **correct**:
  `voices.rs:8195` routes 88..=95 to pads, `:8169` routes 96..=103 to Fx.
- Determinism claim — **correct**: dither RNG is fixed-seed (`Rng::new(0xD17E)`), and every
  `Instant::now()` in the crate is inside a test.
- MSRV 1.70 — **wrong** (it took my brief at face value; my brief was wrong). Corrected to 1.87.
- ~40x realtime — **wrong** (carried from the old README). Corrected to the measured 5x.

Mid-flight I had to send it a contract correction (the builder, and `MidiError::Io` as a struct
variant) once I discovered the clippy interaction. Cheap, and it reworked cleanly. Lesson: settle
the API *before* commissioning the words about it — I nearly wasted the consult.

## Verification

Full gate green in the worktree:
- `cargo fmt --check` — clean
- `cargo clippy --workspace --all-targets -- -D warnings` — clean
- `cargo test --workspace` — 377 passed / 0 failed / 8 ignored, plus 22 across the other suites
- `cargo test --doc -p ferrosintesis` — 3 passed (incl. the crate-level SMF parse+render doctest)
- `cargo build --release -p ferrosintesis-cli` — clean
- `cargo +1.87 check --workspace` — clean (MSRV proven, not asserted)
- `cargo package -p ferrosintesis-samples-{core,orchestral} --no-verify` — both well under the cap

**Not** verified: a full `cargo publish --dry-run` of `ferrosintesis` itself. It cannot pass until
the two sample crates are actually on the registry (the verify build resolves `=0.1.0` from
crates.io, not the path). That is expected and is the forced publish order, not a defect.

## Still open (for Arthur)

- **The publish itself has NOT happened** and needs an explicit go. crates.io is a one-way door:
  a version can be yanked but never deleted.
- **No root LICENSE.** Everything outside the crate dirs (`tools/`, `albums/`, `build.py`) is
  all-rights-reserved by default. Fixing it is one file, but a blanket root MIT would sweep in
  nineteen albums of creative work — that is Arthur's call, not mine. Parked in scratchpad.
- **`ferrosintesis-cli` is `publish = false`**, so `cargo install ferrosintesis` will not work.
  Deliberate per the 2026.07.09 HLD; worth restating in the release notes so nobody expects it.
