# 2026.07.16 — JRN — Slipstream (ten-display album inspired by Three-Sixty-One)

## Task
Arthur loved "Three-Sixty-One" (Through Lines T16) and commissioned a ten-track
album inspired by it: same complex soundscape, multiple counterpoints, soaring/
sweeping synths, complex rhythm and fills, highly layered, DUAL GUITARS,
build-drop-build architectures; occasional T361 references, largely different.

## Design (done)
- Concept: **Slipstream** — an air display in ten acts; the dual guitars are a
  two-ship display team flying a different machine-verified formation per track
  (octaves / trades / contrary / inversion / hocket / mirror canon / sixths /
  retrograde / soar-over-pedal / lead+counter).
- HLD: `wrk_docs/2026.07.16 - HLD - Slipstream album (ten displays).md` —
  global disciplines (duo, pan, contour, fills, soar, counterpoint) + ten
  per-track contracts with oracle plans. T361 quotes pinned verbatim in
  material.py (ORBIT_RIFF_361, SCREAM_*_361), used in T1 (wink), T9
  (searchlight), T10 (flypast + scream reprise).
- Scaffold: `albums/fable5/Slipstream/` in the federated movements shape —
  machinery copied from Through Lines; new conductor.py (registry, 10 tracks,
  seeds 202611NN) and material.py (ASCENT_CELL, mirror(), FILL_LIB A-H with
  A-F inherited note-for-note from T361, quotes, Morse) — verify_material()
  green. `COMPOSER-NOTES.md` = compact exemplar digest so composer agents
  don't re-read t16 (token economy). Registered in render-catalog ALBUMS
  (compiles; NOTE: discover() errors until midi/ has files — resolved once
  tracks land, must be green before integrate).
- ferrosintesis-cli release binary built in the worktree.

## Composition process + the constraint that shaped it
- Plan: one subagent composer per track (self-contained modules; scoped
  `build.py --track N` loops; plain-text reports per the Winter Guests
  lesson), adversarial judge per track.
- **BLOCKER pattern: the account's 5-hour usage windows.** Launch 1 (10
  parallel composers, 11:00) burned the window tail → agents died on
  "session limit, resets 12:10pm". Relaunch (batched 2-at-a-time, 12:14)
  exhausted the NEXT window ~50 min in (~450k subagent tokens) → all died,
  next reset 5:10pm. No files were lost (composers write at the end; nothing
  half-written), but zero tracks landed from ~900k tokens spent. The window
  budget is shared fleet-wide — heavyweight parallel composition does not fit.
- **Strategy now:** strictly ONE composer at a time; composer reads the cheap
  digest (COMPOSER-NOTES.md + HLD + engine.py + material.py) instead of the
  full exemplar; judges cut (build.py --verify is the objective gate; the
  lead re-runs it inline); wakeup-driven loop resumes at each window reset
  (next: 17:10). Expect ~2-4 tracks per clean window; overnight windows
  finish the album.
