# 2026.07.18 — JRN — CC7 volume / CC10 pan controller slew (MM-BUG-KILN-00011)

Engineer's log for routing CC7 (channel volume) and CC10 (pan) through the same
per-block slew that CC11 (expression) already uses.

## Context / diagnosis

- CC11 is smoothed: `expr_target` (set by CC) + `expr` (slewed current), updated once
  per BLOCK by `strip.expr += self.expr_smooth * (strip.expr_target - strip.expr)`
  (`engine.rs:2326`). `expr_smooth = 1 - exp(-BLOCK/(0.03*sr))` (`engine.rs:1196`),
  a ~30 ms one-pole calibrated for once-per-block application.
- CC7 volume (`engine.rs:1706`, `s.volume = v*v`) and CC10 pan (`1707-1710`,
  `s.pan = v` + `s.haas_delay` derived) are applied DIRECTLY. `g` and `theta` are
  recomputed once per 64-sample block from those un-slewed values → a CC7 fade or
  CC10 sweep steps hard at block boundaries (~1.45 ms grid).
- `reset_all_controllers` (CC121, `engine.rs:1901`) does NOT touch volume or pan —
  correct GM semantics (CC121 resets neither). The existing test at `engine.rs:3584`
  asserts volume/pan survive a CC121, which pins that.

## Key decision: jump-on-first-author (why not just mirror CC11)

CC11 slews from its default (1.0) even on first author. If I copied that for volume,
the FIRST CC7 on a set-once channel would ramp from the default (100/127)² over
~30 ms instead of jumping — which would CHANGE every catalog album's render (they all
set CC7/CC10 once at the top). The bug explicitly says "on the fable5 albums (CC7 set
once) *any* render-diff would be a bug." So bit-identicality of set-once controllers
is an acceptance criterion, and jump-on-first-author is required, not a nicety:
first CC7/CC10 sets current = target (instant, exactly as today); subsequent values
only move the target (slew). A set-once channel is therefore bit-identical; only a
genuine *sweep* (repeated CC7/CC10) newly smooths.

## Plan

Fields per strip: `volume_target`+`volume_authored`, `pan_target`+`pan_authored`
(mirroring `expr_target`/`expr_authored`). Slew volume/pan once per block next to the
expr slew. Move haas_delay derivation to per-block (tracks slewed pan), gated on
`pan_authored` so a channel with no CC10 keeps haas_delay = 0 exactly as today.

## SURPRISE / BLOCKER (2026.07.18): design premise refuted

The bug (and my DRAFT AC1) assumed the catalog sets CC7/CC10 once. **False for pan.**
My own scan of 124 committed MIDIs:
- **24 MIDIs automate CC10 pan** multi-value (Three-Sixty ch0 = 1219 events full
  0→127; Bright Matter ch0 ~1250; Winter Guests ch2 = 930; + demos). Slewing pan
  changes all 24 albums.
- **1 MIDI automates CC7 volume** (Hollow Hill Part Two ch14 = 82→0→78, a hard cut).

Key reframing: catalog CC7/CC10 are authored at *musical* (CC-event, ~100 ms)
resolution, not per-block — so there is no catalog block-rate zipper to fix; the
block-boundary stepping is a *foreign-GM* concern. The fix mainly serves faithful
foreign playback; its catalog effect is a side effect to minimise.
