# 2026.07.20 — JRN — GM109 bagpipe: periodic click on held notes

Arthur: *"When a note is held for the bagpipes there is a periodic clicking sound —
it's as if we've not selected the right loop extents?"*

He was right, and the diagnosis is more specific than "the extents are slightly off":
the bake's loop-search **objective actively preferred the broken window**.

Worktree `D:\worktrees\midi-music\20260720-FIX-HUM-bagpipe-held-note-loop-click`,
branch `task/20260720-FIX-HUM-bagpipe-held-note-loop-click`, off `origin/main` `dbef98a`.

## Reproduction

Rendered 16 s held GM109 notes (CC91=0, CC93=0) with the release CLI, then folded a
spectral-flux novelty curve (512-pt Hann, hop 64, half-wave rectified) at the exactly
predicted loop lag. 6–9 sigma on nearly every pitch. A held clarinet (GM71) and the
`--no-samples` modeled GM109 show nothing.

Folding the baked buffers in isolation is starker still — novelty peak **35–62x the
median**, against a null control (folding at a lag that is not the loop) of 1.5–2.6.

## Root cause

`LoopVoice` (`sampler.rs`) plays a whole baked WAV on a plain modulo wrap — no
crossfade, no loop metadata. The buffers were 0.40 s (chanter) / 1.5 s (drone), cut by
`prepare.py::extract_loop`, whose entire search was:

```python
val   = abs(x[i] - x[j])                              # i = fixed SFZ loop point
slope = abs((x[i+1] - x[i]) - (x[j] - x[j-1]))        # j = i + length
return val + slope
```

Two scalars at a single sample pair, with the START FIXED and only the endpoint moved
over +/-2 periods. For a harmonically rich reed that is degenerate: a value+slope match
is 2 constraints, which roughly `2H` phases per cycle satisfy, so the minimiser lands
off the integer-period grid. Re-deriving the committed choice from the cached sources,
the old cost rates the **non-integer** length better on every single file — for
`chanter_G5` by 11x (0.012 vs 0.138). The search did not fail to find the good loop;
the objective ranked it worse.

Two distinct defects followed, both once per loop:

1. **Harmonic phase jump** — the wrap lag equals `frac(n/period) x period` in all eight
   files. Large in `chanter_F4` (+17.4 smp), `chanter_C5` (-5.5), `chanter_G5` (+22.0,
   0.384 of a period) and `drone_G2` (-17.7).
2. **Level/timbre drift inside the window** — `chanter_G4` and `chanter_D5` each carry a
   clean monotone ~4 dB ramp (r^2 0.97 / 0.91) across the loop, so the wrap steps 4 dB
   ~2.5 times a second. `chanter_C5` drifts ~475 Hz in spectral centroid at flat level.

`chanter_A4` is genuinely clean on both counts (172.001 periods) — and it is exactly the
zone that measured quiet in the render (foldZ 2.85 vs 6.4–8.8). That correlation is the
strongest single piece of evidence.

## Why it shipped

The bake gate `_seam_click` measures a **single-sample** value step; the runtime oracle
`bagpipe_loop_sustains_across_wraps` only checks RMS stays flat within 20%. Neither can
see a phase jump or a slow ramp buried in a buzzy reed. Same class as the sax-loop entry
already in `lessons_learnt.md` ("a seam-clean sustain loop is NOT a flat loop").

## What I ruled out

A workflow lane re-implemented `LoopVoice::render` bit-faithfully in numpy and rendered
with **no engine at all**. The artifact reproduces at 4.7–11.5 sigma. Swapping f64 phase,
or linear for cubic interpolation, does not remove it; feeding a mathematically perfect
loop through the same code scores at the decoy null. Reverb/chorus/bus-glue/limiter
factorials move nothing (2.37 vs 2.37 with the limiter off). So: not the engine, not the
interpolator, not the mix. The bake.

**Hypothesis I got wrong and had to drop:** trimming the shipped buffer to a whole number
of periods barely helps and sometimes hurts (`chanter_G5` 39 -> 58). Integer-period
trimming of a window whose *content* drifts fixes nothing. The window has to be chosen,
not repaired.

## The fix

**Bake side** (`tools/ferrosintesis-samples/prepare.py`):

- New `wrap_error_db(x, start, length, probe)` — the physical discontinuity: what the
  modulo wrap plays (the head) minus what naturally FOLLOWED in the recording, in dB
  relative to the loop's RMS. Only the bake can measure this; it needs the source
  continuation, which the shipped buffer no longer has. It sees every harmonic, and a
  phase jump and a level step alike.
- New `find_loop` — two-stage. An O(1) cheap cost (via prefix sums, since prepare.py is
  stdlib-only) ranks candidates over **both** start and length, lengths restricted to
  integer period counts (+/-2 samples for f0 error), scored on seam value+slope, RMS
  half-parity and brightness half-parity. The best 24 are then scored by `wrap_error_db`
  and the winner wins. Ranking by the cheap proxy alone is precisely what shipped the bug.
- `BAGPIPE_LOOP_S` becomes ranges: chanter `(0.06, 0.14)`, drone `(0.08, 0.20)`. Short by
  design — a 0.4 s loop cannot dodge the reed's own drift, and repeats at ~2.5 Hz where
  the ear counts clicks; under ~0.12 s the repeat sits above ~8 Hz and fuses into timbre.
- Hard gate `BAGPIPE_MAX_WRAP_DB = -14.0`, raising rather than shipping a click.

**Runtime side** (`crates/ferrosintesis/src/sampler.rs`):

- `LoopVoice.pos`/`step` f32 -> f64. The read phase climbs to `n` and resets every wrap,
  so f32 rounding error was itself a loop-rate sawtooth: error RMS ramped 28x (29 dB)
  across a loop, lifting sidebands on a 5 kHz partial from -97 to -68 dB. Real, ~59 dB
  below the bake defect, and free to remove. `LoopVoice` is used ONLY by GM109 (chanter +
  both drones); `SaxLoopVoice` is a separate type and untouched.

## Results

Re-baked all eight buffers with `python prepare.py --only=chanter` (sources were already
cached under `%TEMP%/vsco2ce_src/<VSCO_REV>`; no network needed). Wrap error now **-16.3
to -25.1 dB**, all passing the gate. Buffers shrank from 17.5k/66k samples to 2.7k–6.3k.

render — key 69 is the cleanest of all at excess 0.01.)

## The oracle

`sampler::tests::looped_sustain_banks_are_loopable` — written over the BANKS, not the
bagpipe, so any future looped sustain is covered the day it lands. Per zone: a whole
number of pitch periods (|frac| < 0.05, using the zone's measured `root`), level spread
< 3 dB and brightness spread < 4 dB across 20 ms blocks.

Verified genuinely red: with the old WAVs restored it fails on the first zone —
`chanter @341.4 Hz: loop spans 138.158 periods`. Green on the new bake.

Bake side gained four new tests in `test_prepare.py`, including one that pins the
integer-period property and one that rejects a window spanning a swell. Note the test
tone had to become **harmonically rich** — a single sine identifies its phase uniquely
from value+slope, so the old broken search passed on it. That is why the unit tests never
caught this.

## Notes / follow-ups

- Only the demos use GM109 (`demos/synth_feature_showcase`, `demos/ferrosintesis_reference`);
  no album does. Render-diff reach is demos only.
- The FreePats archive holds 26 WAVs (24 chanter takes + 2 drones); the bake uses 8 and
  ignores `A#4/B4/C#5/D#5/E5/F5/F#5` entirely. Better zone coverage is available — parked
  in `scratchpad.md`, not this change.
- `SaxLoopVoice` animates its loop (vibrato, tremolo, +/-0.22% read-rate random walk
  explicitly commented "defeats the loop-tell"); `LoopVoice` has none. Adding just the
  drift is a plausible future refinement, but NOT the tremolo: the bagpipe must stay
  constant-amplitude (`bp_o1_bagpipe_chanter_is_constant_amplitude_saxes_keep_dynamics`
  pins it, and constant bag pressure is the instrument). Parked.
- Measurement trap that cost me a cycle: the FreePats sources are **24-bit** (`sw=3`).
  Reading them as 16-bit yields noise that folds flat and looks like a perfect loop. One
  workflow lane hit the identical trap independently.
- Metric trap: `foldZ` (a z-score) saturates — it reads 5.7–6.5 on signals whose true
  excess is 1.02. Use peak/median with explicit decoy-lag nulls instead.
