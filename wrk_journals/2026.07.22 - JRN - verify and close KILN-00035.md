## Method: an independent repro, not the fixer's tests

Both facets of the original observation are reachable from the **public** API
(`offline::{parse, render}`, `live::RealtimeSynth`), so I wrote my own repro
rather than re-running the fixer's coverage. Because it touches no `pub(crate)`
item, the *same file* compiles on the pre-fix tree (`5605e67`) and the post-fix
tree — which is what makes the fails-before/passes-after check meaningful here.
(The fixer's own tests reference `EvKind::GmReset`, `decode_sysex_payload` and
`voice_seed_index`, none of which exist pre-fix, so they *cannot* be run against
the old code at all.)

The repro asserts **parity between entry points**, which is exactly what the bug
claims is broken — not an absolute threshold:

- **Facet 1** — an SMF holding a note across a mid-file GM System On, and the same
  wire bytes through `RealtimeSynth`. Observable: did the held voice survive?
  (offline `Stats::max_polyphony > 1`, live `active_voice_count() > 0`).
- **Facet 2** — GS "Use for Rhythm Part" (block `0x1A` → channel index 10) followed
  by a note on that channel, rendered with and without the SysEx, offline and live.
  Observable: does the message change the audio?

Kept as a scratch instrument (`crates/ferrosintesis/tests/kiln35_entry_point_parity.rs`,
uncommitted) — the fixer already landed seven regression tests; committing a
parallel set would be duplication, and it would turn a docs-lane closure into a
code branch.

## Result — post-fix (`b63bd51`, contains `c26dfff`)

Both pass. Root cause is addressed at the right layer: one shared recognizer
(`midi::decode_sysex_payload`) is now the *only* place a system SysEx shape is
defined, and both entry points call it — so the two paths cannot drift again by
construction. GM System On got its own `EvKind::GmReset` → `EngineCore::gm_system_on`,
used identically offline and live.

## Render safety — proved structurally, not sampled

The fixer claimed "all 124 catalog MIDIs byte-identical". I checked it two ways
that are stronger than a render-diff:

1. **A SysEx census over every committed MIDI: 140 files, zero SysEx events of any
   kind.** So no committed MIDI can reach any changed decode path — the stricter
   recognizer and the new `GmReset` sort key are unreachable from the catalog.
2. `voice_seed_index` (new, decoupled from `Stats::voices_spawned` so a GM reset can
   restart seeding while public stats stay cumulative) is the load-bearing risk: if
   it ever diverged from `voices_spawned`, *every* render would change. All three
   `stats.voices_spawned += 1` sites (engine.rs:1608, 1951, 2104) are paired 1:1 with
   a `voice_seed_index += 1` on the next line, both fields start at 0, and both seed
   consumers (engine.rs:1578, 1986) read the new field. Absent a `GmReset` the two
   counters are provably equal, so seeds are unchanged.

## Deliberate behaviour changes I checked and accepted

The new recognizer is **stricter** than the old prefix matching. It now requires a
complete, exact, seven-bit payload in a terminated `F0` event, so three shapes that
the old SMF parser accepted are now ignored: a GS Reset missing its checksum byte, a
GM/XG System On carrying trailing bytes, and a System On split across `F0`/`F7`
packets. All three are out-of-spec or vanishingly rare, none appears in-repo, the
live path now behaves identically, and `system_sysex_rejects_malformed_shapes`
codifies it as intended. This is a design decision consistent with the bug's own
goal (one shape definition, no drift), not a residual gap — **no new ID split.**
