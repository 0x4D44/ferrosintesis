## The fix

`LaVoice::build` applied the `0.5..=2.05` credible-repitch window to the
**sample-rate-converted playback step** rather than the musical pitch ratio. At 96 kHz
every step is scaled by 44100/96000 = 0.459, so a note sitting essentially *on* its zone
root — ratio ~1.0, the most credible repitch there is — fell through the lower bound and
silently lost its sampled onset, while a far less credible octave-up repitch landed
mid-window and engaged. Choosing a legal output rate changed the instrument.

Fix: validate `ratio = target_hz / zone.root`, then convert with `* 44100 / sr`. The
`step` expression is unchanged operation for operation — only the guard moved.

## Two things the report understated, both found by sweeping instead of trusting it

**1. 186 combinations, not 3 programs.** The report named GM 33/34/35. But `build` is the
shared entry point for *every* LA-wrapped voice, so I swept programs 0..=127 x 8 keys x
{44.1, 48, 96} kHz against the pre-fix tree: **186** (program, key, rate) combinations
changed eligibility with the output rate. Mostly 96 kHz losing what 44.1 keeps; a few
(GM 4 key 64) already broke at 48 kHz.

**2. A second SRC-scaled guard.** `LaVoice::retrigger` re-checks the window when a
round-robin stroke rotates zone, and it tested a step too — same defect, same file, ~200
lines down. Fixing only the reported site would have left tremolo restrikes
rate-dependent. This needed a new `base_ratio` field: `retrigger` re-checks against a
*different* zone root and cannot recover the ratio from `base_step` without knowing `sr`.

This is the third time in two passes that "enumerate the whole thing before fixing the
reported item" paid. It is not a list this time — it is a shared code path and a copied
guard — but the same discipline caught it.

## The engagement detector is exact, not thresholded

Worth remembering. When `build` rejects a note it returns `Err(sustain)`, and the caller
unwraps **the same model** `samples: false` would have built — same program, key, seed. So
the two renders are bit-identical, and *any* difference means the sample engaged. No RMS
threshold to tune, no flaky margin, and it works uniformly across all 128 programs
including whole-voice sampled ones.

## What I did NOT test, and why

The report asked for pitch regressions alongside engagement. I dropped them. On an
**unmodified** tree, a Goertzel peak on GM 35 E1 moved 35 cents between 44.1 and 48 kHz
purely on bin spacing — at 41 Hz over a 0.5 s window the estimator cannot resolve the
question being asked. Pinning a threshold there would have measured the estimator, not
the synth (`lessons_learnt`: "Prove an estimator can SEE the effect before pinning a
threshold"). The step formula is algebraically unchanged, so there is nothing for a pitch
test to catch here anyway.

## A new bug fell out: KILN-00074

The all-program sweep panicked. Exactly two combinations: **GM 42/43 at C1 at 96 kHz**,
`attempt to subtract with overflow` in `DelayLine::tap`. `BowedString` allocates its two
waveguide lines with literal sample counts (`voices.rs:8436-8437`, `new(320)` and
`new(1600)`) that do not scale with `sr` — every other `DelayLine` site in the crate
derives its size from `sr` or the target delay. C1 needs ~1349 samples at 44.1 kHz but
~2936 at 96 kHz. In release the index wraps instead of panicking, so it degrades to silent
wrong-sample reads.

Raised as `MM-BUG-KILN-00074` (Should/High) and **deliberately not fixed** — different
mechanism, different file, and this pass fixes KILN-00061. The sweep carries a two-entry
skip list naming that bug ID, with an instruction to delete it when that bug lands. That
keeps an unrelated crash from reddening this oracle without hiding it.
