# 2026.07.24 — JRN — KILN-00064: the sustain-loop search off the realtime path

Fixing pass, one bug. Picked `MM-BUG-KILN-00064` (Should / High) as the highest-value
Open item landable unattended. The other Should/High, `MM-BUG-KILN-00045`, is a
bass-family tonal recalibration — a listening-and-fitting job, not a one-pass fix.

## What the bug said, and what was actually true

The report: every samples-enabled **GM 76** NoteOn runs `find_bottle_loop()` while
constructing `BottleLoopVoice`, inside `fill_ring()`'s deadline-bearing block. 67.4 M
multiply-accumulates and 30,560 square roots per note, for a result that never changes.
And it runs *before* the pitch-ratio check, so keys that fall back to the modeled Wind
bottle pay it too.

All confirmed. But `find_bottle_loop`'s own doc comment says it is a copy of
`find_sax_loop` — so I read `SaxLoopVoice::new` before touching anything, and it has the
identical shape: search first, cache never, ratio second. **GM 64-67 had the same defect
and nobody had filed it.**

That is the repo's recurring pattern showing up again (CLAUDE.md, "Hand-maintained lists
are the recurring defect here"): the reported item was the newest instance, not the spec
of the work. Here it was not a list but a copied function — same shape of mistake.

Measured with the new counter, before the fix:

| Voice | NoteOns | Loop searches |
|---|---|---|
| GM 76 bottle | 10 keys | 10 |
| GM 64-67 sax | 4 programs x 2 vels x 7 keys | 56 |

One search per NoteOn in both. The memo was simply absent.

## The fix

The right layer turned out to be `Zone`, not either constructor. A zone and its PCM are
`'static` and immutable, so its loop bounds are a **constant** — the constructors were
recomputing a constant per note. So:

- `Zone` gains `sustain_loop: OnceLock<Option<(usize, usize)>>` plus a memoizing
  `Zone::sustain_loop(LoopFinder)` accessor. The "no usable loop" verdict caches too, so a
  failing search does not repeat either.
- Both constructors check the pitch ratio first, read the memo second.
- `prewarm()` resolves every sax and bottle zone's loop on the setup thread. It also warms
  `bottle_loop_bank()` for the first time — the **active** GM 76 route. Only the retired
  `bottle_bank()` onset bank was warmed before.

Behaviour is unchanged by construction: the memo returns the same bounds, and the two
reordered guards both return `None`.

## Three oracles, and why three

Proven fail-first: I reverted the bottle half, ran them, reverted the sax half instead,
ran them again, then restored. Each named its own bypass line and count.

1. `sampler::prewarm_leaves_no_sustain_loop_unsearched` — counts real searches during
   voice construction after `prewarm()`. Red at 10 and 56, green at 0.
2. `live::realtime_note_on_after_prewarm_does_no_decode_or_loop_search` — the same claim
   driven through `render_add`, so the work is measured where the deadline actually is.
   Replaces `sample_prewarm_is_available`, which only proved the call did not panic.
3. `sampler::every_sustain_loop_search_is_memoized_and_prewarmed` — source-derived. It
   enumerates every `find_*_loop` the file declares, then requires that no call site
   bypasses the memo and that `prewarm()` forces each one.

Number 3 exists because 1 and 2 enumerate the looped voices **by hand**. The moment a
third looped voice lands, they would keep passing while covering less — exactly the
silent-shrink failure KILN-00059/00060/00069 all shared. Deriving the set from the source
is what stops that.

## Two things worth remembering

**Put the counter in the search body, not at the memo.** Counting inside
`Zone::sustain_loop`'s `get_or_init` would count only searches that went *through* the
memo — so a future rewiring that called `find_bottle_loop` directly again would be
invisible to the very oracle written to prevent it. In the body, it counts the expensive
work no matter the route. I then routed the two existing direct test callers through the
memo so nothing legitimately bypasses it.

**The counter oracle cannot produce a false green, only an inflated red.** The first
fail-first run reported 20 searches where the bottle burst alone accounts for 10 — the
live oracle was running concurrently and sharing the process-global counter. That is
harmless in the direction that matters: when the invariant holds, *nothing* increments, so
no sibling can push it off zero. When it is already broken the number is a lower bound.
Documented on the test; rerun with `--test-threads=1` to attribute.

## Validation

- `cargo test -p ferrosintesis --lib` — 644 passed, 0 failed, 25 ignored (pre-rebase tree).
- `cargo fmt --all --check`, `cargo clippy -p ferrosintesis --all-targets -- -D warnings`
  — clean. Clippy wanted a `type LoopFinder` alias for the fn-pointer parameter.
- Render-diff inventory, scoped: **9 rendered, 0 diffs**. The six committed MIDIs that
  actually author GM 64-67/76 — found by parsing program-change events out of every album
  and demo `.mid`, not by grepping the Python — plus three controls that author neither. A
  control diff would have meant contamination; an affected-file diff would have meant the
  memo returns different bounds. Both clean, which is the expected result for a change
  that is bit-identical by construction.
- `origin/main` moved 13 commits ahead mid-task (the whole mandolin sample feature), so I
  rebased before the render-diff — otherwise the diff would have measured their work too.

Timing was never measured, here or in the report. The proven claim is the deterministic
one: zero searches and zero decodes during post-prewarm voice construction, down from one
search per NoteOn. Callback wall-clock remains unmeasured.
