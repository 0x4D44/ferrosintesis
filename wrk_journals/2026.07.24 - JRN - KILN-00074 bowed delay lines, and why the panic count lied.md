# 2026.07.24 — JRN — KILN-00074: bowed delay lines, and why the panic count lied

Third bug of the fixing pass, and the one I raised myself last pass. Fixing it also let
me delete the skip list it had forced into KILN-00061's sweep, so the two are now clean.

I raised this bug and I fixed it. That is allowed — two-eyes governs **closure**, not
fixing — but it does mean closure is owed to a different pair of eyes, and I have said so
in the ledger entry.

## The defect

`BowedString` allocated its two waveguide delay lines with literal sample counts,
`DelayLine::new(320)` and `new(1600)`, while the loop they must hold is `~sr / f` samples
long. Every other `DelayLine` site in the crate derives its size from `sr` or from the
target delay. These two were the exceptions, and a literal cannot be right at more than
one sample rate.

## The number in my own bug report was wrong

I wrote "exactly two panicking combinations" (GM 42/43 at C1 at 96 kHz). That was an
honest measurement of the wrong thing.

It counted **panics**. An over-long delay only panics when `idx + buf.len() - i`
underflows; for other values of `idx` the expression stays non-negative, `& mask` wraps
the index, and `tap` quietly returns an unrelated sample. A panic scan cannot see those.

Re-measured with the new `debug_assert`, which catches every undersized read rather than
only the ones that underflow:

| rate | undersized reads |
|---|---|
| 44 100 | 0 |
| 48 000 | **4** |
| 88 200 | 8 |
| 96 000 | 8 |
| 192 000 | 10 |
| **total** | **30** |

**It breaks at 48 kHz** — not a 96 kHz curiosity — and does so silently in release. That
is a materially different bug from the one I filed. 44.1 kHz is clean, which is the only
reason no album render was ever affected: it is the CLI default.

The lesson, and it is a general one: **a crash-counting probe measures the subset of a
memory-safety defect that happens to trip a bounds check.** If the failure mode has a
silent branch, count with an assertion placed at the invariant, not with `catch_unwind`
around the symptom.

## The fix, and where the guard went

`bow_line_len(sr, share)` sizes each line from the **same arithmetic `set_freq` uses**.
`BOW_MIN_HZ` is now a named constant shared by `set_freq`'s pitch floor and the sizing, so
lowering the floor without regrowing the lines — the latent way to re-create this — is one
edit instead of two files that must agree.

The more valuable half is in `dsp.rs`: `DelayLine::tap` now `debug_assert!`s that the
requested delay fits, naming both the reach and the line length. That guard is **general**
— it protects every `DelayLine` call site, not just the bowed string — and it converts the
silent-wrap failure mode into a loud, self-explaining one. The bug's own Fix section
suggested considering it; it turned out to be the thing that made the real scope
measurable at all.

It fires nowhere across the 653-test suite, so no other line is undersized on a tested
path.

## Oracles

- `every_program_renders_at_every_common_rate` — all 128 programs x 5 low keys x
  {44.1, 48, 88.2, 96, 192} kHz. Swept over every program rather than the two reported,
  because a fixed-size literal is a mistake any voice could carry and only a sweep says
  which do. The rate set is chosen because **nothing validates it**: both
  `with_sample_rate` builders accept any value, so every rate a caller can pick is a rate
  we ship.
- `bowed_string_survives_a_downward_bend_at_high_rate` — `set_freq` runs per sample off
  `base_f * bend * vib * drift`, so the loop grows *after* construction. A sweep that only
  renders at the written pitch would miss a line sized from `key_freq(key)` instead of
  from the floor. This is the case the obvious test does not cover.

Both proven red on the pre-fix tree before the fix was restored.

## Validation

- `cargo test -p ferrosintesis --lib` — 653 passed, 0 failed, 25 ignored.
- `cargo fmt --all --check`, `cargo clippy --workspace --exclude amp-lab --all-targets
  -- -D warnings` — clean.
- Render-diff inventory — see below. Expected zero: at 44.1 kHz the old buffers were
  already long enough, and `DelayLine` reads are `& mask` into a circular history, so a
  larger power-of-two buffer returns the identical sample for any delay that fitted in the
  smaller one. The inventory tests exactly that reasoning.

## Pass summary across the three bugs

| Bug | Reported scope | Actual scope |
|---|---|---|
| KILN-00064 | GM 76 bottle | + GM 64-67 sax, same copied guard |
| KILN-00061 | 3 bass programs | 186 combinations + a second guard site |
| KILN-00074 | 2 panics at 96 kHz | 30 undersized reads, from 48 kHz up |

Three for three, the reported symptom was narrower than the defect. In every case the
thing that found the rest was **sweeping the whole space instead of trusting the report's
enumeration** — which is the convention CLAUDE.md already states for hand-maintained
lists, generalising cleanly to copied code paths and to fixed-size buffers.
