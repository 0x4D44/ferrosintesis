# 2026.07.24 — JRN — KILN-00076: the backing loop stole the GUI's channel

Fifth bug of the fixing pass, and the first **Must**. An autonomous review pass landed nine
new bugs (KILN-00076..00084) mid-session, three of them Must, which re-ordered the queue
ahead of the Should/Medium synth-calibration band I would otherwise have reached.

## The defect

amp-lab's committed backing loop authored `CC0=1` and `Program 29` on channel 1 at tick
zero — the channel the GUI owns. `Player::advance` resets its event index to zero at every
wrap, so those are not one-off setup: they replay every 8 bars. UI rig changes are one-shot
messages, so the backing wins. Every wrap silently restored the GM29 lead while the UI and
the copied export both still showed the user's selection.

## Choosing between the report's two routes

The report offered either fixing the asset or filtering UI-owned channel state out of
repeated backing events at runtime. I took the asset route, and the deciding fact is one
line: `const BACKING: &[u8] = include_bytes!("../assets/backing.mid")`.

The backing is **compiled in**. There is no user-supplied sequence, so a runtime filter
would be dead code defending a case that cannot arise — complexity guarding a hypothetical.
Fixing the asset removes the conflict at source.

The safety check that made it a clean choice: `Lab::new` already calls `send_rig()` at
startup, so channel 1 is initialised from the current `Rig` regardless. The backing was
never the only source of that state — it was a redundant *second* source that outlived the
first.

Volume and pan stay backing-owned. They place the guitar in the mix; they do not choose
which guitar it is. Only voice state conflicted.

## Why two oracles again

- **The census** reads the shipped `include_bytes!` blob and rejects the whole class —
  Program Change, Bank Select MSB *and* LSB — not the two specific messages the generator
  happened to write. A census keyed to "does it contain `[B1 00 01]`" would pass the moment
  someone wrote the LSB instead. Red at **2**.
- **The two-wrap regression** reads what `Player::advance` actually emits, so a future
  `advance()` that re-sent setup state at a boundary would be caught even with a clean
  asset. Red at **6** — `[B1 00 01]` and `[C1 1D]` three times across two wraps, which is
  the reported mechanism made visible.

Neither subsumes the other: the census misses a player bug, the wrap test misses a dirty
asset replayed by some other path. Same pattern as the KILN-00059 pair.

## What I deliberately did not do

**I did not run the app.** amp-lab is an egui GUI holding a live cpal output device;
launching it unattended would grab the audio device and cannot be safely isolated (CLAUDE.md
is explicit about stopping there). The report had the same limit. So the audible transition
remains unmeasured, and I said so in the ledger rather than implying I had heard it. What is
proven is deterministic: those bytes are gone from the asset and never emitted across two
wraps.

## Gate note worth remembering

`.deltic-integrate.toml` **excludes amp-lab** from the integration gate — deliberately, since
it drags in egui + cpal (~200 crates) that no shipped crate needs. So `cargo test -p amp-lab`
and `cargo clippy -p amp-lab` are not "extra diligence" here, they are the *only* coverage
this change will ever get. Trunk will not re-run them. Anyone touching amp-lab has to run
them by hand or the change lands ungated.
