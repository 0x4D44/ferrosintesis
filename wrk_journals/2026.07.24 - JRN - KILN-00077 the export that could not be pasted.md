# 2026.07.24 — JRN — KILN-00077: the export that could not be pasted

Sixth bug of the fixing pass, second **Must**, second amp-lab bug in a row.

## The defect

amp-lab's whole point is that a session ends with a *setting*, not an opinion — and the
Copy Settings button is how the setting leaves the tool. It emitted `amp(0, 72)` under an
`# engine.py` label. There is no `def amp(...)` in any album engine. The snippet raised
`NameError`, and even with a helper invented it carried neither the score object, the
channel, nor the beat.

So the tool's advertised deliverable did not work, and had presumably never been pasted.

## Why the old test did not catch it

`export_names_every_knob_and_flags_neutral` checked that the output *mentions* each knob
name and contains the prose "shipped voicing". Both were true of a completely unusable
snippet. It tested that the string was well-formed English, not that it was correct code.

That is the useful generalisation: **a test over a generated artifact's prose is not a
test of the artifact.** The fix is to consume the artifact the way its consumer does — here,
read it back as MIDI and compare against the bytes the live audition sends. Then the
tool and the pasted album cannot disagree about what the rig is.

## Choosing between the report's two options

It offered: emit against the existing API, or land a new `amp()` helper first and then
emit it. I took the first.

The deciding fact is that album `engine.py` files are **per-album copies**, not a shared
import. A helper would have to be added to each independently and kept in step, multiplying
the surface that can drift — for a snippet that is only three calls per knob anyway. The
existing `Score.cc` / `Score.program` surface is already sufficient.

## One judgement call worth recording

The old export elided neutral knobs. I now emit all six.

That looks like noise until you think about the paste target: an album's channel may already
carry a non-neutral amp block from an earlier beat. Eliding neutrals would *inherit* those
rather than reset them, so the pasted rig would silently differ from the auditioned one
depending on what came before it in the piece. Writing all six makes the snippet **set** the
rig.

It also has a testing consequence: it is what makes byte-equality against `Rig::bytes()` a
meaningful check rather than a curated one.

## The oracle

Parses the emitted snippet back into MIDI in Rust — not by executing Python. That keeps it
self-contained (no interpreter on PATH, no album fixture) and deterministic.

Two details that matter:
- An unrecognised call is a **hard failure**, not a skip. A line the parser quietly ignored
  is a line the oracle does not check.
- It cross-checks its parsed-line count against the number of `sc.` occurrences in the
  whole export, so a malformed line cannot slip past by simply failing to match.

Swept over all four program/bank combinations × five knob states × four channels. The bank
flag and the program are exactly what a single hand-checked case would have silently fixed
— the same "one example is not a sweep" lesson as the previous five bugs, in yet another
shape.

## Gate note, again

`.deltic-integrate.toml` excludes amp-lab from the integration gate, so `cargo test -p
amp-lab` and `cargo clippy -p amp-lab` are the *only* coverage this change gets. Trunk will
not re-run them. That is now twice in two passes; anyone working amp-lab should treat those
two commands as mandatory rather than optional.
