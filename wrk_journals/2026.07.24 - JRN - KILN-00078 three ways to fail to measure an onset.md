# 2026.07.24 — JRN — KILN-00078: three ways to fail to measure an onset

Seventh bug of the fixing pass, the last **Must**, third amp-lab bug in a row. The fix
itself was straightforward. Measuring it was not, and that is the part worth writing down.

## The fix

`Player::advance` had each event's frame and threw it away, so the callback submitted
everything due in the block before rendering any of it. Every event collapsed onto the
block's first sample — 23 ms of quantization at a 1024-frame buffer, and an on/off pair
inside one callback never sounded at all because both were applied before any audio
existed.

Three changes:
1. `advance` reports each event's offset within the caller's span.
2. The callback renders in **spans**: audio up to the next event, that event's bytes, on.
3. **The callback core is factored out of the cpal closure** into `audio::Core`.

Number 3 is the one that mattered most. The closure captures a device, so it only runs on
real hardware — which is exactly why a `Must`-severity scheduling defect existed with no
failing test to its name. Untestable code is where this class of bug lives. `Core::process`
takes a buffer and a frame count; a test drives it at any block size with no device at all.

## Three ways I failed to measure the wrap case

The report asked for a loop-boundary test. I wrote it three times as an audio test and
every version **passed while the bug was present**:

1. **"Is there a sound after the wrap?"** — true either way. Useless.
2. **Energy before vs after the scheduled onset.** When collapsed, the note fires early and
   has decayed to near-silence by its real slot, so both windows are ~0 and their ratio is
   noise. It passed by luck.
3. **First sample above an absolute gate.** Defeated twice: the previous note's release tail
   sat above the gate at the wrap, so it "found" the onset immediately in both cases. I
   lengthened the loop so the tail died away — and then the note's own **attack ramp**
   displaced the detected onset by ~230 frames, so the fixed code failed its own test.

The reason none of them could work only became clear after the third: **collapsing
quantizes an event to the start of the callback containing it, not to the wrap.** So the
error is at most one block, and any audio window wider than one block sees the two
behaviours as identical. I had been reasoning as though collapse dumped everything at the
loop boundary; it doesn't.

The offsets are exact integers. Measuring them as integers — a unit test on `advance` with
a hand-computed straddling span — is stronger, instant, and honest about what is being
claimed. That is what landed.

**The generalisable bit:** when an audio oracle keeps needing another epicycle (a longer
fixture, a different gate, a wider window), that is evidence the instrument is wrong for
the quantity, not that the threshold needs tuning. Ask what the quantity actually *is* —
here, an integer — and measure that. Three of this repo's existing lessons are the same
shape ("prove an estimator can SEE the effect", "score against a control render", "a metric
whose lowest band sits above what you changed"). This one adds: *if the artifacts keep
moving, change instrument.*

I kept the two audio tests that genuinely discriminate — first-changed-output-frame across
five block sizes, and the on/off pair — because those measure through the real render path
and both go red on the real defect.

## Validation

- `cargo test -p amp-lab` — 14 passed, 0 failed.
- `cargo clippy -p amp-lab --all-targets --locked -- -D warnings`, `cargo fmt --all --check`
  — clean.
- Fail-first: disabling the offset in **both** `advance` and the span loop turns all three
  timing oracles red. Pre-fix numbers: note 543 frames early at block 1024; the on/off pair
  1567 frames early.
- No render-diff: `crates/amp-lab/` only.

**Not verified:** audible jitter on Arthur's device. amp-lab holds a live cpal output device
and was not run, same limit the report had. Residual quantization is the synth's own
64-frame block — the report's suggested follow-up (a timestamped command surface on
`RealtimeSynth`) is deliberately not done here.
