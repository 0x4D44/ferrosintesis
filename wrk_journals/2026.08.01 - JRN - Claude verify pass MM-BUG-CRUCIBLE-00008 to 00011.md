## Method

Each fix ships its own regression test in the same file it repairs, so "check the
test out and confirm it fails without the fix" could not be done by reverting the
commit — that would revert the test too. Instead I reverted **only the production
hunk** in a scratch copy of `crates/render-catalog/src/main.rs`, kept the tests,
and re-ran them:

- 00009 — put `flatten()` back into `directory_paths` → both discovery regressions fail.
- 00010 — `if output.status.success()` → `if true` → the preflight regression fails.
- 00011 — polling loop → pre-fix unbounded `wait_with_output()` → the hanging-encoder
  test never returns (killed at a 90 s external bound).

`main.rs` was backed up by `cp` and restored by `cp` (md5 `336c0617…` before and
after) — no `git checkout` on a dirty tree, and `git status` clean at the end.

## Worth remembering

**A std-only test file can be run against another commit's data with plain
`rustc --test`.** For 00008 the oracle *is* the test, so reverting was impossible.
Instead I extracted the pre-fix `albums/` tree with
`git archive 3fbe77f^ albums | tar -x -C <tmp>` and compiled both the old and the
new `album_midi_overlaps.rs` standalone with `CARGO_MANIFEST_DIR` pointed at it.
The old oracle passes on that corpus; the new one reports 25 files and 7 243
same-pitch overlaps. That is the cleanest fails-before evidence available for an
oracle-vs-corpus bug, and it costs seconds — no second worktree, no cargo build.

**Regenerated MIDI needs a reproducibility check, not just a green oracle.** 00008
rewrote 26 committed `.mid` files. `python3 build.py` in
`albums/fable5/The Burning Meridian` reproduced them (and
`album_manifest.json`) byte-identically, and `--verify` was all-green — so the
committed files really are what the fixed engines emit.
