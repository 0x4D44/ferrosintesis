## What happened

The assigned area is a *generated* crate: 158 `include_bytes!` entries, one `get()`, two
self-tests. Almost no logic. So the review went where the risk actually is for a package
like this — whether the documentation it publishes is true, and whether the oracles that
claim to guarantee that actually run.

Three lenses: a reachability census, an adversarial "defeat the guards" pass, and my own
documentation/provenance read. I re-verified every subagent claim against source before
writing it down; two did not survive.

## The finding that mattered

`partial_summary_error` in `crates/ferrosintesis/src/inventory.rs:957` opens with
`if packaged.len() > 8 { return None; }`. This crate has 15 sample families, so all three
of its completeness checks — manifest description, README intro, module docs — return
`None` unconditionally. Every other branch of `public_inventory_surface_errors` is inert
here too (no README table, no "contents" word, the `--only=<family>` selector discarded
for its angle brackets). The oracle asserts nothing about this crate while counting it
toward its own `checked > 20` anti-vacuity bar.

Two things made it worth reporting rather than shrugging at:

**It is two-sided.** The module's own fixture `public_inventory_oracle_rejects_two_of_three_gm_summary`
(`inventory.rs:1497`) feeds a 3-family crate a description naming 2 of 3 and asserts all
three errors fire. The live crate is the same shape at 15 families and passes. Every
fixture in the module uses 2–3 families, so the `> 8` branch is exercised by no self-test.

**The blind spot is exactly the wrong two crates.** Only two of 25 sample crates exceed 8
families: this one (15) and `-orchestral2` (14). Those are the two aggregation crates —
and the two that have already produced published-doc drift bugs (KILN-00154, 00192,
00193). The guard switches itself off precisely where the defect recurs.

That is CLAUDE.md's "derived oracle is only as good as its enumeration predicate" again,
in a new costume: not a wrong predicate this time, but a *size-conditional* one. The `> 8`
bail was probably reasonable — a crates.io one-liner cannot name 15 families — but the
correct answer is to escalate the requirement (demand a complete README family table above
8) rather than to drop all three checks.

## Second-time-reported, still-unfiled

The published-doc defects (README says "six" chanter WAVs where 15 ship; the harpsichord's
VCSL source appears nowhere in the README; the crate description omits 27 of 158 files;
the onset/crossfade claim is wrong for the 17 bagpipe loops) were **already confirmed on
2026-07-27** by the previous review of this same crate. That pass recorded "Filing blocked;
no bug ID was created" — a write denial under `bugs/`.

19 days later they are still live, and this pass could not file them either: every shell
call is refused (`don't ask mode`), so `deltic bugs new` is unreachable. I dispatched a
subagent purely to test whether the denial was session-wide; same wall, both tools.

I considered hand-deriving `max+1` over `bugs/` and rejected it. The number space is
per-host and shared with `reqs/` and `issues/`, so a hand-picked ID can collide with a
sibling worktree's concurrent allocation — and because the two records land at different
paths, git merges both halves without a conflict. That is the precise failure the rule
exists to prevent. Better to report the blocker loudly than to poison the ledger quietly.

**The lesson is not about this crate.** Two review passes have now spent real effort on
the same defect and it has never reached the queue the fix loop drains. A review pass that
cannot write to `bugs/` produces prose, not tracked work.

## What was refuted

Worth recording, because these are the plausible-sounding findings a thinner pass would
have shipped:

- **Dead payload.** All 158 files reachable. The `bank!` macro takes a `$file:literal` and
  `embedded_wav` panics on an unknown name, so the requestable set is exactly the literals
  in `sampler.rs` — and each of the 158 appears once. Both `_f`/`_p` velocity arms and both
  chanter round robins are live.
- **`steel_*` looks dead** — it is the GM 25 CC0=2 alternate since the Eastman banks took
  the default slot. Reachable, therefore not dead, per the repo's own rule. This is the
  family most likely to trip a future census.
- **"Nothing validates WAV format."** The subagent's headline, and wrong as stated: the
  mono/16-bit/44.1 kHz promise *is* enforced by `parse_wav`'s assertion, given that every
  file is reachable and `prewarm()` initializes every bank. Narrowed the finding to what
  survives — silence, truncation, and per-file localization. Note the protection is a
  *consequence of full reachability*, not a packaging-time property: a future
  packaged-but-unread WAV bypasses it, exactly as the retired `drum_*` overlays did.
