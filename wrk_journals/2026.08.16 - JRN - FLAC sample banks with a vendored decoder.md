# 2026.08.16 — JRN — FLAC sample banks with a vendored decoder

## Why

`ferrosintesis.exe` was 105.73 MiB, and the embedded sample banks were ~104 MiB
of it. The banks are `include_bytes!`d, so they are most of what any
ferrosintesis-linked binary weighs — including `mdpc.exe` in the mddosem repo,
where the same banks were 50% of a 208 MB emulator. FLAC is lossless, so
re-containering them is a pure size change.

## Outcome

`ferrosintesis.exe`: **110,864,384 → 65,263,616 bytes (−43.49 MiB, −39.2%)**.
1,028 files converted, 864 of them kept; every one verified bit-exact.

## The decoder is vendored, and that was forced rather than chosen

Arthur's instruction was to vendor rather than take `claxon`. Reading CLAUDE.md
made clear it was the only option, not a preference: the root workspace's
dependency closure is 100% first-party path crates — zero `source =` lines in
`Cargo.lock` — which is what lets a fresh clone build the synth and render the
whole catalogue with no network. Both facts were re-measured at the start and
again at the end: still 0 `source =`, still 0 `build.rs` anywhere.

The absent `build.rs` also settled *where* decoding happens. It cannot be a
build step, so it is the existing `prewarm` pass, off the realtime thread.

`src/flac.rs` implements STREAMINFO plus CONSTANT / VERBATIM / FIXED / LPC
subframes with Rice and Rice2 residuals including the escape encoding. It is
scoped hard to 16-bit mono 44.1 kHz and rejects anything else by name — every
bank has been exactly that shape for as long as `parse_wav` has asserted it, and
we own the encoder. Narrowing is a safety property here, per the 2026.08.01
lesson on `seq.rs:Loop::parse`.

## Three oracles, layered

1. **Encode-time.** `to_flac.py` decodes each fresh FLAC back through ffmpeg and
   compares to the original `data` chunk before deleting any source. One
   mismatch aborts the run with nothing removed.
2. **Load-time, forever.** FLAC's STREAMINFO carries an MD5 of the *unencoded*
   audio. The decoder checks it on every load, so each bank proves its own
   bit-exactness with no reference WAV and no external tool. A vendored MD5
   backs it, pinned against the published RFC 1321 vectors rather than against
   values this implementation produced.
3. **Render-diff.** The mandated inventory for a `sampler.rs` change. For a
   lossless container swap the expectation is not "explainable diffs" but
   **zero** — same PCM in, same f32 out, same render.

Before wiring anything in, the decoder was compiled standalone and run against
ffmpeg output for 10 banks across flute, grand, hi-hat and sax: 319,958 samples
bit-identical, and 3,000 leading prefixes of the first file rejected without a
panic. It was correct first try, which I did not expect.

## What did NOT convert, and why

- **`b1-upright` (52 files, 9.80 MiB).** Every file carries a `b1t` chunk — the
  decimated mu-law natural tail from the 2026.07.28 HLD. A FLAC container has
  nowhere to put it. Moving these needs the tail in a FLAC APPLICATION block.
- **`drumkit` + `drumkit2` (164 files, 16.48 MiB).** These decode PCM *inside
  the asset crate*: `decode_wav` + `PCM_CACHE` in their own `lib.rs`, rather
  than handing bytes to ferrosintesis. Every sample crate is dependency-free by
  design and these are published to crates.io, so giving them FLAC means a new
  shared first-party crate in a published dependency graph. That is an
  architectural decision, so they were reverted to RIFF (restored byte-exactly
  from HEAD) rather than decided unilaterally.

Together that is 26.28 MiB still available, behind one design question:
**should the decoder become its own tiny published crate that both ferrosintesis
and the drum banks depend on?**

## The bit that cost time

I converted all 24 crates first and only then discovered the drum crates
self-decode. The workspace suite went from green to ~50 failures, and the
failure that named the cause was one assertion deep inside
`ferrosintesis-samples-drumkit/src/lib.rs:794` — not in ferrosintesis at all.

The lesson generalises past this change: an asset crate is not necessarily a
passive byte table. Before any container change, grep the asset crates for a
runtime decoder, not just the consumer.

## Oracles that fired correctly on the way

Worth recording because they are the repo's own pattern working:

- `payload.rs`'s anti-vacuity floors caught the scan collapsing to 216 files
  when the filters still said `.wav` — they refused to pass on a shrunken set
  rather than quietly asserting less.
- `no_document_states_a_stale_asset_crate_count` caught **my own README
  sentence**: "Three banks are still RIFF" parses as a claim that a default
  build embeds three asset crates. Reworded.
- `documented_payload_size_is_within_ten_percent` caught the README's "~111 MiB"
  against a measured 61.0 MiB.

None of these needed debugging; each named the problem.
